# PayHug 기능명세 · 기능별 정책 · IA — 구조 정의서

> 이 폴더(`payhug-spec/spec/`)는 **실제 개발된 프론트엔드 화면**을 기준으로
> **① IA(정보구조) · ② 화면·기능별 기능명세 · ③ 기능별 정책(가능/불가 · 연결 · 계산)** 을
> 하나의 행(row) 단위로 정리한 **구조(틀)** 다.
>
> **왜 이 구조가 먼저인가:** 나중에 (1) 개발자가 만든 산출물과 (2) 우리가 따로 정리한 정책 문서를
> 파일로 넣었을 때, 이 표의 행에 그대로 얹어서 **행 단위로 대조**하고 `확인 필요`를 `확정`으로
> 승격하거나 **충돌을 플래그**할 수 있게 하기 위함이다. 구조가 없으면 받은 문서를 어디에 매핑할지 알 수 없다.

---

## 1. 이 폴더가 무엇이고, 무엇이 아닌가

| 구분 | 이 폴더(`spec/`) | 이미 있는 다른 문서 |
|---|---|---|
| 다루는 것 | 화면·버튼·모달·토글 **단위의 기능 동작 + 정책** | — |
| IA | `01_IA.md` — 무엇이 어디에 있는가(라우트·메뉴·화면·상태) | `analysis/code_01·02` = 라우트 인벤토리(하이레벨) |
| 정책 원문 | 각 행의 "정책/연결/계산" 컬럼(화면 맥락) | `payhug-spec/01~07` = 정책 원문·논의 |
| 충돌·미확정 | 각 파일 C·D 섹션 + `90_정책레지스터.md` | `analysis/00_종합.md` = 충돌 레지스터 C1~C6 |
| 화면 이미지 | Figma node id로 참조 | Figma `Tcf69tIciGxmlqCIuRb0iI` 페이지 `511:174` (208 프레임) |

이 폴더는 **정책을 새로 확정하지 않는다.** 코드에서 관찰되는 "구현된 동작"은 사실로 적되,
**정책적 판단(되는지/안 되는지, 얼마로 계산하는지)** 은 근거가 있을 때만 `확정`, 없으면 `확인 필요`로 남긴다.

## 3. 메뉴별 파일 표준 양식

각 `admin/*.md`·`merchant/*.md`는 아래 4개 섹션(A~D)을 반드시 가진다. **모든 파일이 동일한 컬럼**을 쓴다.

### A. 화면 개요
- 목적 / 진입·권한 / 라우트 / 코드 경로 / Figma node / 캡처된 상태 변형 목록

### B. 기능 명세 · 정책 표 (핵심)

| 컬럼 | 의미 | 작성 규칙 |
|---|---|---|
| **#** | 행 번호 | |
| **기능/요소** | 버튼·토글·필터·모달·필드 등 | 화면에 보이는 라벨 그대로 |
| **트리거** | 무엇을 하면 발생하나 | 진입 / 클릭 / 토글 / 입력 / 조건충족 |
| **동작·결과** | 실제로 무슨 일이 일어나나 | 코드에서 관찰된 사실 위주 |
| **정책: 가능/불가** | 되는가/안 되는가 | `가능` / `불가` / `조건부(조건)` / `해당없음` |
| **연결** | 어디로 연결되나 | 이동 화면 · 호출 API(`GET admin/...`) · 상태전이(A→B) |
| **계산** | 어떤 계산이 일어나나 | 수식·기준(수수료율·지급일 등). 없으면 `해당없음` |
| **근거** | 무엇을 보고 적었나 | `code app/x/page.tsx:120` · `문서 03 §2` · `node 947:2` |
| **상태** | 확신 수준 | `확정` / `가설` / `확인 필요` (§4) |

### C. 정책 확인 필요 항목 (Open Questions)
- 이 화면에서 근거 없이 확정할 수 없는 정책 질문을 체크리스트로. `[[07_OPEN_QUESTIONS]]` 및 `Cn` 연결.

### D. 미확정 지뢰 관련 (해당 화면만)
- 이 화면에 **수수료율 / 지급 캘린더 / 예상 지급 차액** 중 하나가 나타나면, 그 라벨·표기·계산을 기록하고 **임의 값 채택 금지**.

## 4. 상태·정책 표기 규칙 (절대 원칙)

`CLAUDE.md`의 원칙을 이 폴더에 그대로 적용한다.

**상태 컬럼:**
- `확정` — 근거(코드 동작 + 정책 문서/조항)가 명확. **출처를 반드시 병기.**
- `가설` — 코드로 보이지만 정책 문서에 없거나, 정황상 추정. "가설"임을 명시.
- `확인 필요` — 정책이 미확정이거나 근거 없음. **임의로 확정하지 않는다.**

**절대 하지 말 것:**
1. **6개 개념을 합치지 않는다**: 미지급금 · 선정산 제외금액 · 바로이체 · 과지급 · 미회수금 · 환급 (정의: `02_TERMS_AND_STATUS`).
2. **3대 지뢰 값을 임의 채택 금지**:
   - 수수료율 (1% / 0.604% / 0.6+0.11+0.1% / 0.25% 병존 → `analysis/00_종합.md` C1)
   - 지급 캘린더 (계약 "매일" vs 운영 D+1 vs DB D+2 → C2)
   - 예상 지급 차액 (정의 미확정인데 화면 핵심 라벨 → C4)
3. **내부 운영 용어 ↔ 가맹점 노출 용어 구분** (매핑: `05_UI_REQUIREMENTS` §5).
4. 어드민의 `매출 회수`(락계좌→모계좌 스윕) ≠ 정책의 `회수`(과지급 회수).
5. 예상값 / 확정값 / 실제 지급값, 그리고 스크래핑 시각 / 지급 시각 / 기준일 / 최종 업데이트 일시를 혼동하지 않는다.

## 6. 핸드오프: 개발자 산출물 · 정책 파일을 받으면 (요약)

상세 절차는 `91_핸드오프_가이드.md`. 요약:

1. **매핑**: 받은 문서의 항목을 이 표의 **행(#)** 에 매핑한다. 매핑 안 되는 항목은 "표에 없던 기능" → 신규 행 추가(누락 발견).
2. **대조**: 각 행의 `동작·결과`(코드 사실) vs 받은 정책을 비교.
   - 일치 → 상태를 `확인 필요`/`가설` → `확정`으로 승격, 근거에 문서 출처 추가.
   - 불일치 → **충돌 플래그**(행에 `⚠️충돌` 표시 + `90_정책레지스터.md`에 등록). 임의로 한쪽 채택 금지.
3. **미확정 해소**: C 섹션·`90_정책레지스터`의 항목 중 받은 문서로 확정되는 것 갱신.
4. **역방향 검증(현행화)**: 정책에는 있는데 코드에 없는 기능 → "미구현/기획-개발 갭"으로 별도 표기.

이 구조 덕분에, 문서를 던져주면 **"이 정책은 06_회원관리.md B표 3행에 해당, 현재 코드 동작과 일치 → 확정"** 처럼
정확한 위치로 이해·반영할 수 있다.
