## A. 화면 개요

- **목적**: 가맹점 앱에 노출되는 약관을 **컨텍스트(노출 맥락) → 약관 종류 → 버전(개정본)** 3계층으로 관리하는 화면이다. 컨텍스트·약관 종류·버전을 각각 추가·수정·삭제할 수 있고, 버전별로 게시(발효) 여부를 토글로 켜고 끌 수 있다. (근거: code 01_admin app/terms/page.tsx:198-199 "약관 컨텍스트, 종류, 버전을 관리합니다")
- **진입·권한**:
  - 사이드바 "관리자" 그룹의 "약관 관리" 메뉴로 진입한다 (code 01_admin components/AdminLayout.tsx:114-116, href `/terms`).
  - 인증: API가 401을 응답하면 `/login?reason=expired`로 강제 이동한다 (code 01_admin lib/apiClient.ts:20,35,54-56). 화면 자체에는 **역할(role)·권한 분기 코드가 없어** "누가 약관을 수정할 수 있는가"는 코드만으로는 확정할 수 없다(확인 필요).
  - 개정 등록 시 작성자는 `getAdminUser().name`(localStorage `admin_user`)로 기록하며, 값이 없으면 `"admin"`으로 저장한다 (code 01_admin app/terms/page.tsx:116-117, lib/api.ts:7-11).

## C. 정책 확인 필요 항목 (Open Questions)

- [ ] **게시(발효) 정책** — `toggle-publish`는 단순 boolean 반전이며, 코드에 "종류당 게시 버전은 1개" 제약이 **없다**. 동일 종류에 여러 버전을 동시에 게시할 수 있는지, 게시=즉시 발효인지 아니면 `effectiveFrom` 도래 시점 발효인지 미확정. (관련: #16) — 근거: code app/terms/page.tsx:124-129 (단일 게시 강제 코드 부재)
- [ ] **`effectiveFrom`(시행일) vs `isPublished`(게시)의 관계** — 미래 시행일 버전을 미리 게시할 수 있는지, 시행일 도래 시 이전 버전이 자동으로 `effectiveTo` 마감(만료)되는지 미확정. `TermRevisionItem.effectiveTo` 필드는 존재하나 화면에서 설정/표시하지 않음. — 근거: services/termsService.ts:40,111 (effectiveTo 미노출)
- [ ] **삭제 제약의 백엔드 근거** — UI는 (a) 미게시 버전만 삭제 버튼 노출, (b) "사용자 동의 이력 있으면 거부" 안내를 표시하나, 실제 거부 로직은 백엔드에 있고 코드로 확인 불가. 동의 이력 보존 정책은 archive_02(약관 동의 이력)와 정합하지만 이 API의 동작은 검증 필요. (관련: #19, #37)
- [ ] **컨텍스트 ↔ 약관 체계 매핑** — `signup`(회원가입)/`contract`(전자계약)/마케팅수신 컨텍스트가 계약 문서상 약관 체계(서비스 이용약관·개인(신용)정보 동의·이용계약서·양수도계약서·재양도합의서 — archive_02 §1.1)의 어느 항목에 대응하는지 확정 필요. 특히 "전자계약(contract)" 컨텍스트가 6단계 비대면 계약의 개별계약서(이용계약·양수도)를 이 약관 관리로 함께 다루는지, 아니면 별도 계약 템플릿 관리가 있는지. (관련: 03_merchant 계약, archive_02)
- [ ] **필수(isRequired) 플래그의 가맹점 화면 반영 경로** — 어드민에서 설정한 `isRequired`가 가맹점 회원가입 약관동의(`node 868:2`/`873:2`)·6단계 계약 필수동의(`node 855:2`/`861:2`)의 필수/선택을 실제로 구동하는지 API 계약으로 확인 필요. (관련: #31, 가설)
- [ ] **약관 수정 권한** — `/terms` 접근·수정에 대한 관리자 역할(role) 분기가 화면 코드에 없음. 약관은 법적 효력 문서이므로 편집 권한 제한 정책 필요 여부 확인. (관련: A. 진입·권한, 07_OPEN_QUESTIONS)
- [ ] **버전 수정(updateRevision) 허용 범위** — 이미 게시·시행 중인 버전의 본문/버전번호를 사후 수정 가능한지(감사·법적 관점) 정책 필요. 코드는 게시 여부와 무관하게 수정 버튼을 노출한다. (관련: #18, #25)

## D. 미확정 지뢰 관련

- **수수료율 / 지급 캘린더 / 예상 지급 차액**: 이 화면에 **직접 표기·계산되는 지뢰 값 없음**. 약관 본문(`content`)은 자유 텍스트 필드로, 약관 문서 내에 수수료율(C1)·지급 주기(C2) 문구가 포함될 수는 있으나 이 화면은 그 값을 **계산하거나 라벨로 표시하지 않는다**(단순 텍스트 저장·표시). 따라서 3대 지뢰의 임의 채택 위험은 없음.
- 참고: 약관/계약 본문에 담기는 수수료율·"매일(주말·공휴일 포함)" 지급 등 조항의 값 자체는 계약 문서(archive_02 §2.3 양수도 제4·17조)와 C1·C2에서 별도 관리하며, 이 약관 관리 화면의 텍스트와 정합성 검증은 별도 과제.
