## A. 화면 개요

- **목적**: 어드민 웹의 관리자(및 파트너·영업·제휴·투자자 등 참여자)가 로그인하는 화면이다. 아이디·비밀번호로 인증 토큰을 발급받아 쿠키에 저장하고, 인증된 사용자만 어드민 화면으로 들여보낸다.
- **진입·권한**:
  - 로그인하지 않은 상태로 보호 경로(로그인 페이지를 제외한 모든 경로)에 접근하면, 서버 미들웨어 `proxy.ts`가 `/login?redirect=<원래경로>`로 리다이렉트한다 (`code 01_admin proxy.ts:19-23`). Next.js 16에서는 `proxy.ts`(export `proxy`)가 프레임워크의 미들웨어 컨벤션이라 서버측 게이트로 실제 동작한다 (`code 01_admin package.json` next 16.1.6).
  - 클라이언트측 2차 게이트도 둔다. `AdminLayout`이 마운트될 때 `admin_access_token` 쿠키가 없으면 `window.location.href`로 `/login?redirect=<pathname>`로 내보낸다 (`code 01_admin components/AdminLayout.tsx:233-238`). 즉 서버·클라이언트 **이중 게이트** 구조다.
  - 로그인에 성공한 계정 중에서도 허용된 `userType`만 통과한다 (아래 B-8).
  - 어드민에는 **자가 회원가입·비밀번호 찾기 화면이 없다** (`app/` 하위에 signup·find-password 라우트 부재). 계정은 백엔드에서 프로비저닝한다. `가설`(라우트 부재는 코드로 확인되나, '셀프서비스 미제공'이 확정 정책인지는 근거 없음 → C-5).

## C. 정책 확인 필요 항목 (Open Questions)

> 아래 항목은 참조 정책문서(`06` 등)에 대응 조항이 없어 B표에서 `확정`으로 승격되지 못한 근거다. 별도 인증·권한 정책 문서 확보 시 해당 B행을 `가설`/`확인 필요` → `확정`으로 승격.

- [ ] **인증 정책의 실체는 백엔드**: 프론트는 필드 공란 여부만 검사(B-2~4)하고, ID(휴대전화/사업자번호) 형식·비밀번호 규칙·시도 제한·잠금·2FA 여부는 `POST /auth/login`(Spring) 소관 — 이 레포에 근거 없음. 관련: 07_OPEN_QUESTIONS.
- [ ] **세션 만료 150분의 근거**: 쿠키 만료를 코드가 150분으로 하드코딩(B-9). 백엔드 발급 토큰의 실제 TTL과 일치하는지, 갱신(리프레시) 정책이 있는지 확인 필요. 불일치 시 쿠키만 남아 401→강제 로그아웃(B-25) 경로로 처리됨.
- [ ] **허용 userType 7종의 권한 범위**: `ADMIN/PAYHUG/PARTNER/SALES_ORG/SALES/AFFILIATE/INVESTOR`가 로그인은 되나(B-8), 역할별로 접근 가능한 메뉴·데이터 범위(B-23 네비 필터 외 서버측 인가)는 정책 미확정. 참여자 계정이 어드민 웹에서 볼 수 있는 정보 경계 확인 필요. 관련: 06_회원관리.
- [ ] **redirect 파라미터 안전성**: `?redirect=` 값을 검증 없이 `router.replace`(B-15). 외부 URL/오픈리다이렉트 차단 화이트리스트 필요 여부 — 보안 정책 확인 필요.
- [ ] **자가 가입·비밀번호 재설정 부재의 정책 확정**: 어드민에는 signup/find-password 라우트가 없다(코드 사실). 계정 발급·초기화가 전적으로 백엔드/운영 수동인지 정책으로 확정 필요(가맹점 웹 M-02와 달리 셀프서비스 없음).
- [ ] **DEV_BYPASS_AUTH 운영 차단 보장**: 개발 우회 플래그(B-26)가 운영 빌드에서 확실히 미설정/제거되는지 배포 파이프라인 차원 확인 필요.
