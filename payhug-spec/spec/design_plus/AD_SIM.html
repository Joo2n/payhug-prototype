정책 · 계산 로직 · 데이터 출처 코드 기반 심화 · 확정 / 가설 / 확인필요 표기
실제 정산·이체·저장 없이, 정산 상품(정책)과 가상 거래를 넣어 수수료 → 장부(원장) → 이해관계자 배분 → 가맹점 지급액이 어떻게 나오는지 서버 실계산으로 미리 확인하는 내부 검토용 시뮬레이터다. 스크래핑·동기화·배치 마감 같은 실제 정산 파이프라인을 우회하고, 매출을 사람이 직접 입력해 '계산 로직'만 떼어 검증한다. 계산은 서버가 수행하고 화면은 결과를 표시만 하며, 어떤 데이터도 남기지 않는다.
계산선정산이 어떻게 계산되나
수수료 3종과 부과 주기
선정산 수수료는 세 갈래다.채권매입 수수료 : 매출을 미리 사주는 대가. 거래 건마다 부과.시스템 이용료 : 플랫폼 이용료 성격. 거래 건마다 부과.이체 수수료 : 실제 계좌 이체 비용 성격. 하루 정산 묶음(배치)당 1회만 부과.앞의 둘은 건별 원장으로 쌓이고, 이체 수수료만 배치 단위로 따로 한 줄 잡힌다(화면에도 '배치당 1회'로 명시).확정
채권매입 요율은 참여자별로 나눠 등록
채권매입 수수료 요율은 참여자마다 각각 등록된다(투자자·페이허그·상위/하위파트너·영업조직 각자의 몫이 별도 행). 화면이 이 요율을 큰 값부터 정렬해 보여준다.[가설] 이 구조는 '가맹점이 낸 채권매입 총액을 몫대로 나눈다'는 성격으로 읽히지만, '총액 = 배분액 합'이라는 등식 자체는 이 화면 코드로는 확인되지 않는다(계산은 서버).확정
시스템 이용료 (일반 유형 한정)
매출 건별 요율로 부과되며 페이허그·상위/하위파트너가 나눠 받을 수 있다. 단 이는 '일반' 유형에서만 존재하고, '다우' 유형엔 시스템 이용료 자체가 없다(요율표·납부/수취 옵션 모두 없음). 파트너 수취 여부는 항목별 토글로 결정되고, 토글을 모두 끄면 페이허그만 수취한다.확정
이체 수수료 성격
정률(%)이 아니라 정액(원)으로 설정된다. 하루 이체 1건에 대응하는 실비 성격이라 배치당 1회만 잡힌다. 기본 수취자는 페이허그이고, 파트너/영업이 나눠 받도록 토글할 수 있다.확정
장부(원장) 구성
건별 원장은 참여자 줄마다 매출 · 매출VAT · 원가 · 원가VAT · 수익 · VAT · 순수익 · 배분액 8개 값을 함께 보여준다. 상위로 넘겨줄 몫은 원가/통과분으로, 자기 몫은 순수익·배분액으로 남는 형태다. 건별 원장은 채권매입·시스템 이용료 두 종류만 뜨고, 이체 수수료는 건별 원장 없이 배치 줄로만 나온다.확정
시스템 이용료는 건별+합산 두 뷰
시스템 이용료는 거래 한 건 한 건 원장으로도 보여주고, 그 밑에 참여자별로 합산한 뷰(건별 합산 N건)로도 다시 보여준다. 같은 값을 두 관점으로 확인시키는 표시 구조다.확정
기록용(통과) vs 직접배분
원장·배분표의 일부 줄은 '기록용'으로 표시된다(회색 이탤릭). 실제 돈이 움직이는 배분이 아니라 장부에만 남기는 통과 기록이며, '가맹점 부담 수수료' 집계에서 제외된다. 반대로 '직접배분' 줄이 실제 지급되는 몫이다.확정
법인·사업자(VAT) 구분
참여자마다 법인/개인, 사업자(VAT) 여부 표시가 붙는다. 요율마다 VAT를 별도(위에 얹음)로 볼지 포함으로 볼지 설정한다. 단 페이허그 몫엔 VAT 별도/포함 선택칸이 없다(화면에 '—'로 표시).확정
가맹점 지급액 요약
요약 카드에 총 거래금액 · 거래 건수 · 총 수수료(가맹점 부담) · 가맹점 지급액이 나오고, 총 수수료 밑에 채권매입·시스템·이체로 쪼갠 부과 내역이 붙는다. 부과 내역 분해는 화면이 직접 계산해 보여주지만, 지급액 자체는 서버가 준 값이라 '총거래−부담수수료=지급액' 등식은 화면에서 재계산하지 않는다(가설적 읽기).확정
스킵되는 거래
일부 거래는 계산에서 제외('스킵')되고 그 사유가 건별로 표시된다(수수료 합계·지급액에서 빠짐). 다만 어떤 조건에서 스킵되는지는 서버가 판단하며 이 화면 코드에선 확인되지 않는다.확정
부호(양수/음수)·회수 분기 없음
선정산 원칙상 같은 항목도 금액 부호·지급완료 여부로 처리가 갈리고(지급 전 음수=당일 차감, 지급 후 음수=회수 검토), 시스템 데이터 모델에도 취소회수·예상차액 등 조정 유형이 별도로 존재한다. 그러나 이 시뮬레이터엔 그 분기가 없다 — 양(+)의 매출을 넣어 정상 배분만 확인하는 용도다.확인필요
설정설정 — 정산 상품(정책)이 담는 것
정책 = 계산 규칙 묶음
시뮬레이터가 고르는 '정책'은 곧 정산 상품 관리에서 만든 상품이다. 하나의 정책에 참여자·요율·수수료 납부/수취 규칙이 통째로 묶여 있고, 시뮬레이터는 그 묶음을 그대로 계산에 적용한다.확정
규칙 유형 2종 (일반 / 다우)
정책은 '일반' 또는 '다우'로 만든다. 참여자 구성·기본 요율표가 다르다.일반 : 투자자·페이허그·상위파트너·하위파트너·영업조직 / 요율 = 채권매입 + 시스템이용료 + 이체다우 : 투자자·페이허그·상위영업·하위영업 / 요율 = 채권매입 + 이체 (시스템 이용료 없음)생성 후 유형은 변경 불가(수정 화면에서 잠김).확정
요율 입력 단위
채권매입·시스템 이용료는 %로, 이체 수수료는 원(정액)으로 입력한다(화면 안내문: '1% → 1 입력'). 내부적으로는 더 잘게 저장되지만, 기획 관점의 핵심은 '%와 원 두 단위가 섞여 있다'.확정
미배정 참여자 요율 숨김
편집 화면에서 투자자를 배정하지 않으면 투자자 요율칸이, 영업조직을 배정하지 않으면 영업 요율칸이 숨겨진다(그 몫이 없으므로). 배정 상태가 요율표 노출을 좌우한다.확정
수수료 납부자 설정
시스템 이용료·이체 수수료는 각각 누가 낼지 지정한다.미설정 = 가맹점 부담(기본)상위/하위파트너(다우는 상위/하위영업) 지정 시 그쪽이 대신 납부상위/하위 중 택1(둘 다 켤 수 없고 나중 선택이 앞 선택을 덮음). 채권매입엔 납부자 선택이 없다 → 항상 가맹점 부담.확정
수수료 수취자 설정
파트너/영업이 시스템료·이체료를 나눠 받을지를 항목별 토글로 켠다. 모두 끄면 페이허그만 수취. 납부자(누가 내나)와 수취자(누가 받나)는 별개 축이다.확정
참여자 = 실제 등록 계정
정책의 각 자리(투자자·파트너·영업·제휴사·페이허그)는 임의 텍스트가 아니라 실제 등록된 유저 계정에서 골라 배정한다. 배정 계정의 법인/사업자 속성이 그대로 VAT 계산에 반영된다.확정
상품 수명주기
정책은 생성·수정·비활성화·삭제할 수 있다.비활성화 : 신규 배정만 막고 기존 배정 이력은 유지삭제 : 되돌릴 수 없고, 배정된 가맹점이 있으면 삭제 불가확정
연결어디에 연결돼 있나
정책 목록 = 실제 정산 상품
시뮬레이터 드롭다운의 정책은 정산 상품 관리와 같은 목록을 서버에서 그대로 불러온 것이다. 별도 목업이 아니라 운영 중인 실제 상품을 고른다.확정
카드/배달 정책 분리 적용
카드 거래와 배달 거래에 서로 다른 정책을 걸 수 있다. 둘 중 최소 1개는 선택해야 실행 버튼이 활성화된다(둘 다 미선택이면 비활성).확정
락계좌·플랫폼과는 연결 안 됨
실제 정산에서 매출은 플랫폼 락계좌(여신협회=카드·배달의민족·요기요·쿠팡이츠)를 통해 들어오지만, 이 시뮬레이터는 락계좌·플랫폼과 실제로 연결되지 않는다 — 매출을 사람이 입력하고, 거래 유형도 카드/배달 둘뿐이다. 위 플랫폼 연결은 다른 화면(실제 정산)의 맥락이다.확정
매출 회수(스윕)와는 무관
어드민의 '매출 회수'(락계좌→모계좌 자금 이동)와 정책상 '회수'(과지급 회수)는 서로 다른 개념인데, 이 화면은 둘 중 어느 것도 다루지 않는다. 순수 계산 미리보기다.확정
데이터데이터 출처·흐름
저장하지 않는다
계산은 서버가 실제로 수행하지만 결과를 남기지 않는다(화면 안내문에 '저장 없이 미리 확인'). 실행할 때마다 새로 계산해 화면에만 뿌린다. 실제 정산 데이터에 영향이 없는 안전한 검토 도구.확정
매출 입력이 수동 — 스크래핑 우회
실제 정산은 플랫폼에서 매출을 스크래핑해 가져오지만, 이 화면은 그 단계를 건너뛰고 사람이 유형(카드/배달)과 금액을 직접 입력한다. '스크래핑 이후의 계산 로직'만 떼어 검증하는 구조.확정
실제 파이프라인 단계는 여기 없음
운영 정산은 동기화 → 정산 처리 → 배치 마감 순으로 흐르지만, 시뮬레이터엔 이 단계가 없다. 배치·마감·이체 실행 없이 '한 번의 계산 결과'만 보여준다.가설
예상값/확정값 구분은 다른 화면에
정산 데이터 모델엔 수수료가 예상인지 확정인지 구분(예상 건수·확정 건수 집계)이 존재한다. 다만 주말·스크래핑 장애 시 '평균매출×할인율'로 예상값 대체하는 로직은 이 화면 코드엔 없다 → 서버·다른 화면 확인 필요.확인필요
스크래핑 검증 상태 (실제 정산 기준)
실제 정산 쪽엔 플랫폼 연결 상태가 정상·이상·장애·스킵·검증제외로 관리되고, 장애 시 '이전 검증 시각 기준'으로 처리하며 '락계좌로 결제계좌 변경 후 재검증'을 안내한다. 시뮬레이터 자체 기능이 아니라 파이프라인 맥락.확정
정책정책·주의 (미확정 지점)
수수료율 실제 숫자 미확정
화면은 선택한 정책의 요율로 서버가 계산한 값을 표시만 한다. 정책에 어떤 수치를 넣어야 맞는지(1% / 0.604% / 0.6+0.11+0.1% 등 병존)는 여전히 미확정. 코드에 특정 요율이 못박혀 있지 않으므로 근거 확정 전 임의 채택 금지.확인필요
지급 캘린더(D+N) 안 드러남
이 화면은 '언제 지급되는가'(매일/D+1/D+2)를 계산·표시하지 않는다. 이체 수수료가 배치당 1회라는 주기만 확인될 뿐, 지급 시점 규칙은 별도 확인 필요.확인필요
'예상 지급 차액' 정의
가맹점 화면 핵심 라벨 '예상 지급 차액'의 정의는 이 화면에서 확인되지 않는다. 시뮬레이터는 확정 계산 미리보기라 차액 개념을 다루지 않는다(차액 수수료 개념은 다른 화면 데이터 모델에만 존재).확인필요
입력 검증 부재
거래 금액에 최소·최대·음수·필수 검증이 없다. 0원·음수·빈 값이 그대로 서버로 넘어갈 수 있어, 결과 해석 시 입력값 신뢰 범위를 개발과 별도 확인 권장.확인필요
계산 전량 서버 수행
수수료·원장·배분·지급액 모든 계산은 서버가 하고 화면은 표시만 한다(부과 내역 분해와 시스템료 합산 뷰 정도만 화면이 재집계). 따라서 부과 순서·부호 처리·반올림 같은 세부 규칙은 이 화면이 아니라 서버 계산 로직에서 검증해야 한다.확정
