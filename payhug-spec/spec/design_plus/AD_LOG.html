정책 · 계산 로직 · 데이터 출처 코드 기반 심화 · 확정 / 가설 / 확인필요 표기
활동 로그는 서버 DB에 자동 기록된 업무 이벤트를 훑는 조회 전용 화면이다. 코드 대조로 확인된 심화 지점: (1) 목록과 요약을 서로 다른 2개 경로로 따로 불러오고, 요약 카드는 화면 코드에 박힌 6개 카테고리·최근 24시간으로 고정돼 서류 카테고리와 사용자가 건 기간 필터를 무시한다(요약 경로는 기간을 바꿀 수 있는데도 24시간으로 고정 호출). (2) 이벤트 유형 필터 선택지는 전체 제외 29종인데, 표에 한글 라벨을 붙이는 사전은 31종이라 '회수 전용 모드 활성화/해제' 2종은 표에는 뜨지만 필터로 골라낼 수 없다. (3) 이벤트 어휘에 매출대금 회수(락계좌→모계좌 스윕 계열)와 부채 회수가 함께 섞여 있고, 이들이 실제로 주황 '회수' 배지 하나로 묶이는지는 카테고리를 서버가 정하므로 확인 필요이며, '부채(DEBT)'가 6대 개념 중 과지급·미회수금 어디에 해당하는지도 미확정이다. (4) 같은 어드민에 별도 화면인 'AI 모니터링 어시스턴트'가 있어, 이건 DB 업무 이벤트가 아니라 다른 백엔드 서버의 원본 서버 로그를 자연어로 조회한다.
설정화면에 박혀 있는 고정값 (서버가 아니라 화면 코드가 정함)
요약 카드 카테고리 6개 고정
요약 카드에 뿌리는 카테고리는 가맹점·계약·계좌·관리자·정산·회수 6개로 화면 코드에 박혀 있음표·배지에는 '서류' 카테고리가 별도로 존재(증빙 서류 업로드 등)하는데 요약 카드에서만 서류가 빠져 있음서버 요약이 서류 건수를 내려줘도 카드에는 안 뜸나중에 카테고리가 늘면 화면 코드를 고쳐야 반영됨확정
요약 = 최근 24시간 고정
요약 카드는 최근 24시간으로 고정 집계 — 아래 기간 필터를 걸어도 카드는 안 바뀜요약 조회 경로는 조회 기간(시간 수)을 넘길 수 있게 돼 있는데도 화면이 24로 못박아 부름결과적으로 목록과 요약은 서로 다른 시간 기준(목록=필터값 / 요약=24시간)확정
목록 20건씩 고정
한 페이지 20건으로 고정, 사용자가 페이지당 건수를 바꿀 수단 없음확정
필터 드롭다운 29종 vs 표시 라벨 31종
이벤트 유형 필터 선택지는 전체 제외 29종인데, 표에 한글 라벨을 붙이는 사전은 31종차이 나는 '회수 전용 모드 활성화'·'회수 전용 모드 해제' 2종은 표에는 라벨로 뜨지만 필터로는 골라낼 수 없음사전에 없는 코드값이 오면 원문 코드가 그대로 노출됨확정
필터 축은 이벤트 유형·기간뿐
거를 수 있는 조건은 이벤트 유형·시작일·종료일 3가지뿐가맹점·행위자로는 못 거름 — 특정 가맹점의 로그만 보려는 조회 불가확정
연결데이터를 어디서 몇 번 불러오나
목록·요약을 따로 2번 호출
진입 시 목록과 요약을 각각 별도 경로로 불러옴 (한 번에 안 옴)목록: 유형·시작일·종료일·페이지를 조건으로 조회요약: 최근 24시간 카테고리별 집계만 따로 조회 → 그래서 필터와 무관하게 움직임확정
같은 어드민의 '별도' 로그 화면
이 화면(활동 로그)과 별개로 'AI 모니터링 어시스턴트'라는 다른 화면이 존재활동 로그 = 서비스 서버에 쌓인 업무 이벤트(승인·이체·회수 등)AI 어시스턴트 = 원본 서버 로그를 자연어 질문으로 조회(이체 실패·스크래핑 오류 등 기술 로그)두 화면의 데이터 출처·성격이 완전히 다름 → 문서·IA에서 구분 필요확정
AI 어시스턴트는 다른 서버·같은 로그인 토큰
AI 어시스턴트는 본체와 다른 백엔드 서버로 붙고, 응답을 실시간 흘려보내는(스트리밍) 방식으로 받음자연어 질문 → 서버가 조회식을 자동 생성 → 원본 로그 N건을 근거로 요약을 흘려보냄별도 인증 체계가 아니라 어드민 로그인 토큰을 그대로 실어 보냄확정
계산숫자·시간이 만들어지는 방식
요약 카드 숫자는 서버가 셈
카테고리별 건수는 서버가 미리 집계해서 내려주고, 화면은 그대로 표시만 함 (화면에서 재계산 없음)서버 요약엔 전체 합계·집계 기간 값도 함께 오지만 카드는 카테고리 6개 숫자만 쓰고 나머지는 버림확정
'전체 N건'의 실제 의미
헤더 우측 '전체 N건'은 현재 필터가 반영된 목록 총 건수 (서버 응답값)유형·기간을 걸면 같이 줄어듦 → 전체 로그 개수가 아님요약 카드(24시간)와는 기준이 달라 두 숫자를 더하거나 맞춰볼 수 없음확정
시간 표기 시간대
시간은 보는 사람 브라우저의 로컬 시간대로 변환해 '오전/오후 HH:MM'으로 표기서버가 어떤 시간대(UTC 등)로 저장하는지, 스크래핑·지급 시각과 기준이 맞는지는 서버 영역 → 확인 필요확인필요
데이터로그는 언제 자동으로 찍히나
각 이벤트가 자동 기록되는 조건
표의 한 줄은 서버가 특정 사건이 일어날 때 자동으로 남기는 기록가맹점 승인/반려, 계약 초기화, 정산 활성/비활성, 이체 성공/실패, 매출대금 회수, 부채 차감 등어떤 처리 시점에 정확히 찍히는지(트리거 조건)는 서버 로직 → 화면만으로 확정 불가확인필요
행위자 유형의 의미
행위자 유형 배지는 관리자 / 사용자(가맹점) / 시스템 3종 (유형 값이 비면 배지 없이 이름만 표시 — 이 표시 규칙은 확정)'시스템'이 사람이 아니라 배치·자동 처리가 남긴 기록(정산 배치 완료, 자동 이체 등)이라는 해석은 추정가설
'TG'(알림 발송 여부) 채우는 주체
맨 끝 'TG' 점(초록=발송 완료/회색=미발송)은 서버가 채워주는 발송 결과값이 알림이 가맹점 알림톡인지 운영팀 내부 알림인지 대상이 불명확 → 6대 개념 문서의 '알림톡'과 같은 것인지 확인 필요확인필요
정책'회수' 어휘에 숨은 개념 혼재 (핵심 정책 이슈)
이벤트 어휘에 성격 다른 '회수'가 공존
이벤트 유형 어휘 안에 성격이 전혀 다른 두 '회수'가 함께 들어 있음매출대금 회수 계열: 매출대금 회수 완료 / 매출대금 회수 실패 = 어드민의 락계좌→모계좌 스윕(자금 이동)부채 회수 계열: 부채 차감 / 부채 상환 완료 / 부채 회수 완료 / 부채 회수 모드 이체 생략이 둘은 완전히 다른 개념인데 한 화면·한 어휘군에 뒤섞여 있음 → 분리 정의 필요확정
둘을 같은 '회수' 배지로 묶는지
주황 '회수' 배지 하나로 위 이벤트들이 실제로 묶이는지는 이벤트→카테고리 분류를 서버가 정하므로 화면만으로는 단정 불가화면은 카테고리 이름에 색만 입힐 뿐, 어떤 이벤트가 '회수' 카테고리로 오는지는 서버 응답값 → 서버 분류 규칙 확인 필요확인필요
'부채'와 6대 개념의 매핑
로그가 쓰는 '부채'가 6대 개념 중 과지급·미회수금 어디에 해당하는지 미확정부채 등록/수정/취소/회수완료가 과지급 회수 흐름인지, 계약상 미정산금인지 근거 없음 → 임의 매핑 금지확인필요
'부채 회수 모드 이체 생략'의 정책 함의
