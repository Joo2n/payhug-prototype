정책 · 계산 로직 · 데이터 출처 코드 기반 심화 · 확정 / 가설 / 확인필요 표기
가맹점 하루치 매출을 "정산 단위(배치)"로 묶어, 수수료를 떼고 이해관계자들에게 나눠준 결과를 원장 단위로 열어보는 내부 전용 조회 화면이다. '정산 현황' 페이지의 여러 탭(선정산 결과·정산 상세·차액 정산·이체 내역·계산서 발행·VOC) 중 정산의 계산·배분·이체를 파고드는 탭들로, 화면 자체는 결과를 "읽어서 보여줄 뿐" 정산을 실행하지는 않는다. 뒤에는 매출 수집→정산 계산→마감의 3단계 처리, 주말·수집장애 때 평균매출로 지급액을 추정하는 대체 로직, 한 건의 매출이 여러 참여자에게 어떻게 쪼개지는지 기록하는 배분 원장이 있다.
데이터데이터 출처·흐름 (매출을 어디서 언제 가져와 확정하나)
화면 성격 (읽기 전용)
이 화면은 이미 계산·마감된 정산 결과를 조회하는 창구다. 배치를 만들거나 지급을 실행하는 버튼은 (미정산 누락 처리를 제외하면) 이 화면에 없고, 계산·마감은 뒤에서 돌아간 결과를 그대로 읽어 보여준다.예외: '선정산 결과' 탭의 미정산 누락만 이 화면에서 직접 지급 처리(바로이체/기록만)할 수 있다.확정
3단계 처리 (수집→계산→마감)
한 가맹점의 하루치 정산은 ①매출 수집 → ②정산 계산 → ③마감의 3단계로 만들어진다. 각 단계의 산출물이 뒤 화면 숫자의 뿌리다.①수집 : 매출 데이터를 끌어와 저장(가져온 건수)②계산 : 수수료를 매기고 배분 계산(처리 건수 / 제외 건수)③마감 : 그날치를 하나의 정산 단위로 잠그고 대상 금액·지급 건수 확정특정 가맹점·특정 날짜를 지정해 이 3단계를 다시 돌리는 수동 실행 기능이 있으며(대상없음/실패로 끝날 수 있음), 이는 이 화면이 아니라 별도 운영 기능이다.확정
매출 수집 출처
매출은 크게 카드와 배달 3사(배달의민족·요기요·쿠팡이츠)에서 들어온다. 화면 곳곳에서 매출원을 카드/배민/요기요/쿠팡이츠로 구분해 표시한다.카드는 승인번호·카드사가, 배달은 주문번호·매장명이 함께 붙는다.확인 필요 : 카드 매출을 어느 기관에서 어떤 주기로 긁어오는지는 이 화면 코드만으로는 드러나지 않음.확정
시각·기준일 구분
한 줄 안에 성격이 다른 날짜·시각이 섞여 있으므로 반드시 구분해 읽어야 한다.매출일(기준일) : 그 매출이 발생한 날. 정산 단위를 묶는 축정산 마감 시각 : 그날치를 잠근 시점(정산일). 없으면 아직 '미정산'이체 요청 시각 : 실제 송금을 요청한 시각(이체 내역)차액 반영 시각 / 광고비 정산일 / 입금예정일 등도 각각 다른 의미. 스크래핑 시각·지급 시각·기준일을 혼동하면 안 됨.확정
예상값 대체 (주말·수집장애)
매출을 실제로 못 긁어오는 날엔 추정치로 지급을 잡는 대체 로직이 있다. 추정 사유는 딱 두 가지 — 주말이거나 매출 수집 장애.추정 지급액은 그 가맹점의 평균 매출에 일정 할인율을 적용해 계산(평균 매출·평균 수수료·평균 순지급액·할인율·요일을 근거로 보관)하고, 평균 낼 실데이터가 부족하면 '추정 불가' + 마지막 실데이터 일자를 남긴다.단, 이 화면(조회 탭)은 이 상세 추정 근거를 표로 펼치지 않는다. 화면에는 추정으로 잡힌 건에 '예상' 뱃지와 '예상매출 N건 포함' 카운트로만 나타나고, 위 평균·할인율 계산은 같은 정산 계층의 인접 기능이 담당한다.확정
할인율·평균 산정 수치
추정에 쓰는 할인율(%)과 '평균을 며칠치로 잡는지'의 구체 수치는 코드에 박혀 있지 않고 서버에서 내려받아 쓴다.미확정 3대 지뢰 중 수수료율·예상 지급 차액과 얽히므로 임의 확정 금지. 실제 값은 정책·서버 설정에서 확인.확인필요
예상 / 확정 / 실지급 구분
건별로 수수료가 실제인지 예상인지를 라벨로 나눈다(현장결제 건은 '차감'). 추정으로 잡힌 거래·정산 단위엔 '예상' 뱃지가 붙는다.나중에 실제 매출·수수료가 확정되면 그 차이를 차액 정산으로 되돌린다.즉 화면 금액은 '예상으로 먼저 준 값'과 '실제 확정값'이 섞일 수 있으므로 뱃지를 함께 읽어야 한다.확정
매입상태 (채권 매입 결과)
건별 상세에 매입상태가 표시된다 — 매입완료 / 매입취소 / 승인취소 등. 카드 매출채권을 실제로 사들였는지(또는 취소됐는지)를 나타내며, 취소 건은 뒤의 '취소 환수' 차액으로 이어질 수 있다.확정
뒤늦게 도착한 매출 (미정산 누락)
그날 마감이 끝난 뒤 도착한 매출은 정산에서 빠진 채로 남고, 시스템이 이를 따로 추적한다.'해당일 정산완료 - 누락' 표시 = 이미 마감된 날에 새로 들어온 건.'입금예정일 경과'는 참고용 추정일 뿐, 실제 입금 여부는 별도 확인이 필요하다고 화면이 명시.확정
계산선정산 계산 로직 (수수료 3종 → 원장 → 배분 → 지급액)
수수료 3종 + 차액
선정산 수수료는 항상 세 갈래 + 차액으로 쪼개져 기록된다. 화면·엑셀·계산서가 한 곳에서 정의한 이름을 공유한다.채권매입 수수료 : 아직 안 들어온 매출채권을 미리 사들이는 값시스템 이용료 : 플랫폼 사용료이체 수수료 : 실제 송금 비용차액 수수료 : 나중에 실제값 확정으로 생기는 보정분확정
선정산 수수료 = 3종 합산
요약·목록에 뜨는 '선정산 수수료' 한 줄은 실제로 채권매입 + 시스템이용료 + 이체수수료 (+ 차액수수료)의 합이며, 툴팁·괄호로 분해를 함께 보여준다.확인 필요 : 각 수수료의 %율(1% / 0.604% / 0.6+0.11+0.1% 등 병존)은 코드에 없고 서버 정책값(3대 지뢰 C1).확정
최종 가맹점 지급액 공식
가맹점이 받는 '선정산 지급액'은 순지급액(매출−카드/배달 수수료) − 선정산 수수료 + 차액 − 오프라인 차감으로 만들어진다.정산 단위(배치) 헤더에서는 다시 정산금액 − 현장결제 차감 − 광고비 차감 = 실 지급으로 한 번 더 정리해 보여준다.일부 건엔 'UPL기준 지급액'이 함께 뜨며, 이 값이 선정산 지급액과 다르면 그 차이를 대조용으로 노출한다. (UPL이 정확히 어떤 기준인지의 정의는 코드가 확정해주지 않음 → 세부는 확인 필요)확정
배분 원장 구조
한 건의 매출·수수료는 참여자별로 한 줄씩 원장에 남고, 각 줄은 매출 · 원가 · 수익 · 부가세(VAT) · 순수익 · 배분액 컬럼으로 구성된다.'매출−원가=수익', 세금 반영이 '순수익', 그 참여자에게 실제 떨어지는 몫이 '배분액'이라는 해석. 한 정산 단위 안 모든 배분액의 합 = 그 배치 지급 총액(소계로 확인).확정
기록용 배분 vs 패스스루 (다른 개념)
둘을 혼동하면 안 된다.기록용 : 배분 '상태'가 실제 이체 대상이 아니라 장부에만 남기는 줄. 목록에서 항상 맨 아래로 내려 정렬한다.패스스루(통과 금액) : 특정 참여자가 받은 게 아니라 계산상 통과시킨 금액을 나타내는 원장의 수치 항목으로, 데이터엔 있으나 이 화면 원장 표에는 컬럼으로 노출되지 않는다.확정
납부자(마이너스) 원장
시스템이용료·이체수수료는 '누군가 받는' 동시에 '가맹점이 대신 낸다'로 양쪽에 기록된다.배분액이 음수이면서 시스템이용료/이체수수료인 줄은 '납부' 줄로 표시되고, 같은 수수료를 양수로 받는 상대를 '납부 → OOO'로 이어 보여준다.즉 수수료 한 건이 '내는 쪽(−)'과 '받는 쪽(+)'으로 짝지어 남는 구조.확정
이해관계자(참여자)
배분을 받는 참여자는 역할로 구분된다 : 투자자 · 페이허그 · 상위파트너 · 하위파트너 · 상위영업 · 하위영업 · 가맹점.참여자마다 법인/사업자 여부 뱃지가 붙고, 계산서는 가맹점 단위로 발행하되 참여자+역할 단위로 기간을 합산한다.확정
원장 묶음 3종
정산 단위의 원장 상세는 세 방식으로 접었다 펼쳐진다.시스템 이용료 건별 합산 : 여러 거래의 시스템 이용료를 참여자 단위로 한 번에 합산한 요약거래별 원장 : 카드/배달 각 건마다 참여자 배분을 나열('예상' 뱃지 포함)배치 단위 원장 : 수수료 유형별로 배치 전체를 묶은 것확정
배분·지급 상태값
배분 한 줄의 상태는 이체완료 · 이체대기 · 이체실패 · 부채상계 · 기록용으로 갈린다.부채상계는 실제 이체 대신 밀린 금액과 상계 처리된 배분이라는 뜻으로, 단순 '기록용'과 구분된다.확정
연결설정·연결 (계좌·정산방식·정책이 어디에 묶여 있나)
계좌 흐름 + 이체 대행
실제 송금은 외부 이체대행을 통해 나가며, 이체 내역에 수취 은행·계좌·거래번호가 남는다.지급 이체는 가맹점 계좌로 직접 나간다.매출 회수(스윕)만 락(잠금)계좌 → 미지급계정(출금) → 모계좌(입금)의 2단계 계좌 이동을 탄다. 즉 '락→미지급→모' 3단은 회수 경로 전용이지 모든 지급의 흐름이 아니다.확정
정산 방식 3종
정산 단위는 처리 방식으로 나뉘고 목록 행에 뱃지로 구분된다.일반 선정산 : 기본. 매일 마감으로 만들어지는 정상 정산바로이체(파랑) : 누락·특수 건을 골라 즉시 실제 이체이미지급(회색) : 이미 수동 이체가 끝난 건을 이체 없이 장부에만 지급완료로 기록확정
이체 상태값
이체 한 건의 상태는 성공 · 확인완료 · 실패 · 요청중 · 타임아웃으로 표시된다(성공·확인완료를 성공으로 간주).이체 구분은 지급 · 회수(=스윕) · 수동 지급. 실패 건엔 실패 사유가 함께 노출된다.확정
수수료 정책 설정
수수료율·정산 규칙은 정책으로 등록·수정·비활성화되며, 정산 계산이 이를 참조한다.정책 편집 화면은 이 정산 상세 화면과 별개이고, 이 화면은 계산된 결과만 보여준다.확인 필요 : 정산상품 배정·수수료 면제·회수 전용 모드 등 세부 설정 항목은 이 화면 범위 밖.가설
에이전시 연결
가맹점마다 에이전시 코드가 붙을 수 있고(없으면 '미지정'), 목록·배분·이체·차액 어디서나 이 코드로 필터링된다. 엑셀에도 에이전시 컬럼이 항상 들어간다.확정
진입 경로·권한
정산 상세·계산서 발행·VOC 대응 탭과 미정산 누락 처리는 내부 어드민(ADMIN·PAYHUG)에게만 노출된다(선정산 결과·차액 정산·이체 내역 탭은 그 외 계정도 볼 수 있음).옛 정산 목록 경로로 들어와도 지금의 정산 현황 화면으로 자동 이동시킨다.확정
형제 탭 (계산서·VOC)
같은 정산 현황 페이지에는 정산 결과를 재료로 쓰는 계산서 발행·VOC 대응(자료 추출) 탭이 함께 있다. 정산 상세의 배분·합계가 이 탭들의 입력이 된다.확정
정책정책·주의 (차감·회수·개념 구분)
현장결제·광고비 차감
지급액에서 미리 빠지는 두 가지 차감이 있다.현장결제(오프라인) 차감 : 온라인으로 선정산했는데 실제로는 매장에서 결제된 건 → 그만큼 당일 지급에서 뺀다광고비(우리가게클릭비) 차감 : 배달 플랫폼 광고비를 지급액에서 회수. 광고 기간·부가세와 함께 기록되고 회수완료/부분회수/미회수로 상태를 관리하며 누적 미회수를 이어서 추적한다.확정
미회수 차액 이월
실제 확정 후 되돌려 받아야 할 금액(환수)이 그날 지급액보다 크면, 그날 지급은 0원으로 처리하고 못 회수한 나머지를 다음 정산으로 넘긴다.화면엔 '미회수 차액 이월 −금액 / 다음 정산에서 차감' 안내가 뜬다.'미회수금' 성격의 이월이며, 아래 '매출 회수(스윕)'와는 전혀 다른 개념.확정
차액 정산의 5갈래
예상값과 실제 확정값의 차이는 차액 정산으로 정리되며 유형이 나뉜다 : 카드 수수료 차액 · 배달 수수료 차액 · 취소 환수 · 예상매출 대사 · 미회수 이월.각 건은 '이전 수수료'와 '확정 수수료'를 대조해 환급(+) 또는 차감/환수(−)로 잡히고 '반영완료 / 대기중(다음 반영 예정)' 상태를 가진다.확인 필요 : '예상 지급 차액'의 정확한 정의(3대 지뢰 C4)는 코드가 확정해주지 않음.확정
차액 필터의 원장 미연결 건
차액 정산을 특정 매출 유형(카드·배달앱)으로 거르면 원장과 연결된 건만 보인다.예상매출 대사처럼 원장에 직접 연결되지 않는 차액은 유형 필터로는 안 잡히고 '전체'에서만 확인된다. 필터 결과가 비어 보인다고 없는 게 아님.확정
"매출 회수" ≠ 과지급 회수
이체 내역의 매출 회수는 락계좌 → 미지급계정(출금) → 모계좌(입금)로 자금을 쓸어 담는 2단계 자금 이동(스윕)이다. 출금·입금 2건이 잡히지만 실제 자금 이동은 1회다.이는 정책의 '과지급 회수'(더 준 돈을 되받는 것)와 완전히 다른 개념이므로 절대 합치면 안 됨.확정
미정산 누락 처리 2방식
마감 후 도착한 누락 건은 지급 권한 어드민이 골라 처리한다.바로이체 : 가맹점 계좌로 순지급액 전액을 실제 이체이미지급(기록만) : 이미 수동 이체된 것으로 보고 이체 없이 장부에만 지급완료 기록이틀 이상 지난 건은 선정산이 아니라 카드/배달 수수료만 뗀 순지급액 전액을 그대로 이체한다(선정산 수수료 미부과). 여러 날치는 합산해 1회 이체하되 원장은 거래일별로 남기며, 처리 전 '미리보기'로 이체 예정액·횟수를 먼저 확인할 수 있다.확정
지급 캘린더(D+N)
이 화면 코드에는 'D+며칠에 지급한다'는 지급 주기가 박혀 있지 않다. '이틀 이상'은 누락 건을 전액 이체로 돌리는 기준일일 뿐 정규 지급 캘린더가 아니다.계약'매일' vs 운영 D+1 vs 설계 D+2 병존(3대 지뢰 C2) — 근거 없이 어느 값도 채택 금지.확인필요
