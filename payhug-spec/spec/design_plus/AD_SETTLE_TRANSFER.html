정책 · 계산 로직 · 데이터 출처 코드 기반 심화 · 확정 / 가설 / 확인필요 표기
'이체 내역' 탭은 선정산 지급·매출 회수가 쿠콘을 통해 실제 계좌로 이체된 결과(성공·실패)를 날짜별로 보여주는 조회 화면이다. 상단 KPI와 날짜별 금액 분해는 서버가 내려준 기간 합계를 쓰지 않고, 회수 2단계(출금+입금)를 1건으로 다시 묶은 뒤 화면에서 재집계한 값이다.
계산KPI·금액 집계 로직 (화면 재계산)
KPI 4장은 화면이 다시 계산
서버가 기간 합계(전체 건수·성공 건수·전체 금액·성공 금액 등)를 함께 내려주지만, 상단 KPI 카드는 그 값을 그대로 쓰지 않는다. 날짜별 내역을 화면에서 다시 합산해 만든다.서버 합계 중 실제로 쓰는 건 '전체 건수가 0인가'(데이터 없음 안내를 띄울지) 판단 하나뿐재계산하는 이유: 회수 2단계(출금+입금)를 1건으로 묶은 뒤 세야 실제 이체 건수와 맞기 때문확정
'성공' 판정 + 건수·금액 기준이 서로 다름
상태가 성공 또는 확인완료면 성공으로 집계(둘은 동급).실패 KPI의 건수는 '실패' 상태만 셈. '요청중'·'타임아웃'은 성공 건수에도 실패 건수에도 안 잡힘 → 성공 건 + 실패 건의 합이 전체 건수와 안 맞을 수 있음실패 KPI의 금액은 전체금액에서 성공금액을 뺀 값 → '요청중'·'타임아웃' 금액도 실패 금액에 포함됨주의: 건수 기준과 금액 기준이 다르다.확정
지급 이체 / 매출 회수 버킷 분리
각 건을 '회수'와 '그 외(지급)'로 나눠 따로 집계한다. 회수가 아닌 것은 전부 지급 버킷으로 들어가며, '수동 지급' 뱃지 건도 회수가 아니므로 지급 쪽에 합산된다.확정
날짜 헤더의 금액 분해
날짜별 헤더 우측에 지급/회수 × 성공/실패 금액을 쪼개 보여준다. 지급·회수 모두 금액이 0인 구분은 아예 표시하지 않고, 실패 금액도 0이면 실패 부분만 감춘다. 여기서 '실패'로 묶이는 금액도 KPI와 같은 기준(성공이 아닌 나머지 전부)이다.확정
정렬 기준
날짜 그룹은 이체일 토글로 최신순/오래된순 전환. 단 같은 날 안의 각 행은 토글과 무관하게 항상 이체 요청 시각 최신순 고정이다(토글은 날짜 묶음 순서만 바꿈). 회수 페어는 출금 요청 시각을 대표값으로 정렬한다.확정
연결쿠콘 회수 2단계 페어 묶음
회수는 원래 이체 2건
'매출 회수' 한 건은 실제로는 쿠콘 이체 두 건으로 일어난다.① 출금: 락계좌 → 미지급계정 (쿠콘 출금이체 코드 02003700)② 입금: 미지급계정 → 모계좌 (쿠콘 입금이체 코드 02001110)돈이 최종적으로 한 번 이동한 것이므로 화면에선 두 건을 한 줄로 묶어 1건처럼 보여주고 '2단계' 표시를 붙인다(펼치면 ①②가 나옴).확정
페어를 묶는 규칙
'회수' 구분이면서 위 두 코드에 해당하는 출금·입금 건만 페어 대상이다(지급·수동 지급은 절대 안 묶임). 출금 건과 입금 건을 같은 가맹점 + 같은 금액이면 한 쌍으로 매칭한다. 짝을 못 찾은 출금·입금은 각각 단독 행으로 남는다.확정
묶은 페어의 표시 금액·상태
묶인 행의 대표 금액·거래정보(수취 은행/계좌/수취인·거래번호)는 출금 건 기준으로 보여준다.상태는 ①②가 모두 성공/확인완료여야 '성공', 하나라도 실패면 '실패', 그 외에는 출금 건 상태를 따른다.확정
동일 가맹점·동일 금액 회수가 여러 건이면?
매칭이 '가맹점+금액'만 보므로, 같은 날 같은 가맹점에 같은 금액 회수가 여러 건 있으면 출금·입금이 엉뚱하게 짝지어질 여지가 있다(먼저 발견한 짝에 붙는 순서 의존). 실무상 흔치 않지만 표시 오류 가능성으로 확인 필요.확인필요
설정구분·필터·권한 설정
구분 뱃지 3종
이체 한 건의 성격을 색으로 구분한다.지급(파랑): 선정산 정상 지급 이체회수(보라): 락계좌→모계좌 매출대금 스윕수동 지급(노랑): 운영자가 수기로 실행한 지급 이체확정
상태 뱃지 5종
성공(초록)·확인완료(초록)·실패(빨강)·요청중(노랑)·타임아웃(주황). '확인완료'는 이체 후 결과가 확정 확인된 상태로, 성공과 동급으로 집계.확정
기간은 서버 조회, 가맹점·에이전시는 화면 필터
기간은 서버에서 걸러 가져오지만, 가맹점명·에이전시 필터는 화면에서 걸러내는 방식이다. 가맹점 검색은 가맹점명·가맹점번호·사업자번호 부분 일치로 잡힌다. 에이전시는 특정 코드 또는 '미지정'(에이전시 없는 건) 선택 가능.확정
에이전시 드롭다운 목록의 출처
에이전시 선택지 목록은 이체 내역이 아니라 '선정산 결과' 화면 데이터에서 뽑은 에이전시 코드로 채워진다. → 이체 내역에만 있고 선정산 결과 쪽엔 없는 에이전시가 있으면 드롭다운에 안 떠서 못 거를 수 있음. 실제 영향 범위 확인 필요.확인필요
탭 노출 권한
'이체 내역' 탭은 페이허그 내부 전용 제한이 걸려 있지 않다. (정산 상세·계산서 발행·VOC 대응 탭은 페이허그 내부만 노출되도록 조건이 붙어 있으나, 이 탭엔 그 조건이 없음.) 다만 실제 이체 데이터라 취급 주의. — 서버·경로 단계의 별도 접근 통제 여부는 이 화면 코드만으론 확인 불가.확정
데이터데이터 출처·연결 지점
표의 원천 = 쿠콘 이체 결과
이 화면의 각 행은 쿠콘 실제 이체 결과를 날짜별로 묶어 받은 것이다. 거래번호·수취 은행/계좌/수취인, 그리고 실패 시 쿠콘 실패 사유 문구를 그대로 노출한다.단독 행은 실패 시 마지막 칸에 실패 사유를 보여주며 20자 넘으면 말줄임(마우스오버 시 전체)묶은 회수 행은 실패여도 거래번호만 보이고 실패 사유 문구는 표 겉면엔 안 뜸(펼친 ①②에서 각 상태 확인)확정
표의 '시간' = 이체 요청 시각
표에 찍히는 시각은 이체를 요청한 시각이다. 이와 별개로 결과가 확인된 '확인 시각'과 쿠콘 결과코드가 데이터엔 있으나 화면엔 표시하지 않는다. → 지급 시각·기준일과 혼동 금지.확정
개별 배분 '이체 완료' 처리
배분건(이해관계자 배분) 하나를 운영자가 이체완료로 수동 표시하는 기능이 시스템에 존재한다. 단 이 표시 조작은 이 탭이 아니라 정산 상세(배분) 쪽에 붙는 기능으로 보이며, 이 화면은 결과 조회 중심이다.가설
'수동 지급' 뱃지 vs 모계좌 수동 입금
표의 '수동 지급' 뱃지(운영자 수기 지급 이체)와, 모계좌 원장에 외부 입금을 수기 등록하는 별도 기능은 서로 다른 것이다. 명칭이 비슷해 혼동 주의 — 정확한 정의 확인 필요.확인필요
정책정책·주의
'매출 회수' ≠ 과지급 '회수'
이 화면의 매출 회수는 락계좌→모계좌 자금 스윕일 뿐, 정책상 과지급 회수(가맹점에 더 준 돈을 되받는 것)와 완전히 다른 개념이다(충돌 C5). 6대 개념(미지급금·선정산 제외금액·바로이체·과지급·미회수금·환급)과 섞지 말 것.확정
KPI 건수와 표의 줄 수가 다르다
회수 페어를 1건으로 묶어 집계하므로, KPI '회수 N건'과 실제 표에서 펼쳤을 때 보이는 줄 수(2줄)가 어긋난다. 정산 담당이 건수 대조할 때 오해 소지 → 화면 안내 문구 필요.가설
이 화면엔 금액 부호 처리가 없다
지급도 회수도 금액을 모두 양수로 표기한다. 지급 전 음수(당일 차감)·지급 후 음수(과지급 회수 검토) 같은 부호 분기는 여기서 다루지 않는다 — 그 판단은 차액 정산·선정산 결과 쪽 소관.확정
수수료율·지급 캘린더와 무관
