## 0. 한 줄 결론

**"검증"은 설계되지 않았고, "회수"라는 이름의 프레임에 그려진 것은 정책상의 회수(과지급 회수)가 아니라 어드민의 매출 회수(락계좌→모계좌 스윕)와 전자계산서 발행 체계다.** 담당 영역 2개 프레임 어디에도 대사(reconciliation) 로직, 과지급 회수 절차, 미회수금 관리, 가맹점 안내 시점이 존재하지 않는다.

프레임 크기는 1920×1280이나 **텍스트 노드가 3개뿐**이고 도형·화살표·그룹이 0개다. 다이어그램이 전혀 그려지지 않았다.

### 1-1. 여기서 확정할 수 있는 것

- `확정` 이 프레임에 그려진 "검증" 항목은 **연동 상태 점검 2가지뿐**이다: ①최근 3개월 치 데이터 수신 여부 ②로그인 비밀번호 오류 여부. (Figma 24:2079 > 03.매출 내역 검증_Flow (774:985), 노드 1071:594·1071:595)
- `확정` 승인내역 ↔ 매입내역 ↔ 실입금액의 **3중 대사(검증) 로직은 이 프레임에 존재하지 않는다.** 프레임 전체가 비어 있으므로 "설계 중"이 아니라 "미착수"로 보아야 한다.

### 1-2. 여기서 확정할 수 없는 것 (전부 `확인 필요`)

- 검증의 대상(무엇과 무엇을 맞추는가), 검증 시점, 검증 주체(시스템/담당자), 불일치 판정 임계값
- 불일치 시 처리: 지급 보류인지, 예상값으로 지급 강행인지, 해당 매출처만 제외인지
- 불일치 상태를 가맹점에게 보여줄지 여부와 그 문구 (02 §5 `대사 불일치`, 05 §6 `정산 확인 중`에 대응하는 것이 아무것도 없음)
- `최근 3개월 치 데이터`가 **개시 전 1회 점검**인지 **매일 반복 점검**인지. 문장이 명사형 메모라 시점이 없음.

### 1-3. 다른 프레임에 흩어져 있는 "검증 비슷한 것" (참고)

이 프레임이 비어 있으므로, 검증에 해당하는 서술은 담당 영역 밖에 산재한다. 담당 영역 밖이므로 여기서는 위치만 지목한다.

- 04 프레임(774:1054) 화살표 라벨: `당일 변동사항이 있는지 / 매일 오후에 한번더 / 가맹점의 계좌가 변동되었는지` (노드 796:152) — 계좌 변동 점검
- 04 프레임 메모: `계좌 조회했더니 국민은행으로 들어오면 중단 처리 어드민 SNS 발송 계좌변동 01 : 중지` (노드 862:138)
- 매출채권DB(529:2199) 메모의 "승인내역=매입내역 일치 여부 대사 검증 필요" — 문제 인식만

→ `가설` 검증 로직은 04 프레임과 DB 메모에 조각으로 흩어져 있고, 03 프레임으로 취합되지 않았다.

## 2. 04.정산금 회수_Flow (774:1054) — 실제 내용은 3개의 서로 다른 주제

프레임 제목은 `정산금 회수_Flow`(774:1059)이나 실제로 그려진 것은 아래 3개다. **정책상의 회수(과지급 회수)는 이 중 어디에도 없다.**

### 2-A. 자금 흐름 = 락계좌→모계좌 스윕 (어드민 용어의 "매출 회수")

화살표로 확인되는 실제 자금 경로 (`확정`, 노드 796:149 / 796:169 / 796:777 / 820:787 / 820:795 / 820:801):

```
카드사/배달앱  ──[정산금 이체]──▶  가맹점: 선정산 전용 출금 계좌 (796:164)
인포텍: 스크래핑 API (796:155) ──▶ 페이허그: 정산 시스템 (796:160)
정산 시스템 ──[정산금 출금 지시]──▶ 쿠콘: 선정산 전용 출금 계좌 (796:782)
쿠콘: 선정산 전용 출금 계좌 ──▶ 쿠콘: 모계좌 (K뱅크 페이허그 가상계좌) (820:793)
모계좌 ──▶ 투자자 어드민 (820:798) ──[수익금 조회]
쿠콘: 스크래핑 API (862:134) : 계좌 적요(거래내역, 적요 스크래핑)
```

- `확정` 매출 데이터 스크래핑 주체는 **인포텍**(`카드사(여신협회) 매출조회`, `배달앱 매출조회`, 노드 796:776)이고, 계좌 적요 스크래핑 주체는 **쿠콘**(`계좌 적요(거래내역, 적요 스크래핑)`, 노드 862:137)이다. 스크래핑 계통이 2개로 분리되어 있다.
- `확정` `선정산 전용 출금 계좌는 액션시 모든 돈을 가져온다` (노드 862:142) — 부분 인출이 아니라 **전액 스윕**.
- `확정` 이 흐름은 CLAUDE.md 원칙 6의 **어드민 "매출 회수"(락계좌→모계좌 스윕)**이며, 정책의 **"회수"(과지급 회수)와 다른 개념**이다. 프레임 이름이 `정산금 회수`인 탓에 두 개념이 한 이름을 쓰고 있다.

### 2-B. 회수(스윕) 운영 시각·횟수·수동 개입

| 노드ID | 텍스트 (화면 그대로) |

여기서 확정되는 것:

- `확정` **회수(스윕) 횟수 = 하루 2회.** 오전은 **자동**(`돈을 빼는 건 자동`), 오후는 **수동**(`오후 출금은 담당자 버튼으로 한다`). (노드 862:141·862:142)
- `확정` **스크래핑 횟수 = 3시간 간격 총 8회**, 그중 **성공 판정 기준은 오전/오후 2회**. 8회는 오류가 많아서 재시도하는 구조. (노드 1140:1023)
- `확정` **카드사 매출은 카드사별 하루 1회 업로드**되고 **카드사마다 업로드 시각이 다르며**, 여신협회 최종 업로드 시각은 **Figma 문서 자체가 물음표로 미확정**(`여전협 마지막 업로드 시간은??`). (노드 1140:1026)
- `확정` 계좌 적요 조회 결과 **정산금이 국민은행(=선정산 전용계좌가 아닌 곳)으로 입금되면 중단 처리**하고 어드민 SNS를 발송하며, 상태값은 `계좌변동 01 : 중지`. (노드 862:138)
- `가설` `20만원이 비어…` 메모는 **오전 스윕 후 잔액 부족(미회수분)을 담당자가 눈으로 발견해 수동 출금 지시하는 운영**을 뜻한다. 즉 **미회수 감지가 시스템 판정이 아니라 담당자 인지에 의존**한다.

여기서 **확정되지 않는 것** (전부 `확인 필요`):

- 오전 스윕의 **정확한 시각**. 이 프레임에는 시각이 없다. (전체_flow 503:2의 `락계좌 … 11시, 4시 인출`과 `가설` 수준으로만 대응)
- 오후 수동 출금의 **판단 기준**(얼마가 비면 누르는지), **마감 시각**, **누락 시 처리**
- **회수 실패 시 처리**: 재시도 횟수·간격·에스컬레이션·가맹점 통지 — 프레임에 일절 없음
- `계좌변동 01 : 중지`의 **해제 조건**과 **소급 처리**(중지 기간 중 발생 매출의 취급)

### 3-5. 회수 실패 시 처리

- `확정` **재시도·에스컬레이션·통지 규칙이 프레임에 전무하다.**
- `가설` 유일한 실패 대응은 수동이다 — `20만원이 비어, 선정산 전용 출금을 더해야 한다알면 수동으로 담당자가 버튼 눌러서 출금 지시` (862:141). 즉 **부족분 감지는 담당자 인지 의존**이며, 자동 알람·대사 리포트가 설계되지 않았다.

### 3-6. 과지급 / 미회수 발생 조건과 후속 절차

- `확정` **과지급·미회수금의 발생 조건, 채권 생성, 회수 방식(차기 지급 차감 / 락계좌 회수 / 직접 입금 / 상계), 부분·분할 회수, 회수 완료 판정이 두 프레임 어디에도 없다.**
- `확인 필요` 프레임 제목이 `정산금 회수`이므로 **원래 여기에 들어가야 할 내용이 통째로 빠진 것**인지, 아니면 애초에 이 프레임의 "회수"가 스윕만을 의미했는지 기획 의도 확인이 필요하다.

### 3-7. 가맹점에게 안내되는 시점

- `확정` **두 프레임에 가맹점 대상 안내(화면·알림톡·메일) 트리거가 하나도 없다.** 등장하는 통지는 `어드민 SNS 발송`(862:138) 하나이며 이는 **내부 담당자 대상**이다.
- `확정` 계산서 관련해서도 `가맹점은 조회 (선택)`이고 `가맹점 이메일 수집을 안하고 있음`(3301:919) — 즉 **발행 사실을 가맹점에 푸시할 수단이 현재 없다.**
- `확인 필요` 수집 실패·중지·과지급 발생 시 가맹점 안내 시점과 채널.

## 4. 기존 분석(figma_01_선정산시스템.md) 대비 정정 사항

기존 분석 30~31행의 서술을 아래와 같이 정정한다.

1. **[정정] 774:1054를 "실제 내용은 전자계산서 발행 체계"로만 요약한 것은 불완전하다.** 프레임 하단 절반은 명백히 **락계좌→모계좌 스윕 자금 흐름 다이어그램**(카드사/배달앱 → 선정산 전용 출금 계좌 → 쿠콘 → 모계좌 → 투자자)이다. 즉 이 프레임은 "회수와 무관한 내용"이 아니라 **어드민 용어의 "매출 회수"를 그린 것**이며, 빠진 것은 **정책 용어의 "회수"(과지급 회수)**다. 이 구분이 기존 분석에 없어 "회수 로직이 전무"라는 결론의 근거가 흐려졌다.
2. **[누락 보완] 하위총판 채권매입 수수료 `0.45%`(1126:776)가 기존 분석에 없다.** 기존 분석 43행은 3336 메모 기준 `하위파트너 0.5%-0.4%=0.1%`를 인용하는데, 본 프레임은 하위총판→상위총판 **0.45%**로 적혀 있다. 새로운 충돌 값이다(아래 5-①).
3. **[누락 보완] 계산서 발행일 `월 1회 (10일)`(3301:918), 발행 명의 `하위총판 명의로 대신 발급`, 발행 채널 `바로빌`, `관리자 승인 여부` 단계**가 기존 분석에 없다.
4. **[누락 보완] `계좌 조회했더니 국민은행으로 들어오면 중단 처리 / 계좌변동 01 : 중지`(862:138)** — 상태 코드가 명시된 몇 안 되는 중단 규칙인데 기존 분석 88~91행의 "선정산 중단 조건" 목록에 빠져 있다.
5. **[누락 보완] 스크래핑 주체가 인포텍(매출)과 쿠콘(계좌 적요) 2계통으로 분리**되어 있다는 사실이 기존 분석에 없다. 이것이 대사(승인·매입 vs 실입금)의 데이터 원천 구조다.
6. **[동의] 774:985가 사실상 빈 프레임이라는 기존 판단은 정확하다.** 메타데이터로 재확인 결과 텍스트 3개 외 도형·화살표 0개.

## 5. 충돌 레지스터 (확정 금지 항목)

### ① 채권매입 수수료 체인 — 새 값 `0.45%` 등장

| 출처 | 체인 |
|---|---|
| 본 프레임 774:1054 | 가맹점 **1%** → 하위총판 / 하위총판 **0.45%** → 상위총판 / 상위총판 **0.25%** → 페이허그 |
| 전체_flow 503:2 | 가맹점→총판 **1%**, 총판→페이허그 **0.25%**, 페이허그→투자자 **0.11%** (하위/상위 구분 없음) |
| 낱개 메모 3336 | 가맹점→하위총판 1%, 하위→상위 **0.5%**, 상위→페이허그 0.25% |
| 구버전 470:2 | **0.35% / 0.65%** |
| 수익권DB 529:2 | **0.70% / 0.35% / 0.11%** |

→ 하위총판 마진이 본 프레임 기준 `1% − 0.45% = 0.55%`, 3336 메모 기준 `1% − 0.5% = 0.5%`로 **다르다.** CLAUDE.md 미확정 지뢰 C1에 **0.45%를 새 후보로 추가**해야 한다. 어느 값도 채택 금지.

### ② 시스템이용료 0.1%의 부과 대상

- 본 프레임: `페이허그 → 상위총판` 과세 계산서 `0.1% (시스템 이용료)` (821:13) — **총판에게 청구**
- 고객센터 settlement.html: "페이허그 수수료는 면세, **시스템이용료와 전산 수수료는 과세** 항목이에요. 그래서 세금계산서가 면세분과 과세분 2종으로 나뉘어 발행돼요."
- 본 프레임의 가맹점 계산서(821:23)는 **면세 1% 단일**이며, 과세분은 `이체 수수료 부과 하는 케이스 (다우)`에만 발생

→ **충돌.** 고객센터는 모든 가맹점이 과세분 계산서를 받는 것처럼 서술하나, Figma상 일반 계약 가맹점은 **면세 1% 1종만** 받는다. 확정 금지, 재무·계약 확인 필요.

### ③ 계산서 발행 명의

- Figma: `하위총판 명의로 대신 발급` (821:23)
- 고객센터·정책서 전반: 수수료 주체를 "페이허그"로 서술
→ 가맹점이 받는 계산서 공급자가 **페이허그가 아니라 하위총판**이 된다. 가맹점 문의 직결 사안. `확인 필요`.

### ④ 계좌 불일치 시 조치 범위

- Figma: `계좌변동 01 : 중지` — 전체 중지로 읽힘 (862:138)
- 고객센터 settlement.html: "카드사·배달앱에 등록된 지정계좌가 선정산 전용계좌와 일치하지 않는 경우 — **해당 매출처가 선정산 대상에서 제외**돼요"
→ **중지(전체) vs 매출처 제외(부분)**로 범위가 다르다. `확인 필요`.

### ⑤ 매출 수집 시각

- Figma: 3시간 1회 총 8회, 성공 2회(오전/오후), 카드사별 업로드 시각 상이, 여전협 최종 업로드 시각 **미상**

→ 충돌은 아니나, **Figma도 여전협 시각을 물음표로 두고 있으므로 고객센터의 "확정 예정"을 지금 확정값으로 바꿀 근거가 없다.** 현행 유지가 옳다.

### ⑥ "회수" 용어 이중 사용

- Figma 774:1054 `정산금 회수` = 락계좌→모계좌 스윕 (내부 자금 이동)

→ **한 단어가 3가지 의미로 쓰이고 있다.** 용어 분리 필요(CLAUDE.md 원칙 6 확장).
