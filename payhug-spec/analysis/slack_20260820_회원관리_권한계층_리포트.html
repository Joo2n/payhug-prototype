4"영업 ↔ 영업조직이 반대"의 실체 — 4개 후보로 분해

먼저 규칙 확인: 계층상 영업조직이 위입니다(영업조직은 영업을 생성 가능, 영업은 영업조직 생성/변경 불가 — 서버 규칙). 그리고 프론트 라벨 매핑(SALES=영업, SALES_ORG=영업조직)은 전 화면에서 일관합니다 — "라벨이 반대로 붙은 코드"는 없습니다. "반대로 보인다"는 인상은 다음 넷이 겹친 것입니다.

  • 다단 적층(영업조직→영업조직→영업): 프론트는 상위 지정에 아무 제약이 없어 몇 단이든 만들 수 있는 화면이지만, 서버가 허용하는지·깊이 상한이 있는지는 미확인입니다. 목 데이터의 최대 체인은 페이허그→파트너→영업조직→영업 4단이고, 조직 2중 적층 예시는 없습니다 — 메타→이로움 같은 실데이터가 목/테스트 범위 밖 케이스라는 뜻입니다. 서버 확인 필요
  • 다단이어도 링크에는 최하위 코드 1개만 실립니다: URL 파라미터는 파트너/제휴사/영업 코드 3종뿐이라 중간 조직 코드는 URL에 없습니다. 다만 7/22 커밋 메시지("상위 코드로 만들면 본인이 체인에서 누락")는 서버가 코드 소유자에서 출발해 상위로 체인을 재구성함을 시사합니다 — 유실이 아니라 "재구성 위임" 구조로 추정. 서버 확인 필요
  • 배분 쪽 한계: 정산 상품 폼은 영업조직 슬롯이 1단 1개(다우 상품만 상·하위영업 2단)라, 3단 조직 체인은 현행 폼으로는 배분에 못 담습니다. 다단 허용 결정 시 배분 모델과 같이 움직여야 합니다. 프론트 폼 기준 확정
  • 개편안의 결정: 결정 레지스터 Q4는 "중간 단계 생략 허용(확인 후 연결)" — 건너뛰기 결정이지 동일 유형 다단 적층의 결정이 아닙니다. 표준 규칙은 "영업조직→하위파트너" 1단 고정이고, 다단 조직 체인 상태 케이스는 카탈로그 57종에 없습니다. 개편 반영 필요

6회원관리 UI 개편(다른 세션) 커버리지 — 오늘 이슈 8건 판정

기준: 결정 레지스터 decisions_0819.md(콘솔 답변 Q1~Q9 반영), 상태 카탈로그 57종(Flow I 등재만·조립 미실행), Figma 매트릭스 54장.

이슈개편안 커버판정
① 가입링크가 목록 탭 필터를 물려받음가입링크를 회원당 고정 난수 URL 자동 발급 + 행 확장에서 복사(R4·R5, I5·I6)로 전환 — 3드롭다운 조합 UI 자체가 소멸해 세 이슈 모두 구조적으로 해소. 단 구 생성기 폐기·기배포 URL 처리의 명시 결정은 없음(code_analysis.md엔 "재사용" 기재 잔존)해소 (폐기 명시 필요)
② 탭 이동 시 선택값 잔존 결함해소
③ '영업' 드롭다운 라벨 혼합해소 (병행 기간 재확인)
④ 프리필 회귀 위험(7/22 사고 사유)등록 계층 연동에 자동 선택·프리필 없음(회귀 벡터 제거)이나 사고를 명시 검토한 기록은 없음. 참여자가 상위 회원의 링크를 보게 되는지는 '확인 필요' 상태부분
⑤ SALES/SALES_ORG 생성 규칙·유형 정정상위 유형 규칙은 확정됐으나 유형×유형 생성 권한표 미정의, 유형 변경(정정) 플로우는 상태 케이스·원고 어디에도 없음 — 메타플레이 실사례를 처리할 수단 부재누락
⑥ 다단 영업조직·중간 조직 정보Q4(생략 허용)와 관계 모델로 방향은 잡혔으나 동일 유형 다단 케이스 없음, 난수 URL→체인 시작점 서버 매핑 미결부분
⑦ 참여자 시점 정산상품·요율 비노출(PAYHUG-202/204)총판 시점 메뉴는 정의됐으나 요율·체인 열람 범위 3곳 전부 '확인 필요', 202/204 인용 0건 — 병행 운영 기간 요건으로 승계 필요부분
⑧ 링크 발급 주체 정책전 유형 자동 발급 전제이나 허용/금지 명문 없음 — 구 정책("파트너 계정으로 생성")의 폐기 여부 미정부분 (정책 명문 필요)

이 판정을 근거로 반영 필요 목록(재확인 2 · 보강 5 · 신규 1)을 개편 세션에, 정책 판단 3건 + 기존 미확정 근거 보강 1건을 정책서 세션에 전달했습니다(전달 내용은 아래 §8).

7백엔드 확인 질문 (기획 → 개발)

프론트에 분기가 없어 서버만 아는 것들 — 이 답이 와야 계정별 매트릭스가 '확정'으로 바뀝니다.

  1. 회원 목록 스코프 규칙: "자기+하위"의 하위 판정(재귀? 깊이 제한?), 비활성 하위 포함 여부, 관리자=전체 여부. ?userType=SALES 필터에 SALES_ORG 포함 여부.
  2. 등록가능유형(creatable-types)의 로그인 유형별 반환값 매트릭스 — 빈 배열(등록 버튼 숨김)이 오는 유형은 누구인가.
  3. 생성/변경 계층 규칙 전체표 — "SALES→SALES_ORG 불가" 외 조합별 허용 여부, 에러의 주어(로그인자인지 선택한 상위인지).
  4. 참여자의 수정 권한 상세 — 상태 변경·상위 변경·추천코드 변경을 필드 단위로 거부하는지.
  5. 삭제·비활성화의 서버측 권한(버튼 숨김은 프론트뿐) + "정산 상품 배정 시 삭제 불가"의 정확한 조건.
  6. 추천코드 유일성·형식 검증(프론트는 대문자 변환뿐).
  7. 영업코드 단독 가입 링크의 유효성 — 가입 API가 코드 소유자에서 상위로 체인을 재구성하는지, 중간 조직이 배분에 포함되는지.
  8. 비활성 계정 로그인 차단 여부(안내 문구만 존재).
  9. 메타플레이·이로움컴퍼니·엔케이 계정의 실제 DB userType — "(영업)" 표기의 진위.
  10. 영업조직 다단 적층 허용·깊이 상한·순환 방지.
  11. 정산 role SALES(=영업조직 몫) 명명 정리 가능 여부, 다단 조직 배분 모델.
  12. 개편 전환기 중복 경로 우선순위 — 같은 가맹점이 기배포 partnerCode/salesCode URL과 개편 난수 링크 양쪽으로 유입될 때 체인 기준을 어느 쪽으로 잡는가 (07 §7-12 연계).
