## 4. 관찰에서 추론되는 정산·지급·회수 로직 (전부 가설)

1. **[가설] 실제 구현 산식**: `선정산 지급액 = (매출 − 외부수수료[카드/배달]) − 선정산 수수료(채권매입 + 시스템이용료 + 이체수수료 300원) ± 카드수수료 차액(전일 이전 거래분) − 오프라인차감`. 03의 기본 구조와 골격은 같으나, `플랫폼 환급 / 추가 지급 / 선정산 제외금액 / 이전 과지급 회수금` 항목이 산식 어디에도 없음.
2. **[가설] 예상 수수료 선지급 + 차액 자동 상계 모델**: 승인 시점에 관리자가 설정한 카드사별 요율(1.15%)로 예상 수수료를 계산해 당일 지급하고, 매입 확정 시 실제 수수료와의 차액을 "다음 선정산에서 환급 또는 추가 차감"으로 자동 반영한다. 대시보드의 `확정률 80.8%`, 배너의 `대기 49건 (+1,670원)`이 이 큐의 상태 표시로 보임. 03 §6 "정산 후 변동" 중 **카드 수수료 차액만** 자동화되어 있고, 배달 플랫폼 정정·환급·취소 변동의 자동 반영 여부는 화면 근거 없음.
3. **[가설] 미확정 매출 선지급**: 일자 카드의 `예상매출 70건 포함` 배지 → 매입 미확정(스크래핑 미완) 건도 예상치로 선정산에 포함해 지급. 포함 기준·리스크 한도 정책은 화면에 없음.
4. **[가설] 배치 스케줄**: 락계좌 매출대금 회수(스윕) 11:00·14:00 하루 2회 → 선정산 지급 11:30 (03의 "오전 10시 데이터 업데이트"는 화면 근거 없음, 매출 `데이터수정` 값은 09:04로 관찰됨).
5. **[가설] 자금 구조**: 모계좌(페이허그) ← 가맹점별 락계좌에서 `매출 회수`(입금) + `외부 입금`(투자금 충전), → `선정산 지급`/`수동 지급`(출금). 즉 어드민의 "회수"는 1차적으로 **락계좌→모계좌 매출대금 스윕**을 의미.
6. **[가설] 이체 한도 500만원**: 12,259,908원·10,372,622원 지급이 이체 실패한 뒤 관리자가 500만+500만+잔액으로 3분할 수동 이체 — 1회 이체 한도(추정 5백만 원) 초과가 실패 원인으로 보임. 실패 시 자동 재처리는 없고 **수동 이체로만 복구**.
7. **[가설] 바로이체 = 미지급 정리 수단**: `DIRECT_PAYOUT_TRANSFER` 이벤트의 상세가 "관리자 미지급 정리"로 기록됨 → 정규 11:30 배치 밖에서 미지급분을 지급하는 별도 트랜잭션. 생성 조건은 불명(04 §6의 "대상 생성 조건 확인 필요"와 동일하게 미해결).
8. **[가설] 과지급 회수는 '부채(DEBT_RECOVERY)' 모드로 구현**: 회수 수단은 가맹점 단위 모드 전환뿐 — 정산은 계속 계산하되 이체를 생략하고 그 금액(`부채 오프셋`)으로 부채를 상환. 건 단위 회수건 관리(발생원인·잔액·부분회수)는 없음. 민속보쌈이 정산 현황에서 매일 `이체대기`로 표시되는 것은 실제로는 부채 회수 모드에 의한 **이체 생략**으로 보임(상태 라벨과 실체 불일치 가능성).
9. **[가설] UPL 대사**: 가맹점 행마다 `UPL기준 금액 (차이 ±)`을 병기 → 외부(기존) 시스템 UPL의 계산액과 자사 계산액을 상시 대사 중이며, 차이가 ±19만원까지 발생. UPL의 정체와 차이 처리 정책은 확인 필요.
10. **[가설] 435,263원 수동 이체 = 04 §3의 환급 미지급 8건 처리**: 04에 기록된 "총 435,263원 수동이체 일괄 처리 검토"와 정확히 같은 금액이 07-13 12:21 `수동 지급`/`ADMIN_MANUAL_TRANSFER_SUCCESS`로 관찰됨 → 수동이체로 실행된 것으로 보임. 다만 이 지급이 어떤 정산건과 연결되는지, 중복 지급 방지 표식이 남는지는 화면상 근거 없음.

## 8. 재기획이 필요한 부분 (정책 없이 구현된 것으로 보이는 지점)

1. **회수 도메인 전면 재설계 (최우선)** — 06의 회수 어드민이 통째로 없음. 현재의 회수 수단은 "가맹점을 DEBT_RECOVERY 모드로 전환해 이체를 전부 생략"하는 극단적 방식 하나뿐. 건 단위 회수건(발생원인·원지급액·잔액·방식·상태) 객체 신설 필요.
2. **'회수' 용어 충돌 해소** — 어드민의 `매출 회수`(락계좌 스윕)와 정책 문서의 `회수`(과지급 회수)가 같은 단어. 활동 로그 카테고리 `회수`에 두 의미가 섞이기 전에 명칭 분리(예: 매출대금 수취 vs 과지급 회수).
3. **미지급 관리 부재** — `가맹점 이체 실패`가 로그로만 남고, 미지급 잔액·재처리 큐·미지급 알림이 없음. 실패 복구가 관리자 기억과 수동 이체에 의존(07-12, 07-13 연속 발생 관찰). 이체 한도(추정 5백만) 정책과 자동 분할·재시도 정책 필요.
4. **수동 이체·바로이체와 정산 데이터의 미연결** — 수동 지급 435,263원이 어떤 미지급건 8건을 정리한 것인지 시스템상 연결 없음 → 06의 "중복 회수(지급) 방지" 요구를 충족 불가. 수동 이체 시 사유·관련 정산번호 필수 입력으로 재기획 필요.
5. **예상매출 포함 지급 정책** — 매입 미확정 건(19%)을 예상 수수료로 선지급하는 것이 관찰되나, 포함/제외 기준·가맹점별 한도·리스크 통제 정책이 문서에 없음(03 §2 산식에도 없음).
6. **오프라인차감** — 산식에 실존하는 차감 항목인데 02·03 어디에도 정의 없음. 발생 조건·계산식 역추적 후 정책화 필요.
7. **선정산 제외를 메모로 운영** — "거래일 7/8~7/9 건은 바이패스 처리" 같은 제외 처리가 수기 메모로만 존재. 02의 '선정산 제외금액'을 데이터(사유 코드·금액·기간)로 승격 필요.
8. **`회수 전용`·`수수료 면제` 토글** — 가맹점 단위 스위치가 존재하나 사용 조건·승인 절차·해제 기준 정책 없음. 오조작 시 지급 전면 중단/무료화되는 고위험 스위치.
9. **UPL 대사 차이 방치** — 행마다 UPL기준 차이(최대 ±19만원 관찰)를 보여주기만 하고, 차이 발생 시 처리 상태(확인 중/정정/무시)가 없음. 04 §4류 과지급의 조기 탐지 수단으로 정식화할 가치 있음.
10. **부채 모드 가맹점의 상태 표기** — 이체를 생략한 건이 정산 현황에 `이체대기`로 계속 표시되는 것으로 보임(민속보쌈 전 일자). 상태값에 `부채 상계` 등 별도 상태 필요.
11. **환급 처리 부재** — 플랫폼 환급(+) 항목이 산식·화면·상태 어디에도 없음. 04 §1·§3 재발 방지가 구조적으로 불가능한 상태.
12. **알림톡 연동 부재** — 06의 1순위 과제인 알림톡 관련 요소가 어드민에 전무(발송 이력·가맹점 알림 여부 필드 없음). `TG` 칼럼(텔레그램 추정)은 내부용으로 보임.
13. **설계 없는 메뉴 6종** — 1:1 문의, 정산 시뮬레이션, 약관 관리, 스크래핑 장애 이력, AI 모니터링 어시스턴트, 그리고 정산 현황의 4개 탭(정산 상세/차액 정산/이체 내역/VOC 대응)은 메뉴만 있고 화면 설계 없음 — 구현 실체 확인 후 문서화 필요.
