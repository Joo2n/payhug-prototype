## 5. 누락 항목

가맹점 UI 자체가 없으므로 "UI 누락"과 "데이터 설계 누락"을 구분한다.

### 5-1. 가맹점 화면 부재 (영역 전체)
- 05가 정의한 가맹점 메인/상세 화면이 이 영역에 없음. 메인 15항목·상세 17항목 전부 대응 화면 없음. `확인 필요`: 별도 캔버스(예: 매출관리 화면)에 존재하는지.

### 5-2. 데이터 설계(DB·계산식) 기준 누락
- **미지급금**: 개념·필드·상태 모두 없음. "20만원이 비어 … 수동으로 버튼 눌러 출금"이라는 운영 메모만 있고 미지급 발생·해소 트래킹 구조 없음.
- **선정산 제외금액**: 없음. `미매입 승인금액`·`미매입 지급예상액`이 가장 근접하나 이는 "매입 미확정" 단일 사유만 커버(`가설`). 검증 불가·위험 거래·지급 보류·한도 초과·계약상 제외의 구분 필드 없음.
- **바로이체 / 바로이체 대상금액 / 바로이체 미지급**: 영역 전체에서 단어 자체가 등장하지 않음. 완전 누락.
- **과지급**: 정산채권DB 예상오차 보정 칼럼이 `과소`(과소예상액면금액, 과소 양수가액, 과소 분배액 = 추가 지급 방향)만 존재. 매출채권DB에 `과다예상 수수료합계액` 등 과다 '예상' 칼럼은 있으나, **지급 후 과지급 발생분을 채권/이력으로 관리하는 구조 없음**.
- **미회수금**: 없음. `상환 부족액` 칼럼이 유일한 근접 항목이나 정의 미기재(`확인 필요`). 회수 잔액·부분 회수·분할 회수 관리 구조 없음.
- **환급(플랫폼 환급·프로모션 환급·광고비)**: 매출채권DB에 배달앱 쿠폰·포인트·배달료 칼럼은 있으나 `+` 방향의 환급 항목(플랫폼 환급, 프로모션 환급) 칼럼 없음. 광고비(우리가게클릭비) 칼럼도 없음.
- **지급 상태·회수 상태**: 02 §5의 지급 상태 11종·회수 상태 9종에 대응하는 상태 필드가 DB 어디에도 없음. 존재하는 상태는 `매입상태` 하나(값 예시도 `매입완료`뿐).
- **최종 업데이트 일시**: 스크래핑 8회/일 체계인데 데이터 기준 시점(최종 업데이트 일시) 필드·표기 없음.
- **취소·환불·추가 매입**: 03 §6 '정산 후 변동' 사유들(승인 취소, 매입 취소, 환불, 추가 매입, 플랫폼 정정)을 담는 칼럼·이벤트 구조 없음. 매출채권DB 메모에 "승인내역=매입내역 일치 여부 대사 검증 필요"로 문제 인식만 존재.
- **04.정산금 회수_Flow의 회수 로직**: 프레임 제목만 '회수'이고 회수 절차(차감·락계좌 회수·직접 입금·수동 처리·부분/분할 회수·상계)가 전무. 전체_flow에도 "(추후) 회수절차는 수기로"라고만 기재.
- **03.매출 내역 검증_Flow / 05.수수료 및 수익배분_Flow**: 빈 프레임. 특히 검증 플로우는 대사(승인 vs 매입 vs 실입금) 정책의 핵심인데 미작성.

## 7. 정책과 충돌하는 부분

1. **지급일 기준**: 03 §5 "전일 매출 기준 … 다음날 오전 11시 30분 지급"(D+1) vs 정산채권DB "`지급예상일` = 거래일자의 익익영업일"(D+2, 예: 20250901 거래→20250903). `확인 필요`: 정산채권DB의 지급예상일이 '가맹점 선정산 지급일'이 아니라 '카드사→락계좌 입금 예정일'이라면 충돌이 아님. 어느 쪽인지 라벨 정의가 없음.
2. **이체수수료 부과 단위**: 03 §3 "가맹점 1개 기준 하루 1회, 이체수수료 300원" vs 01.계약체결 "이체수수료 : **정산금 건당** N원 : 어드민에서 입력", 계산식 모음 "1-1의 거래가 100건 일어나고 마감하여 이체수수료"(마감 시 1회로 읽히나 문구 모호). 건당/일1회가 문서 간 상충. `확인 필요`.
3. **수수료율 수치 혼재**: 503:2(1% / 0.25% / 0.11%) vs 470:2(0.35% / 0.65%) vs 수익권DB 예시(총판 0.70% / 페이허그 0.35% / 투자자 0.11%) vs 3336 메모(가맹점→하위총판 1%, 하위→상위 0.5%, 상위→페이허그 0.25%, 페이허그→투자자 0.11%, 시스템이용료 0.1%, 페이허그 수익 0.14%+0.1%+300원). 최소 3개 버전이 병존하며 어떤 것이 현행인지 표기 없음. 03 문서도 수치를 확정하지 않으므로 `확인 필요`.
4. **산식 구조**: 03 §1 기본 산식은 `+플랫폼 환급 +추가 지급 -선정산 제외금액 -이전 과지급 회수금` 항을 포함하나, Figma 계산식(정산채권DB: 액면금액×(1-할인율) 체인, 계산식 모음)에는 이 4개 항이 전부 없음. 즉 Figma 산식은 '정상 케이스 전용'이며 03의 조정 항목이 구조적으로 누락.
5. **버림·소수점**: 03 §4 "버림 정책 재확인 필요" vs Figma 3336:116-117 "공급가액 소수점 절사 … ← 소수점 처리 방식 개발 확인 필요". 양쪽 모두 미확정(충돌은 아니나 동일 미결이 이중 관리되고 있음).
6. **음수 처리**: 03 §6 "지급 전 음수 발생: 당일 지급액에서 차감 / 지급 후 음수 발생: 미회수금으로 관리" vs Figma에는 음수 분기 로직·필드 없음(과소 방향 보정만 존재). 04 §2 가게배달 음수 케이스와 함께 미반영.
7. **선정산 중단 조건의 산재**: ①1071:597 "당일 스크래핑 안되면 무조건 중단, 락계좌 변경, ID/PW 상이" ②계산식 모음 "3주 승인금액 데이터 없으면 중단, 단 오후 매입금액 있으면 익일 정산" ③스크래핑 실패 시 "예상금액으로 계산 처리(요일별 3주 평균)". ①(즉시 중단)과 ③(예상금액으로 지급 계속)이 상충 가능. 어떤 오류 코드에서 중단이고 어떤 경우 예상 지급인지 기준 미정. `확인 필요`.
8. **예상 지급의 근거**: "AI로 학습시킨 카드예상 수수료율" 및 3주 요일 평균으로 실지급하는 정책은 02 `예상 지급액`(미확정 데이터 기준 계산)의 범위를 넘어 **미수집 매출을 추정해 선지급**하는 것. 02/03에 없는 신규 정책이며 과지급 리스크와 직결. 정책 문서 합의 필요(`확인 필요`).
9. **스크래핑·시각 체계**: 03 "매일 오전 10시 데이터 업데이트" vs Figma "3시간 단위 총 8번", "빠른계좌조회 10:30, 18:30", "모계좌 11시20분 입금, 11시30분 이체", "락계좌 11시·4시 인출". 10시 업데이트 언급은 Figma에 없음. 시각 체계 단일화 필요.

추가로 02 §5 데이터 상태 중 `대사 불일치`, `데이터 정정`, `일부 수집`과 05 §6 문구 8종에 대응하는 상태가 전혀 설계되지 않았다. 스크래핑 실패는 "예상금액 계산" 또는 "중단"으로만 처리되어 가맹점에게 보여줄 중간 상태가 없다.

## 9. 수정 제안

1. **빈 프레임 2개(03.매출 내역 검증, 05.수수료 및 수익배분) 우선 작성.** 특히 검증 플로우에 승인↔매입↔실입금 3중 대사와 `대사 불일치`(가맹점 노출: `정산 확인 중`) 상태 정의를 포함할 것.
2. **04.정산금 회수_Flow 재작성.** 현재 내용(전자계산서·수익배분)은 05.수수료 및 수익배분_Flow로 이관하고, 회수 플로우에는 과지급 발생→회수건 생성→회수 방식(차기 지급 차감/락계좌 회수/직접 입금/수동)→부분·분할 회수→상계→회수 완료 판단을 담을 것(02 §4, 04 §4 기준).
3. **6개 개념의 데이터 분리 설계.** 미지급금 / 선정산 제외금액 / 바로이체(대상·미지급) / 과지급 / 미회수금 / 환급을 각각 별도 엔티티·필드로 설계. 특히 정산채권DB에 `과소` 계열과 대칭인 `과다(과지급)` 계열 칼럼 또는 별도 회수채권 DB를 추가.
4. **상태 필드 추가.** 정산채권DB(또는 지급 배치 DB)에 02 §5의 지급 상태, 회수 상태, 데이터 상태를 코드화하여 반영. 현행처럼 `매입상태` 하나로는 05 §6 문구 8종을 구동할 수 없음.
5. **용어 정합.** 용어정리 3장의 `과정산금/미정산금/미수금액/미수금`을 02 용어집과 단일 매핑표로 통합하고, `미수금`→`미회수금` 등 표준 용어로 통일. `총판(…? …?)`, `유동화기관(투자자?)`의 물음표를 해소. 오탈자(`수신혜`, `부자세`, `파크너`, `스트래핑`, `신찬카드`) 수정.
6. **수수료율 버전 관리.** 470:2(0.35/0.65) 구버전 프레임에 'DEPRECATED' 표기하고, 503:2·수익권DB·3336 메모의 수치를 단일 기준표로 확정. 이체수수료 부과 단위(건당 vs 일1회)를 03과 함께 확정.
7. **지급예상일 정의 명기.** 정산채권DB `지급예상일`이 (a)가맹점 선정산 지급일인지 (b)플랫폼→락계좌 입금예정일인지 필드 설명에 명시. (a)라면 03의 D+1 지급과 충돌 해소 필요.
8. **선정산 중단·예상 지급 정책 일원화.** 스크래핑 실패 유형별로 [빈값=대상 아님 / 오류=예상금액 지급 / 당일 실패=중단 / 3주 데이터 없음=중단]의 우선순위를 하나의 결정표로 정리하고, 예상금액 선지급 정책(3주 요일 평균, AI 수수료율)의 승인 여부를 정책 문서(03)에 반영.
9. **바로이체 설계 착수.** 04 §6의 미결 사항(생성 조건·지급 주체·계좌·주말 기준·실패 재처리·회수금 상계)을 확인한 뒤 별도 플로우 프레임 추가.
10. **가맹점 UI 프레임 신설.** 05 §2~§6 기준 메인/상세 화면을 이 캔버스 또는 별도 캔버스에 작성하고, 내부 용어(액면금액·양수가액·할인율 등)가 노출되지 않도록 05 §5 변환표를 적용. `최종 업데이트 일시` 표기 필수.
11. **Document History 갱신.** 2025.10.03 V.0.0 이후 이력이 없어 버전 추적 불가. 프레임 추가·수수료 변경 시점 기록.
