### 2-2. 기재값에서 역산한 "가맹점이 하는 일" — `가설`

760:71에 단계 목록은 없지만 기재값의 괄호 주석이 **취득 시점**을 알려준다.

| 취득 시점 (Figma 표기) | 가맹점이 제공하는 것 |
|---|---|
| 홈페이지 회원 가입 시 등록 | 상호·주소·대표자명 (사업자등록증 기반) |

| **가입 시 업로드** | 계좌 정보 |
| **가입 시 서명패드로 등록** | 사인(서명 이미지) |
| 어드민에서 입력 | 채권매입 수수료율, 이체수수료 (가맹점이 아닌 **운영자**가 입력) |

> **신분증(주민등록증·운전면허증)은 Figma 760:71에 전혀 없다.** 기재값 어디에도 신분증 항목이 없다. `확인 필요`

### 2-3. 서명 방식 — `확정` + 순서에 대한 `가설`

- 5종 계약서 전부 공통으로 **"계약서 사인 : 가입 시 서명패드로 등록한 사인"**
- → 가맹점이 계약서 5종에 **각각 순차 서명하는 구조가 아니다.** 가입 때 서명패드로 등록한 사인 **1개**가 5종 전체에 자동 반영된다. `확정`(기재값 문구)
- → **"가맹점이 서명하는 순서"라는 개념 자체가 Figma 설계에는 존재하지 않는다.** 순서가 있는 것은 계약서 생성·저장 순서(§3)일 뿐이다. `가설`
- 페이허그 측 사인은 두 곳에 빨강 주석 **"(사인 이미지 저장 필요)"** — 미구현/준비 필요 항목으로 보인다. `확인 필요`

## 5. 충돌 레지스터 (Figma vs 고객센터 / Figma 내부)

### 🔴 CT-1. 채권 양수인이 누구인가 — 고객센터가 사실과 다름

- **Figma**: 정산금채권 양수도 계약서는 **(가맹점 - 총판)** 계약. 양수인 = **채권매입업체:총판**. 페이허그는 **재양수인**(부칙3). 출처: 760:195, 771:795, 760:51, 760:67
- **고객센터** `contract.html` sec-1-2: "사장님이 카드사·배달앱에서 원래 받으실 정산금에 대한 권리(정산금 채권)를 **페이허그가 완전히 사 오는 방식**(양수도)이에요."
- → 가맹점이 실제 서명하는 계약서에는 **총판 상호가 양수인으로 인쇄**된다. 고객센터 설명과 가맹점이 눈으로 보는 계약서가 어긋난다.
- 예외: **다우데이터 계약 시에만** 양수도 계약서 미노출 + 양수인 = 페이허그 (771:795). 즉 "페이허그가 사 온다"는 **다우 케이스에만 맞는 설명**이다.
- **`확인 필요`**: 총판을 경유하지 않는 직계약 케이스가 다우 외에도 있는지.

### 🟡 CT-11. 계약 화면 6단계가 Figma 760:71에 없음

### 🟡 CT-12. 총판·투자자가 고객센터에 전무

- Figma는 계약 참여 주체를 **가맹점·총판(파트너)·페이허그·투자자** 4자로 명시(760:124~134), 영업사원은 총판과 별도 계약(760:186)

- → 가맹점이 서명하는 계약서에 총판·유동화기관이 당사자로 등장하므로 최소한의 설명이 필요하다.

## 6. 기존 분석 문서에 대한 지적

`payhug-spec/analysis/figma_01_선정산시스템.md` 검토 결과:

1. **L27~28 보완 필요** — "계약서 (7장)"을 단순 나열했는데, **7장 = 5개 문서(이용계약서 2p + 양수도계약서 2p + 부칙1·2·3 각 1p)** 라는 매핑이 없다. 또한 L27은 5종을 "서비스 이용계약서, 정산금채권 양수도 계약서, 자동 출금 이체 동의서, 정산금채권 재양도 합의서, 개인(신용)정보 동의서"로 적었는데 **부칙 번호(부칙1=개인정보, 부칙2=자동출금이체, 부칙3=재양도)** 정보가 빠져 있다.
2. **L198 정확** — "계약서 A4 7장 미판독"은 맞다. 다만 **원인이 저해상도가 아니라 '스크린샷 이미지로 붙여넣어져 있고 원본이 595×842라 업스케일 불가'** 라는 점을 명시하면 재시도 낭비를 막을 수 있다. 추가로 **760:59의 수탁사명은 분홍 사각형으로 의도적으로 가려져 있어** 해상도를 올려도 판독 불가다.
3. **L142와 정합** — 이체수수료 건당/일1회 충돌 지적은 타당하며, 본 조사에서 **양수도 계약서 제17조 표가 "정산금 건당 원"으로 명시**됨을 확인해 계약서 측 근거를 보강했다.
4. **누락 지적 없음** — L182(수수료율 확정본 질문)는 유효하다. Figma 제17조 표가 공란이므로 Figma로는 해소 불가임을 본 문서가 확인했다.

## 7. 고객센터 반영 제안 (아티클 — 무엇을 — 어떻게)

우선순위 순.

1. **contract.html sec-1-2 (계약은 대출인가요)** — "페이허그가 완전히 사 오는 방식"을 수정. 실제 양수도 계약서는 (가맹점-총판)이고 페이허그는 재양수인이다. 다만 **총판·투자자 구조를 어디까지 노출할지는 정책 결정 사항**이므로, 확정 전까지는 "정산금 채권을 양수도하는 방식"으로 주체를 특정하지 않게 완화하는 것을 권한다. (CT-1)
2. **contract.html sec-1-1 ⑥ / documents.html** — 계약서 목록 정정. 「고유식별정보 수집·이용 동의서」의 실재 여부를 확인하고, 실제로 서명하는 **정산금채권 양수도 계약서·정산금채권 재양도 합의서**를 목록에 추가할지 결정. 「서비스 이용약관」 → 「페이허그 서비스 이용 계약서」로 명칭 통일. (CT-2)
3. **contract.html sec-1-1 ⑥ / documents.html L50** — 서명 시점 문구. Figma는 "가입 시 서명패드 1회 등록 → 5종 자동 반영", 고객센터는 "6단계에서 서명". 실제 구현 확인 후 한쪽으로 통일. 서명이 1회로 끝난다면 "계약서마다 따로 서명하지 않으셔도 돼요"가 유용한 안내가 된다. (CT-3)
4. **contract.html sec-2-1 (이용료)** — 「전산 수수료가 어떤 단위로 부과되는지는 확정 예정」을 **「정산금 건당」으로 갱신 가능** (양수도 계약서 제17조 근거). 단 03 §3의 "하루 1회" 기술과 상충하므로 정책 확정 후 반영. 아울러 **시스템이용료가 계약서에 근거 조항이 없는 문제**를 정책팀에 에스컬레이션. (CT-5)
5. **contract.html sec-1-7 (계약 기간)** — "계약일"의 정의를 명시. 양수도 계약서 기준 **계약일 = 가입 완료일**. 이용계약서 기준도 동일한지 확인 후 반영. (CT-6)
6. **contract.html sec-1-3 / sec-1-8 / signup.html sec-1-7 (심사)** — "페이허그 내부 심사" 및 "총판에는 심사 권한 없음"은 Figma 계약체결 플로우에 근거가 없다. 어드민 노드·계약상태 값으로 교차 검증 전까지 단정 표현을 완화할지 검토. (CT-4)
7. **개인정보 제3자 제공 안내** — 현재 어느 아티클에도 수탁사·제공받는 자 목록이 없다. 760:59가 마스킹되어 있으므로 확정 목록을 법무·개발에서 받아 별도 섹션으로 신설 검토. 제공 정보 = 고유식별정보·거래정보, 보유기간 = 서비스 종료 시 또는 상담 후 폐기까지는 확인됨. (CT-10, CT-2)
8. **contract.html sec-1-11 (서비스 중지)** — "선정산 이용계약서 **제8조**에 정해진 사유"라고 조문 번호를 인용 중인데, 760:11 본문이 판독 불가라 **조문 번호를 검증할 수 없다.** 원본 계약서로 조 번호 확인 필요. (인용 오류 시 신뢰도 타격)
9. **(내부)** 계약서 템플릿 미완성 항목 — 대상채권 확정일 공란, 재양도 합의서 날짜 "2026. 00. 00.", 페이허그 대표이사 사인 이미지 미저장, 자택주소 필드 의미 불일치, 유동화기관 대표자명 = 총판 성명 오기. 고객센터가 아닌 **기획·개발 이슈로 티켓화** 권장. (CT-7, CT-8, CT-9)
