00시작 전 확인 3건

이 세 가지를 확인하지 않고 QA를 시작하면 정상 동작을 결함으로, 결함을 정상으로 판정하게 된다.

① 백엔드가 함께 배포됐는지 먼저 확인한다

이번 수정의 핵심인 ‘배달 건 주문번호 표기’는 백엔드가 salesSource 필드를 함께 내려줘야만 동작한다. 프론트 코드는 이렇게 돼 있다.

// app/settlement/account/excluded/page.tsx
const isCard = item.salesSource ? item.salesSource === "CARD" : true;

필드가 없거나 비면 전부 카드로 간주한다. 백엔드가 아직이면 배달 건이 여전히 ‘승인번호 / 카드 수수료’로 보이는데, 이건 프론트 결함이 아니라 정상 동작이다.

확인 방법 — 크롬에서 F12 → Network 탭 → 선정산 제외액 내역 진입 → account/excluded 요청의 Response에 salesSource·residual·dateFrom·dateTo·transferId가 있는지 눈으로 본다. 없으면 QA를 시작하지 말고 개발에 백엔드 배포 여부를 먼저 묻는다.

② QA 기간에 develop을 건드리지 말라고 요청한다

지금 DEV 가맹점 앱은 feature/excluded-payout-delivery-manual-transfer 브랜치를 돌고 있다(8/26 11:39 수동 배포). develop에 머지되지 않은 상태라, 누군가 develop에 push하면 DEV가 develop으로 덮어써지고 QA 대상 코드가 사라진다. 개발에 미리 공유해 둔다.

③ 바로이체가 DEV에서 실제 송금인지 확인한다

안내받은 “DEV의 수동이체는 실제 송금 없이 성공 처리”는 수동이체에 대한 설명이다. 바로이체(action:"TRANSFER")도 같은지는 코드에 근거가 없다. 어드민 확인창 문구는 “가맹점 계좌로 순지급액 전액을 실제 이체합니다”이고, 실행 후 취소가 안 된다. 바로이체를 처음 누르기 전에 개발에 확인한다.

01필요한 계정

두 종류가 모두 있어야 한다. 어드민으로 데이터를 만들고, 가맹점 계정으로 결과를 본다. 어드민이 가맹점 화면을 대신 보는 기능은 없다.

계정로그인 정보반드시 갖춰야 할 조건없으면
가맹점
dev.payhug.io		 사업자등록번호 또는 휴대전화번호 + 비밀번호 붙어 있는 사업장의 계약상태가 APPROVED. 정산 활성 상태. 개발·운영에 요청.
신규 가입은 KCB 본인인증을 타서 사실상 불가.
어드민
admin.dev.payhug.io		 휴대전화번호 또는 사업자번호 + 비밀번호
이메일 아님		 userType이 ADMIN 또는 PAYHUG

파트너 계열 계정으로는 QA를 할 수 없다

PARTNER·SALES_ORG·SALES·AFFILIATE·INVESTOR 계정은 수동이체·바로이체·이미지급 버튼이 화면에 그려지지도 않는다. 테스트 데이터를 만들 수 없으니 반드시 ADMIN 또는 PAYHUG 계정을 받는다.

계약상태가 APPROVED가 아니면 진입 자체가 막힌다

대시보드의 ‘미리 받는 돈’ 카드는 계약상태가 APPROVED일 때만 그려진다. 승인 상태가 아니면 ‘계좌 입금 내역보기’ 버튼이 아예 없다. 다른 카드가 대신 뜬다. 사업장이 여러 개면 대시보드 상단 드롭다운에서 APPROVED인 사업장을 골라야 한다.

가맹점 앱 진입 경로

로그인 → 대시보드 → 사업장 선택(APPROVED) → “미리 받는 돈” 카드 → [계좌 입금 내역보기] → /settlement/account?bizNo=…

로그인만 되어 있으면 /settlement/account?bizNo= URL로 직접 진입할 수도 있다. bizNo만 바꿔가며 여러 가맹점을 볼 수 있어 QA에 편하다.

02제외액이 생기는 5갈래

“선정산 제외액”이라는 한 개의 배지 뒤에 서로 다른 처리가 다섯 갈래 있다. 무엇을 만들고 무엇을 확인할지는 이 구분에서 갈린다.

경로누가 어떻게 실행가맹점 화면상세 진입키
A 정상 선정산 자동 배치 (11:30 / 18:00) 미리 받는 돈 클릭 불가 —
B 배치 중 자동 바로지급 버튼 없음. 배치가 스스로 분류 선정산 제외액 payoutId
C 미정산 누락 → 바로이체 운영이 건을 골라 [바로이체] 클릭 선정산 제외액 payoutId 또는 transferId 확인 필요
D 미정산 누락 → 이미지급 같은 화면 [이미지급(기록만)] 안 뜸 — 이체가 없으므로 —
E 가맹점 상세 → 수동 이체 운영이 금액을 직접 입력해 실행 선정산 제외액 transferId

질문에 대한 답

Q. 배치 때 제외액으로 잡혀 바로지급하는 것과, 나중에 돈이 들어온 뒤 바로이체하는 것은 다른가?

다른 처리다. 둘 다 DIRECT_PAYOUT 배치를 만들지만 트리거와 금액 기준이 다르다.

  • B(배치 중)는 어드민에 버튼이 없다. 배치가 돌면서 스스로 분류한다. 운영이 누를 수 있는 화면이 아니다.
  • C(나중에)는 운영이 ‘미정산 누락 추적’에서 건을 골라 누르는 수동 행위다. 그리고 선정산 수수료를 떼지 않는다 — 화면 안내 문구가 “이틀 이상 지난 건은 선정산이 아니라 카드/배달 수수료만 제외한 순지급액 전액을 그대로 이체합니다”이다.

따라서 “선정산 때 제외액이 떠서 우리가 바로지급을 누른다”고 하신 그 행위는 실제로는 C 경로다. B에는 누를 버튼 자체가 없다.

Q. 나중에 들어온 걸 줄 때는 수동이체인가?

아니다. 미정산 누락 추적의 [바로이체] 버튼이다(C). 수동이체(E)는 완전히 다른 물건으로, 어떤 매출 건을 지급하는지 시스템이 모른다. 보내는 값이 금액·적요·중복방지키뿐이고 거래일도 원장 연결도 없다.

// 수동이체가 서버로 보내는 전부
{ amount, memo, idempotencyKey }   // 날짜 없음, 거래 선택 없음

Q. 전자만 제외액이 찍히고, 나중에 준 건 안 찍히나?

둘 다 찍힌다. B·C·E 모두 선정산 제외액으로 뜬다. 안 뜨는 것은 D(이미지급)뿐이고, 그 이유는 “제외 대상이라서”가 아니라 실제 이체가 일어나지 않아 입금 자체가 없기 때문이다. 계좌 입금 내역은 실제 입금 목록이다.

어드민과 가맹점 화면이 서로 다르게 센다

이미지급은 어드민 제외액 집계에는 포함되는데 가맹점 화면에는 안 뜬다. 어드민 선정산 결과 탭의 제외액 카드는 “바로이체 N건 / 이미지급 N건”으로 분해해 보여주지만, 가맹점 앱에는 이미지급 행이 없다. 이 비대칭은 의도된 현재 상태이며, 8/15 회의에서 “이미지급도 가맹점 제외 상세에 노출한다”는 결정이 이미 내려져 있으나 아직 코드에 반영되지 않았다. 이번 QA에서는 “안 뜨는 것”이 정상이다.

합산 행은 어떻게 묶이나

상세 화면에서 여러 건이 한 줄로 접히고 날짜가 2026.06.05~06.16처럼 범위로 표기되는 행을 합산 행이라 한다. 정의는 “원장 없는 지급분”이고, 금액은 입금 총액 − 거래 원장이 붙은 항목의 합이다.

질문답근거
무엇을 기준으로 합쳐지나상세 화면 자체가 payout 1건 또는 transfer 1건 단위. 하루 단위도 이체 실행 단위도 아니다.확정
날짜 범위는 무엇의 최소·최대그 합산 행에 묶인 지급분의 첫 거래일 ~ 마지막 거래일. 다만 어떤 집합의 min/max인지는 코드에 없다.확인 필요
바로이체 건과 수동이체 건이 한 행으로 합쳐지나합쳐지지 않는다. 입금 행 하나는 payoutId나 transferId 중 하나만 갖고, 수동이체는 payout이 아예 없다. 은행 이체도 별건이라 입금 행이 2개가 된다.확정
미리보기의 ‘이체 횟수’와 ‘처리 건수’가 다른 이유3층 구조다. 처리 건수 = 고른 거래 수, 거래일 N일치 = 원장 배치 수, 이체 횟수 = 가맹점 수. 여러 날짜를 골라도 가맹점당 이체는 1회로 합산되고 원장만 거래일별로 쪼개 기록된다.확정

결함 후보 2건 — QA에서 확인할 것

  • 수동이체인데 화면에 “바로이체”로 보인다. 합산 행의 승인번호 자리에 들어가는 값이 “바로이체” 고정으로 정의돼 있고, 프론트는 그 값을 그대로 출력한다. 운영이 수동 이체한 건인데 가맹점에는 “바로이체”로 보일 수 있다.
  • 수동이체 건의 적요가 화면에서 빠졌다. 이번 브랜치 마지막 커밋이 적요 노출을 되돌렸다. 가맹점은 “페이허그 / 시각 / 금액 / 선정산 제외액”만 보고 왜 들어온 돈인지 알 수 없다. 의도된 것인지 확인이 필요하다.

03테스트 데이터 만들기

DEV에 하루치 데이터밖에 없어도 된다. 어드민 단건 등록에서 거래일자를 과거로 직접 지정할 수 있다.

날짜 범위 합산 행은 바로이체로만 만들 수 있다

수동이체는 요청에 날짜 필드가 없어 언제나 단일 행이다. 2026.06.05~06.16 같은 범위 표기를 보려면 반드시 미정산 누락 추적에서 여러 날짜를 함께 골라 바로이체해야 한다.

  1. 과거 날짜 매출을 3일치 넣는다

    어드민 → 가맹점 → 매출 조회 → 가맹점 클릭 → [단건 등록]

    거래일자가 제약 없는 날짜 입력이다. 과거 날짜를 자유롭게 넣을 수 있고 카드 승인·카드 매입·배달 3개 탭 모두 지원한다. 카드 매입 탭은 매입일자·지급예정일까지 따로 지정된다.

    배달 탭으로 서로 다른 과거 날짜 3일에 1건씩 등록한다. 배달 건이 있어야 이번 수정의 핵심(주문번호·플랫폼 차감액 표기)을 확인할 수 있다.

    금액은 매번 다르게 넣는다. 나중에 화면에서 어느 건인지 구분하기 쉽다.

  2. 미정산 누락 목록에 뜨는지 확인한다

    어드민 → 정산 → 정산 현황 → 선정산 결과 탭 → [미정산 누락 추적] 패널 펼치기

    방금 등록한 건이 목록에 나오는지 본다. 나오면 “해당일 정산완료 − 누락” 표식이 붙는다.

    확인 필요 수기 등록 건이 자동으로 누락 대상이 되는지는 백엔드 판정이라 코드로 알 수 없다. 안 뜨면 7번 항목의 질문을 개발에 던진다. 어드민에 배치를 수동으로 돌리는 버튼은 없다.

  3. 1일치만 골라 바로이체 — 단일 날짜 케이스

    한 날짜의 건만 체크한다. [미리보기]를 먼저 눌러 실제 이체 횟수 1회 / 거래일 1일치인지 확인한다. 미리보기는 실제 이체도 기록도 남기지 않는 안전한 조회다.

    확인 후 [바로이체] 실행. 가맹점 앱에서 날짜가 하나만 찍히는 행이 나와야 한다.

  4. 2일치 → 3일치로 반복 — 날짜 범위 케이스

    선택 로직이 날짜 경계를 무시한다. 목록이 가맹점→날짜→거래 3단으로 보이지만 체크 상태는 평면이라 여러 날짜를 한 번에 고르는 것이 기본 동작이다.

    미리보기 모달에 이렇게 뜬다.

    거래일 2일치 (3건)를 합산하여 1회 이체 · 원장은 거래일별로 기록

    여기서 며칠치인지 실행 전에 검증된다. 가맹점 앱에서 2026.MM.DD~MM.DD 범위 표기가 나와야 한다.

  5. 이미지급을 1건 만든다 — 안 뜨는 것을 확인하기 위해

    같은 패널에서 다른 건을 골라 [이미지급(기록만)]을 실행한다. 실제 이체 없이 원장에만 기록된다.

    이 건이 가맹점 앱 목록에 나타나지 않아야 한다. 만들지 않으면 “안 뜬다”를 검증할 수 없다 — 원래 없어서 안 보이는 것과 구분이 안 되기 때문이다.

  6. 수동이체를 1건 실행한다

    어드민 → 가맹점 → 가맹점 관리 → 가맹점 클릭 → 우상단 [수동 이체]

    금액과 적요(선택, 20바이트)를 넣고 2단계 확인을 거쳐 실행한다. 사이드바에서 바로 갈 수 없고 반드시 가맹점 상세를 경유한다.

    같은 금액으로 두 번 실행하면 1건으로 처리된다

    금액을 바꾸지 않으면 중복방지키가 재사용된다. 여러 건을 만들려면 금액을 매번 다르게 넣어야 한다.

04어드민에서 대상 찾기

이미 제외액이 발생한 가맹점을 찾아야 할 때. 전용 필터 화면은 없어서 엑셀 후처리가 유일한 방법이다.

찾는 것경로읽는 방법
제외액 있는 가맹점
1순위		 정산 → 정산 현황 → 선정산 결과 탭 제외액 카드에 바로이체 N건 / 이미지급 N건 분해 표시. 제외액 있는 가맹점은 빨간 글씨. [엑셀]의 ‘선정산요약’ 시트에 가맹점명·선정산제외액·바로이체·이미지급 컬럼이 분리돼 나온다.
바로이체·이미지급 실행일 정산 → 정산 현황 → 정산 상세 탭 배치마다 바로이체 / 이미지급 배지. 엑셀 ‘정산방식’ 컬럼으로 필터.
수동이체 실행일 정산 → 정산 현황 → 이체 내역 탭 구분 컬럼이 수동 지급인 행. 시간 컬럼이 실행 일시.
거래 1건 단위 상태 가맹점 → 매출 조회 → 가맹점 클릭 이체상태 컬럼과, 정산상태 셀 바로 아래 붙는 배지(선정산 / 바로이체 / 이미지급)를 함께 본다.

이체 내역 탭으로 바로이체를 찾으면 안 된다

구분 배지가 지급 회수 수동 지급 3종뿐이라 정상 선정산 지급과 바로이체가 모두 ‘지급’으로 뭉개진다. 바로이체는 정산 상세 탭의 배지로만 판별된다. 반대로 수동이체는 이 탭에서만 잡힌다.

제외액 전용 필터 화면은 없다

제외액은 늘 기간·일자 단위 집계 안에서만 보이고 “제외액 있는 가맹점만” 거르는 필터 UI가 없다. 이체상태·정산상태 드롭다운 필터도 어느 화면에도 없다. 대상을 추리려면 엑셀을 받아 거르는 수밖에 없다.

06화면으로 판정 못 하는 것

아래 항목은 눈으로 봐서는 맞는지 알 수 없다. 개발자도구 Network 탭에서 응답을 직접 봐야 한다.

항목왜 못 하나대신 이렇게
이미지급 미표시 프론트에 거르는 코드가 한 줄도 없다. 안 보이는 게 서버가 뺀 건지 원래 데이터가 없는 건지 구분 불가. 이미지급 건을 일부러 만든 뒤, account 응답 JSON에 그 건이 없음을 직접 확인.
라벨이 2종뿐 서버 문자열을 그대로 찍는다. 화면에 2종만 보인 건 그 계정 데이터가 2종뿐이었다는 뜻일 수 있다. 응답의 label 값들을 눈으로 훑는다.
상단 총액 일치 서로 다른 API의 다른 필드라 우연히 맞을 수도 있다. 목록의 amount와 상세의 totalAmount를 쌍으로 비교. 11건 이상인 건에서.
10개 페이징 요청에 개수 파라미터가 없어 프론트는 몇 개인지 모른다. 응답의 hasMore와 items.length를 함께 본다.
배달 표기 수정 salesSource가 없으면 카드로 폴백한다. 응답에 그 필드가 있는지 먼저 본다. 없으면 판정 자체를 보류.
수동이체 진입 서버가 transferId를 실어야 밑줄이 생긴다. 응답에 transferId가 있는지 확인. null이면 밑줄이 안 생기는 게 코드상 정상.
여러 날짜 바로이체 진입키 이체는 1회인데 원장은 N개라, 어느 키로 들어가는지 코드로 결정되지 않는다. payoutId·transferId 중 무엇이 채워졌는지 기록하고 두 URL을 모두 열어본다.

07개발자 질문

QA 착수 전에 답이 있어야 하는 것들. 그대로 복사해 쓸 수 있게 문장으로 적었다.

착수 전에 반드시

  1. DEV 백엔드에 salesSource·residual·dateFrom/dateTo·transferId 응답 필드가 이미 배포돼 있나요? 프론트는 구버전 응답이면 카드로 폴백하도록 짜여 있어서, 백엔드가 안 올라갔으면 배달 건이 “카드 수수료”·“승인번호”로 잘못 표기돼도 정상처럼 보입니다.
  2. QA 기간 동안 payhug-merchant-web의 develop에 push하지 말아주세요. 지금 DEV는 feature/excluded-payout-delivery-manual-transfer가 수동 배포된 상태라, develop push가 있으면 QA 대상 코드가 덮어써집니다.
  3. “DEV의 수동이체는 실제 송금 없이 성공 처리”가 바로이체(action:"TRANSFER")에도 적용되나요? 날짜 범위 합산 행을 만들려면 바로이체를 여러 번 실행해야 하는데, 확인창에 “실제 이체합니다”라고 돼 있어 확인이 필요합니다.
  4. 어드민 ‘단건 등록’으로 과거 거래일자를 지정해 매출을 넣으면 그 건이 자동으로 ‘미정산 누락 추적’ 목록에 뜨나요? 어드민에 정산 배치를 수동 실행하는 버튼이 없는데, DEV에서 배치를 강제로 돌리려면 어떻게 해야 하나요?

동작 확정용

  1. 미정산 누락 추적에서 여러 거래일의 건을 한 번에 선택해 바로이체를 실행하면, 가맹점 입금내역 그 행의 payoutId와 transferId는 각각 무엇으로 채워집니까? 거래일이 2일 이상이면 payoutId가 null이 되고 transferId만 채워집니까, 아니면 대표 payout 1건의 id가 들어갑니까?
  2. 합산 행의 dateFrom/dateTo는 무엇의 최소·최대입니까 — 그 이체에 묶인 payout들의 대상일입니까, 원장의 거래일입니까? 합산 행은 payout/transfer 1건당 항상 1행입니까?
  3. 이미지급(action:"RECORD_ONLY")으로 처리한 건은 가맹점 입금내역 응답에서 아예 빠집니까? 빠진다면 필터 조건이 “이체 레코드가 있는 payout만”입니까, “payout 상태가 RECORD_ONLY가 아닌 것”입니까?
  4. 가맹점 상세의 수동 이체 건은 거래와 연결이 없는데, 상세 응답의 dateFrom/dateTo와 approvalNo는 무엇으로 채워집니까? approvalNo가 수동이체에서도 “바로이체”로 내려갑니까?
  5. 일반 선정산 배치가 도는 중 자동으로 바로이체 배치가 만들어지는 조건은 무엇입니까? 이 경우도 미정산 누락 바로이체처럼 선정산 수수료를 떼지 않고 순지급액 전액을 이체합니까?
  6. 수동이체 건의 적요를 화면에서 제거한 것이 최종 결정인가요? 지금은 가맹점이 “페이허그 / 시각 / 금액 / 선정산 제외액”만 보게 되어 왜 들어온 돈인지 알 수 없습니다.
