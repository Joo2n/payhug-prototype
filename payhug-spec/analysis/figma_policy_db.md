## 0. 한 줄 요약

이번 판독의 최대 성과는 **`figma_01_선정산시스템.md` §141/§172가 "확인 필요"로 남겨둔 D+1 vs D+2 충돌을 해소할 직접 근거를 찾은 것**이다.
정산채권DB에서 **`지급예상일`과 `입금일`이 동일 값이고 `입금액`이 `액면금액`과 같다** → `지급예상일`은 *가맹점 선정산 지급일이 아니라* **카드사 → 선정산 전용계좌 입금 예정일**이다.
따라서 계약서 "매일"(선정산 지급) vs DB "D+2"(카드사 정산)는 **충돌이 아니라 서로 다른 두 날짜**다. (강한 가설 — 필드 설명문 자체는 여전히 부재)

## 1. 정산채권DB (node 529:2950)

### 1.1 필드 구성

`가맹점ID(MID)` · `거래일자` · `카드사` · `정산채권ID` · `통화` · `액면금액` · `과소예상액면금액` · `보정후액면금액` · **`지급예상일`** · [수익권자] `투자자ID`/`할인율`/`양수가액`/`과소양수가액`/`보정후양수가액` · [페이허그] `IID`/`할인율`/`양수가액`/`분배액`/`과소양수가액`/`과소분배액` · [재양수인·재재양수인] 동일 구조 · [채권매입업체] `AID`/`할인율`/`선정산액`/`분배액` · `상환부족액` · **`입금일`** · `입금액`

정산채권ID 채번 규칙: `M0006542025-09-01농협NH카드` = **가맹점ID + 거래일자 + 카드사명** 결합.

### 1.2 일자 필드 — `지급예상일` (확정)

**산정 규칙: 거래일자의 익익영업일 (D+2 영업일)**. 크롭 확대로 23개 행 전수 검증:

| 거래일자 | 요일 | 지급예상일 | 검증 |
|---|---|---|---|
| 2025-09-01 | 월 | 9/3/25 (수) | D+2 |
| 2025-09-02 | 화 | 9/4/25 (목) | D+2 |
| 2025-09-03 | 수 | 9/5/25 (금) | D+2 |
| 2025-09-04 | 목 | 9/8/25 (월) | 토·일 스킵 |
| 2025-09-05 | 금 | 9/9/25 (화) | 토·일 스킵 |
| 2025-09-06 | 토 | 9/9/25 (화) | +1영업일=9/8, +2=9/9 |
| 2025-09-07 | 일 | 9/9/25 (화) | 동일 |
| 2025-09-08 | 월 | 9/10/25 (수) | D+2 |
| 2025-09-09 | 화 | 9/11/25 (목) | D+2 |

→ **달력일 D+2가 아니라 영업일 D+2**. 주말 거래는 익주 화요일로 밀린다.

### 1.3 `지급예상일`의 정체 (강한 가설 — 이번 판독의 핵심 발견)

근거 3가지:
1. 요약 테이블 1행: `지급예상일 20250903` / `입금일 20250903` — **두 값이 같다**.
2. `입금액 49,500` = `액면금액 49,500` — 입금되는 금액이 선정산액(49,005)이 아니라 **액면금액 전액**이다.
3. `액면금액 49,500` = 매출채권DB의 `지급금액(A-B-C)` 49,500 = **카드사가 가맹점에 지급할 금액**.

→ `지급예상일`은 **카드사가 선정산 전용계좌에 액면금액을 입금하는 날**이다. 페이허그가 가맹점에 선정산금을 지급하는 날이 아니다.

> `확인 필요`: 필드 설명문(description)이 DB 정의 어디에도 없어 라벨만으로는 구분 불가. **필드명을 `카드사입금예정일`로 개칭하거나 설명문을 명기해야 한다.** 현재 이름(`지급예상일`)은 가맹점 지급일로 오독되기 쉽고, 실제로 기존 분석에서 D+1/D+2 충돌로 오인됐다.

### 1.4 용어 함정 — `지급예상일` vs `지급예정일`

두 DB가 **다른 라벨**을 쓴다:
- 정산채권DB → `지급예상**일**` (예상 = 서버 연산 추정치)
- 매출채권DB → `지급예정**일**` (예정 = 여신협회 매입내역 스크래핑 원본값)

동일 개념인지 의도적 구분인지 불명. `확인 필요`.

### 1.5 상태값 — **없음** (중대 공백)

**정산채권DB에는 status 성격의 필드가 하나도 없다.** 지급상태·회수상태·채권상태 어느 것도 없다.
`상환부족액`(숫자)이 유일하게 상태를 유추할 수 있는 필드이나, 이것은 금액이지 상태가 아니다.

→ 02 §5의 지급 상태 11종 / 회수 상태 9종을 구동할 필드가 존재하지 않는다. (기존 분석 §115와 동일 결론, 재확인)

### 1.6 금액 체인 (확정)

1행 예시 — 액면금액 49,500 기준:

| 단계 | 주체 | ID | 할인율 | 금액 | 마진 |
|---|---|---|---|---|---|
| 가맹점 수취 | 채권매입업체 | A0001 | 0.00% | 선정산액 **49,005** | 분배액 322 |
| ↑ | 페이허그 | I000001 | 0.35% | 양수가액 49,327 | 분배액 119 |
| ↑ | 수익권자(투자자) | I000003 | 0.11% | 양수가액 49,446 | 54 |
| 최종 회수 | (카드사 입금) | — | — | 입금액 **49,500** | — |

- **선정산액 = 액면금액 × 0.99** (정확히 1.00% 할인). 3개 행 교차 검증: 49,500→49,005 / 29,700→29,403 / 39,600→39,204 / 108,900→107,811 모두 일치.
- 마진 분배 합계: 322 + 119 + 54 = **495 = 액면금액의 1.00%** ✓
- `선정산액`은 **보정후액면금액이 아니라 원본 액면금액** 기준으로 계산된다 (108,975이 아닌 108,900 × 0.99 = 107,811).

> `확인 필요`: 표기된 `할인율` 0.35%(페이허그) / 0.11%(투자자)와 실제 `분배액`(119 / 54)이 정합하지 않는다. 0.11% × 49,500 = 54.45 ≈ 54 ✓ 이지만, 0.35% × 49,446 = 173 ≠ 119. 할인율이 기간(D+2~입금일) 환산인지, 표기 오류인지 불명.

## 2. 매출채권DB (node 529:2199)

### 2.1 3단 구조

1. **쿠콘 서버 / 여신협회서버 승인내역 스크래핑** — `No.` `구분` `거래일자` `거래시간` `카드사` `제휴카드사` `카드번호` `승인번호` `승인금액` `할부기간`
2. **쿠콘 서버 / 여신협회서버 매입내역 스크래핑** — `거래일자` `매입일자` `카드사` `카드번호` `승인번호` `카드종류` `매입금액(A)` `가맹점수수료` `수수료포인트` `수수료포인트룰` `기타수수료` `수수료합계(B)` `부가세대리납부금액(C)` **`지급금액(A-B-C)`** **`지급예정일`** `MPM OR결제여부`
3. **서버 연산** — `예상수수료율` `예상부가세대리납부금액율` `수수료합계 예상액` `부가세대리납부금액 예상액` `지급예상액` / `미매입승인금액` `미매입지급예상액` **`매입상태`** `지급예정액` `잔액` `실현수수료율` `실현부가세대리납부금액율` / [예상오차] `과다예상수수료합계액` `과다예상부가세대리납부금액` `과소예상지급예정액`

### 2.2 상태값 (확정)

| 필드 | 값 | 의미 |
|---|---|---|
| `매입상태` | **`매입완료`** / **`미매입`** | 승인 건에 대응하는 매입내역 수신 여부 |
| `매핑` (1/0) | `1` = 승인↔매입 매칭됨 / `0` = 미매칭 | 승인내역·매입내역 좌우 연결 플래그 |
| `구분` (승인내역) | `승인` / `취소` | 원거래 vs 취소거래 |

**`미매입` 행의 데이터 형태** (확정, 실제 판독):
- 승인 160,000 (No.49, 우리카드) → 매입내역 없음, 매핑 0, `매입상태 = 미매입`, `미매입승인금액 160,000`, `미매입지급예정액 158,400`, `과소예상지급예정액 -158,400`
- 같은 카드번호·승인번호로 24초 뒤 `취소 -160,000` (No.50) → 역시 매핑 0 / 미매입
- No.71 KB카드 140,000 (노랑 하이라이트) → 미매입, `미매입지급예정액 138,600`

→ **미매입지급예정액 = 승인금액 × 0.99** (158,400 = 160,000 × 0.99). 미매입 건도 예상액은 산출되나 `지급예정액`은 0.

### 2.3 일자 필드 (확정)

| 필드 | 산정 규칙 | 검증 |
|---|---|---|
| `거래일자` `거래시간` | 승인 시각 원본 | 2025-09-01 10:46:10 등 |
| `매입일자` | **거래일자 + 1영업일** | 09-01→09-02, 09-05(금)→09-08(월), 09-11→09-12 |
| `지급예정일` | **매입일자 + 1영업일 = 거래일자 + 2영업일** | 09-01→20250903, 09-11→20250912, 09-12(금)→20250915(월), 09-13(토)→20250916 |

→ **정산채권DB `지급예상일`과 동일한 D+2 영업일 규칙**. 두 DB 교차 일치. 이 규칙은 **여신협회 매입내역 스크래핑 원본에서 오는 값**이지 페이허그가 정한 값이 아니다.

### 2.4 수수료율 — 예상 vs 실현 (확정)

| 구분 | 값 |
|---|---|
| `예상수수료율` | **1.00% 일괄** (모든 행 동일) |
| `실현수수료율` | 신용카드 **1.00%** / 체크카드 **0.75%** |
| `예상부가세대리납부금액율` | 0.00% |

실측 검증: 50,000 신용 → 가맹점수수료 500 (1.00%) / 40,000 체크 → 300 (0.75%) / 150,000 체크 → 1,125 (0.75%) / 230,000 체크 → 1,725 (0.75%) / 95,000 신용 → 950 (1.00%)

### 2.5 프레임 내 빨간색 미해결 메모 (원문 그대로)

> - 계산처리 방식 정리 필요
> - 승인내역 = 매입내역이 일치 여부 대사 검증 필요
> - 배달앱 쿠폰, 포인트 사용분은 어떻게 계산 처리할 건지
> - 수신전, 수신후 ??
> - 예상 오차 금액은 어떻게 할건지
> - **체크카드 수수료율이 신용카드 수수료율보다 작은데, 승인내역에서는 체크카드여부가 없기에 일괄 신용카드수수료율을 적용하기에 체크카드 결제시 불가피하게 발생**

→ 마지막 항목이 `과소예상지급예정액`의 **구조적 발생 원인**이다. 승인 시점엔 신용/체크 구분 불가 → 1.00%로 과다 차감 예상 → 실제는 0.75% → 가맹점 실입금이 예상보다 **많아진다**. 이건 오류가 아니라 설계상 불가피.

## 3. 회원DB_가맹점 (node 503:158)

### 3.2 일자 필드

### 3.3 카드수수료율 — 가맹점별 · 카드사별 상이 (확정, C1 직결)

- **"시스템에서 자동 산출하기에 입력할 필요 없음"**
- 부가세대리납부세율도 동일 방식(Z열 ÷ T열)으로 갱신

### 3.4 기타 필드

## 5. 충돌 · 불일치

### C-DB-1 (해소 근거 발견) — 지급 캘린더 D+1 vs D+2

- `03_정산로직` §5: "전일 매출 기준 … 다음날 오전 11시 30분 지급" (D+1)
- 정산채권DB `지급예상일` = 거래일 익익영업일 (D+2 영업일)
- **해소 근거**: 정산채권DB에서 `지급예상일` == `입금일` && `입금액` == `액면금액`(카드사 지급금액 A-B-C)
- **결론**: D+2는 **카드사 → 전용계좌 입금일**, D+1(11:30)은 **페이허그 → 가맹점 선정산 지급일**. **서로 다른 두 날짜이며 충돌이 아니다.**
- 잔여 리스크: 필드 설명문이 없어 라벨만으로는 여전히 오독 가능. `figma_01` §141/§172의 (a)/(b) 중 **(b)로 확정 제안**.

### C-DB-2 — 카드수수료율 1.00% 일괄 vs 가맹점별 0.15~1.80%

- 매출채권DB `예상수수료율` = **1.00% 고정**
- 회원DB `카드수수료율` = 가맹점별·카드사별 **0.15% ~ 1.80%**
- 회원DB 주석은 "실제 매입내역에서 자동 산출해 주기 갱신"이라고 명시 → 그렇다면 매출채권DB 예상 계산도 회원DB 값을 참조해야 하는데, 예시 데이터는 전부 1.00% 하드코딩
- **M00010(KB 1.80%)의 경우 예상수수료가 실제의 절반 수준으로 과소 계상**된다 → 예상 지급액이 실제보다 크게 표시 → 가맹점 오해 유발
- `확인 필요`: 1.00%가 예시용 더미인지, 실제 로직인지.

### C-DB-3 — 카드 가맹점수수료 1%와 선정산 할인 1%가 둘 다 "1%"

- 매출채권DB: 매출 50,000 → 카드 가맹점수수료 500 (1.00%) → `지급금액(A-B-C)` 49,500
- 정산채권DB: 액면금액 49,500 → 선정산 할인 495 (1.00%) → `선정산액` 49,005
- **완전히 다른 두 수수료가 우연히 같은 1%**. 문서·상담에서 혼동 위험이 매우 높다.
- 가맹점 실수령률: 50,000 → 49,005 = **총 1.99% 차감**
- C1(수수료율 병존) 레지스터에 **"1%가 두 종류"라는 항목을 추가**해야 한다.

### C-DB-4 — 페이허그 할인율 0.35%의 근거 부재

- 정산채권DB 페이허그 `할인율 0.35%` 표기. 그러나 계약DB에는 투자자 매입수수료 0.11%만 있고 0.35% 근거 계약이 없다.
- 게다가 0.35% × 49,446 = 173 ≠ 실제 `분배액` 119. **표기 요율과 실제 분배액이 불일치.**
- `확인 필요`. 근거 없이 0.35%를 채택하지 말 것.

### C-DB-5 — 상태값 체계 전면 부재

- 02 §5 지급 상태 11종 / 회수 상태 9종 → **대응 필드가 어느 DB에도 없음**
- 존재하는 상태: `매입상태`(2값) / `계약상태`(1값만 정의) / `선정산 실적여부`(2값) / `전용계좌로 변경`(2값) / `영업상태`(3값) — 총 5개, 전부 회원DB·매출채권DB 소속
- **정산채권DB(= 실제 지급·회수가 일어나는 테이블)에 상태 필드가 0개**
- 05 §6의 가맹점 화면 문구 8종을 구동할 수 없다.

### C-DB-6 — 계약DB 내부 불일치
