회원관리에서 계약 체인과 수수료 정책을 연결해
등록·조회할 수 있는 구조
현재는 정산상품을 별도로 생성하고 회원관리에서 회원을 등록하지만, 회원 화면에서는 직속 상위만 선택할 수 있어
전체 계약 관계와 각 단계의 수수료율을 확인하기 어렵다. 이번 개편의 핵심은
회원 유형에 따라 필요한 직속 상위만 선택하게 하고, 나머지 계약 체인은 자동으로 구성하며,
기존 정산상품 정책을 실제 회원 계약에 연결하여 전체 구조를 조회할 수 있게 만드는 것이다.

0핵심 결론
이 작업은 단순히 회원등록 모달에 상위 회원 + 수수료율 필드를 2개 추가하는 수준이 아니다.

화면 책임 한 문장
정산상품 관리 = 계약·수수료 정책을 정의하는 화면 /
회원관리 = 회원과 직속 상위 관계를 설정하고, 해당 정책을 적용하여 실제 계약 체인을 구성·조회하는 화면
1개념을 3개로 분리
현재 구조에서는 서로 다른 개념이 한 화면에서 섞여 보일 수 있으므로 개발 전에 다음 세 가지를 명확히 분리한다.
구분 | 의미 | 예
회원 유형 | 이 계정이 무엇인지 | 파트너 / 영업조직 / 영업 / 제휴사
계약 관계 | 누구 밑에 누구인지 | A파트너 → B파트너 → C영업조직 → D영업
정산 정책 | 계약에서 어떤 수수료를 적용하는지 | 채권매입 1%, 시스템료 0.3%, 이체료 등
상위파트너 / 하위파트너의 정의
현재 회원관리에는 파트너라는 유형이 있고, 정산상품 관리에서는 상위파트너 / 하위파트너라는 역할이 등장한다.
같은 파트너가 계약에 따라 상위가 될 수도 있고 하위가 될 수도 있다면 다음처럼 분리하는 것이 적절하다.
회원 유형 = 파트너 / 계약 역할 = 상위파트너 · 하위파트너
반대로 사업 정책상 “한 번 상위파트너이면 항상 상위파트너”라는 것이 확실하다면 회원 유형 자체를 분리할 수도 있다.
이 부분은 구현 전에 정책 확정이 필요하다.

4직속 상위 회원 선택
기존의 상위 회원은 의미가 모호하므로 직속 상위 회원으로 명확하게 바꾸는 것을 추천한다.
그리고 선택 대상은 전체 회원이 아니라 등록 대상의 유형에 따라 제한한다.
등록 대상 | 선택 가능한 직속 상위
영업 | 영업조직
영업조직 | 하위파트너
하위파트너 역할 | 상위파트너
상위파트너 역할 | 페이허그 또는 최상위
회원 수가 늘어나면 현재처럼 긴 단순 select는 사용성이 급격히 떨어진다.
회원명 / ID 검색이 가능한 검색형 Select로 구현하는 것이 적절하다.
5직속 상위를 선택하면 전체 계약 체인을 자동 구성
신규 영업 D를 등록하면서 직속 상위로 C 영업조직을 선택했다고 가정한다.
C가 이미 아래 계약구조 안에 있다면 사용자가 A와 B를 다시 선택하게 만들면 안 된다.
기존 C의 체인
A 상위파트너
└ B 하위파트너
└ C 영업조직
D 등록 후 자동 구성
A 상위파트너
└ B 하위파트너
└ C 영업조직
└ D 신규 영업
UX 원칙: 사용자는 직속 상위 1명만 선택하고, 전체 상위 체인은 시스템이 따라 올라가서 구성한다.
6정산상품 / 계약요율 선택
회원등록 화면에서 수수료를 직접 숫자로 다시 입력시키는 방식은 추천하지 않는다.
기존 정산 상품 관리에 이미 계약 참여자, 채권매입, 시스템이용료, 이체수수료, VAT,
납부 주체, 수취 주체 등의 정책이 존재하기 때문이다.
비추천
회원에서 수수료 직접 입력

12데이터 구조: 회원에 계약 정보를 전부 박지 않기
Claude Code를 돌릴 때 가장 먼저 기존 DB 구조를 확인해야 한다.
단순히 회원 테이블에 부모회원, 수수료율, 정산상품ID를 전부 저장하면 계약 변경 이력 관리가 어려워질 수 있다.

회원과 계약관계를 분리하여 변경 이력을 관리하기 쉬움.
A파트너 소속 → B파트너 소속으로 변경하거나, 수수료가 0.5% → 0.4%로 변경되는 케이스가 발생할 수 있다.
회원 데이터 자체를 덮어쓰면 과거 계약 이력이 사라진다.
따라서 기존 백엔드에 계약/관계 테이블이 있는지 먼저 탐색해야 한다.

19Claude Code 탐색 순서
기존 화면과 로직을 재활용하는 전제로 아래 순서로 코드베이스를 탐색시키는 것이 안전하다.
기존 회원관리 컴포넌트 — 목록, 등록/수정 모달, 프로필/상세 구조 확인
회원 유형/상위회원 필터링 로직 — 현재 parent/member 관계 API 확인
정산상품 관리 컴포넌트 및 API — 참여자, 요율, VAT, 납부/수취 옵션 구조 확인
계약/관계 데이터 모델 — 별도 contract/member_relation 테이블 존재 여부 확인
정산 계산 로직 — 실제 요율을 어떤 원장에서 가져오는지 확인
추천코드 / URL 생성 로직 — 체인 변경 시 영향 여부 확인
기존 UI 재사용 가능 요소 — 검색 Select, 요율 테이블, 상세 View, Tree/Breadcrumb
예외 케이스 검증 — 비활성 회원, 다중 상품, 이력 보존, Skip Level 등
Claude Code에 최종적으로 확인시킬 핵심 질문
“현재 코드베이스에서 회원, 상위회원 관계, 정산상품, 수수료 정책, 추천코드/URL 생성이 각각 어떤 모델과 API에 연결되어 있는지 추적하고,
가장 적은 변경으로 ‘직속 상위 선택 → 상위 체인 자동 구성 → 정산상품 적용 → 계약구조 Preview/조회’를 구현할 수 있는 재사용 경로를 제안하라.”
회원관리 계약 체인 구조 개편안 · 기존 회원관리 및 정산상품 관리 로직 재사용을 전제로 한 1차 설계 문서
