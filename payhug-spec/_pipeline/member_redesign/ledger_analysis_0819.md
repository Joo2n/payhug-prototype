### 1-2. 제시 정책 요약 (검산 대상) [가설 — 채택 제안 상태]

1. 건별 매출·수수료·VAT = 소수 **7째 자리에서 사사오입 → 6자리** 저장.
2. 일별 원장 = 건별 6자리 값 **합산**(추가 반올림 없음, 6자리 유지).
3. 월별 원장(신설) = 6자리 값 합산 후 **정수화**.
4. 표시: 페이허그 관리자 = 6자리, 총판 어드민 = 정수.

### 1-3. 최대 오차 상한 검산

기호: 참값 `x`, 건별 저장값 `x̂ = round₆(x)`, 건별 오차 `ε = x̂ − x`.

- **건별**: 7째 자리 사사오입이므로 `|ε| ≤ 0.5×10⁻⁶ = 5×10⁻⁷원`.
- **일별 원장**: `D̂ = Σ x̂ᵢ` (일 내 n_일 건). 6자리 소수의 합은 10진 연산에서 정확(새 반올림 없음)하므로
  `|D̂ − D| ≤ n_일 × 5×10⁻⁷원`.
- **월별 원장**: `M̂ = round₀(Σ_월 x̂ᵢ)` (월 n건). 정수화가 더하는 오차 ≤ 0.5원이므로

  ```
  |M̂ − M| ≤ n × 5×10⁻⁷ + 0.5  (원)
  ```

- **"최대 1원" 성립 조건**:

  ```
  n × 5×10⁻⁷ + 0.5 ≤ 1  ⇔  n ≤ 0.5 / (5×10⁻⁷) = 1,000,000
  ```

  → **월 100만 건까지 "월별 원장 오차 ≤ 1원"이 성립**한다(31일 기준 일평균 약 32,258건). n = 100만에서 상한이 정확히 1.0원이며, 이는 모든 건의 반올림 오차가 같은 방향으로 최대치일 때만 도달하는 이론상 최악치다(실제로는 오차가 상쇄되어 훨씬 작다). [확정 — 수식 검산]

- **단서 1 · 집계 셀 단위**: 위 n은 "월별 원장 한 칸(셀)에 합산되는 건수"다. 참여자별·수수료 항목별로 셀이 쪼개지면 각 셀의 n은 작아져 여유가 커지고, 전사 합계 셀이 n 최대가 된다.
- **단서 2 · 반올림 1회 원칙**: 한 셀 값이 건별로 **각각 독립 반올림된 k개 필드의 합**(예: 수수료와 VAT를 따로 6자리 반올림한 뒤 합산)이면 건당 오차 예산이 k×5×10⁻⁷으로 늘어 조건이 `n ≤ 1,000,000 / k`로 줄어든다. 파생 필드(순수익 등)는 **반올림된 구성요소로부터 계산**해 항등식(예: 순수익 = 수익 − 부가세)이 자릿수 그대로 성립하게 하고, 원천 반올림 지점은 필드당 1곳으로 명시할 것. [가설 — 권고]

### 1-4. 총판 정수 '표시값' 재합산 금지 [핵심 주의]

총판 화면의 건별 정수 표시값 `round₀(x̂ᵢ)`는 건당 최대 **0.5원**의 표시 오차를 갖는다. 이 표시값을 n건 다시 합산하면

```
|Σ round₀(x̂ᵢ) − Σ x̂ᵢ| ≤ 0.5 × n
```

— 20건만 합쳐도 최대 10원이 벌어진다. 따라서 **모든 합계(일·월·엑셀 포함)는 반드시 6자리 원본으로 합산한 뒤 마지막에 1회만 정수화**해야 한다. 그 결과 총판 화면에서는 "행의 정수 표시값을 눈으로 더한 값 ≠ 합계 표시값"이 자연 발생한다(괴리 최대 ±(0.5n + 0.5)원). 이는 오류가 아니므로 화면 각주로 안내한다.

- 각주 문안(안): *"각 행은 원 단위로 반올림해 표시되므로, 행의 합과 합계 표시값이 수 원 이내에서 다를 수 있습니다. 합계는 원본 금액(소수 6자리) 기준으로 계산됩니다."*
- 현행 프론트 합산 관행(원본값 reduce → 마지막 포맷, §1-1)은 이 원칙과 이미 일치 — **유지**하되, 6자리 원본이 응답에 실려야 성립한다.

### 1-5. 구현상 주의 [가설 — 권고]

- **이진 부동소수점은 10진 6자리를 정확히 담지 못한다**(0.1 문제). 저장·합산은 **마이크로원 정수(원×10⁶) 또는 DECIMAL(p,6)** 를 권고. 마이크로원 정수라면 §1-3의 "합산 정확" 전제가 표현 수준에서 보장된다.
- JS `Number` 안전 정수 한계는 2⁵³ ≈ 9.0×10¹⁵ 마이크로원 ≈ **셀당 약 90억 원** — 월 전사 합계 셀이 이를 넘볼 수 있으면 합계는 서버 계산(BigInt/DECIMAL)으로 내리고 프론트는 표시만 할 것.
- 표시 분기: 총판과 페이허그가 **같은 컴포넌트**를 쓰므로(§전제 용어) 6자리/정수 표시는 `isAdmin` 분기(현행 `app/settlement/overview/page.tsx:39~42` 패턴)로 처리 가능. 현행 `fmt()`(정수 고정)는 페이허그 시점용 6자리 포맷터 추가가 필요하다.

## 3. R3 — 가맹점 파트너·담당자 선택 (수동/자동 현황 + 체인 자동 유도 제안)

### 3-1. 현행 확인 [확정 — 코드]

가맹점에는 성격이 다른 **세 축의 사람 필드**가 있고, 자동/수동이 각각 다르다.

| 필드 | 성격 | 입력 방식 | 근거 |
|---|---|---|---|
| 담당자 `assignedUserId` | 운영 담당 | **어드민 수동 지정만** — 목록 "담당" 컬럼 클릭 → 모달 select(`app/manage/page.tsx:107~125, 439~485`), 상세에도 동일 UI(`app/merchants/[id]/page.tsx:853~880`). `PUT /admin/merchants/{id}/assign` `{assigneeId}`(`services/merchantService.ts:47~49`). **가입 시 자동 세팅 경로 없음**(가맹점 웹에 관련 코드 0건) | 확정 |

| 소개 파트너 `referredByPartnerId` | 계약서 파트너 체인·직인 생성 근거(코드 주석 원문) | **가입 시 URL 코드 자동 + 어드민 수동 재지정**. 가입: 가맹점 웹이 URL 쿼리(`partnerCode` 등)를 sessionStorage에 담아 `/auth/signup`에 자동 첨부(`payhug-merchant-web/app/signup/page.tsx:70~84, 263~274`). 어드민: select+적용(`app/merchants/[id]/page.tsx:804~847`), `PUT /admin/merchants/{id}/assign-partner` `{partnerId}`(`merchantService.ts:58~60`), 응답 `needsResign`으로 승인된 계약의 **재서명 필요** 안내. | 투자자 `referredByInvestorId` | 유동화기관 매칭 | 소개 파트너와 동일 패턴(가입 코드 자동 + 어드민 수동, 승인 후 잠금) + `noInvestor` 체크(:881~931) | 확정 |

### 3-2. 관계 모델 전환 시 제안 — 담당 영업 선택 → 체인 자동 유도 [가설 — 제안]

1. **입력은 "담당 영업" 1개 필드로 수렴**: 가맹점 등록·상세에서 담당 영업(체인 최하단 회원) 1명만 선택한다. 가입 링크로 들어온 경우 추천코드가 그 시작점을 자동 세팅(#10a 확정)하고, 어드민은 수동 보정만 한다 — 현행 소개 파트너의 이중 구조를 그대로 계승.
2. **체인은 저장하지 않고 파생**: 담당 영업 선택 시 서버가 관계(Edge) parent 재귀로 체인을 조회해 "상위파트너 ~ 영업 + 각 구간 요율(예시 표기)" 미리보기를 띄운다. 저장은 담당 영업 ID 하나. `orgRootUserId` 파생 패턴의 일반화다.
3. **계약 성립 시점 스냅샷은 별도**: 표시용 파생 체인과 달리, 계약이 성립되는 순간의 체인·요율은 정산 근거로 **스냅샷 고정**되어야 한다(관계가 나중에 바뀌어도 기존 계약 계산이 흔들리지 않게 — Q8 이력 확정과 한 몸). 스냅샷 저장 위치는 서버 설계 몫.
4. **재서명 연동**: 담당 영업(=체인) 변경 시 현행 `needsResign` 흐름(§3-1)이 그대로 필요하다 — 체인 변경은 계약서 내용 변경이므로.
5. **소개 파트너 필드와의 통합 여부 = 확인 필요**: 현행 소개 파트너는 "계약서 체인·직인 근거", 담당자는 "운영 담당"으로 역할이 다르다. 관계 모델의 담당 영업이 소개 파트너를 흡수하는지(1필드), 운영 담당(`assignedUserId`)은 별도 유지인지 결정이 필요하다. 임의 통합 금지.
6. **DAOU·제휴 채널 분리 유지**: 현행처럼 병렬 트랙 가맹점은 담당 영업 지정을 차단하고 제휴사·대리점 코드 축으로 관리(M1·M2 — 병렬 트랙에 '파트너'·'최상위' 용어 사용 금지).

## 4. Q7 — 비활성 상위의 배분 동결 설계 (경고 + 동결 확정 방향의 후속)

전제: 원장 기록 자체는 계속 남긴다(M7 — "다 기록하면 됨"). 동결은 **지급 정지**이지 기록 중단이 아니다. 또 동결분은 6대 개념(미지급금·미회수금 등) 어느 것과도 병합하지 않고 **"배분 보류액"(가칭) 신규 개념**으로 별도 정의한다. 현행 배분 상태 배지는 이체완료·이체대기·이체실패·부채상계(DEBT_OFFSET)·기록용(RECORD_ONLY) 5종(`BatchDetailTab.tsx:23~29`) — 여기에 상태를 추가하는 방식이 최소 변경이다.

### 6-2. 폐기 vs 재정의 [가설 — 비교]

## 7. R6 — 관계 요율 전환의 정산 현황·원장 반영 경로

전제(확정): 전환 확정(Q2ⓐ) + 병행 방식(Q2ⓑ — 신규 계약 = 관계, 기존 = 상품, 정산상품관리 메뉴 당분간 유지) + 거래유형별 요율 2세트(Q1). 과거 이력 재계산 여부는 미결(Q2ⓒ — 병행 방식상 기존 이력은 상품 기준 유지가 기본 상태).

반영 경로 — 단계 서술:

1. **관계 저장**: 회원관리에서 관계(Edge) 생성 — 직속 상위 1명 + 요율 세트(카드/배달 각 1벌, 값은 예시 표기) + 유효 기간. 상위 변경은 종료일 기록 후 새 관계 생성(Q5·Q8 확정). 프론트 현행에는 이 모델이 전무하므로(`services/partnerService.ts:17` — `parentUserId` 스칼라뿐) 관계 CRUD API 신설이 전제.
2. **가맹점-체인 연결**: 가맹점의 담당 영업 지정(가입 추천코드 자동 + 어드민 수동 보정 — §3). 체인은 담당 영업의 parent 관계 재귀로 파생.
3. **rate source 마킹**: 신규 계약 성립 시 해당 가맹점(또는 계약)에 "요율 출처 = 관계"를 마킹하고, 그 시점의 체인·요율을 계약 스냅샷으로 고정(§3-2-3). 기존 가맹점은 상품 배정(`Assignment`, `types/settlement.ts:20~27`) 유지.
4. **배치 계산(전량 서버)**: 배치 생성 시 가맹점의 rate source를 판정 — 관계면 체인 Edge 요율로 참여자별 수수료·VAT를 건별 계산(R1 자릿수 정책 적용 지점), 상품이면 현행 로직. 프론트는 계산에 관여하지 않음(§1-1 확정)이므로 **이 단계는 전부 서버 작업**이다.
5. **원장 적재**: 계산 결과를 배분(payout)·원장(ledger) 행으로 적재 — 참여자(payee)+역할(role) 단위 행 구조(`types/settlement.ts:75~92`)는 재사용 가능. 제안: 각 행에 **요율 출처(상품/관계)와 적용 관계 ID를 스탬프** — 병행 기간의 감사·R2 체인 검색·Q7 동결 판정이 전부 이 스탬프에 의존한다.
6. **정산 현황 표시**: 정산 상세 탭의 배치 → 배분·원장 조회 경로(`batches/{id}/payouts`·`/ledgers`)와 엑셀 3시트는 그대로 동작 — 표시 role 라벨(UPPER/LOWER/SALES…, `app/settlement/overview/page.tsx:171~178`)을 관계 기반 행에도 유지할지가 서버 role 체계 결정에 달려 있음. [확인 필요]
7. **계산서 발행**: 계산서 탭 집계(가맹점×발행주체×항목)가 관계 기반 원장 행도 동일 스키마로 합산하는지 확인 필요. 과세/면세 판정은 M4의 조건부 규칙(계약 사슬 등장 여부)을 따르며 단정 표기 금지.
8. **시뮬레이션 전환**: 현행 입력이 `cardPolicyId`/`deliveryPolicyId`(`app/settlement/simulation/page.tsx:142~143`)이므로, 병행 기간에는 상품 선택 모드와 가맹점(관계) 기준 모드 2입력이 필요하다.

범위 명시: **관계 요율로 계산되는 것은 신규 계약(3단계에서 관계로 마킹된 가맹점)의 배치부터**다. 기존 가맹점·과거 배치는 상품 기준으로 남으며(동결과 동치), 재계산 실시 여부만 Q2ⓒ로 남아 있다.
