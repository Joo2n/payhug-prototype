REVISED CONTRACT-CHAIN ARCHITECTURE
정산상품을 없애고,
회원 간 연결 자체가 계약 구조가 되도록 변경
회원 등록 시 별도 정산상품을 선택하지 않는다. 회원 유형을 선택하면 시스템이 해당 유형의 직속 상위 유형을 자동 결정하고, 사용자는 그 유형에 해당하는 직속 상위 회원 1명과 상위-현재 회원 사이의 계약 수수료율만 지정한다. 모든 회원이 같은 방식으로 자신의 바로 위 관계만 등록하면 결과적으로 상위파트너 → 하위파트너 → 영업조직 → 영업의 하나의 계약 체인이 완성된다.
정산상품 선택 없음직속 상위 1명만 선택수수료는 관계(Edge)에 저장체인은 자동 연결전체 구조 조회 View
0이전 안에서 정정되는 핵심
이전 안회원 → 정산상품 선택 → 요율 적용
정산상품 관리에서 만든 정책을 회원에게 적용하는 구조.
→
수정안회원 → 직속 상위 선택 → 관계 수수료율 지정
정산상품이라는 중간 개념을 제거하고 회원 간 계약 관계 자체가 구조와 요율을 가진다.
삭제: 회원등록의 ‘적용 정산상품’, ‘정산상품 선택’, ‘정산상품에서 요율 자동 적용’ 개념.
추가: ‘직속 상위 회원’과 ‘상위-현재 회원 간 계약 수수료율’을 하나의 관계로 저장.
1핵심 설계 원칙
①현재 회원의 유형을 선택한다.
②직속 상위의 유형은 시스템이 결정한다.
③직속 상위 회원 + 수수료율을 선택한다.
④이 관계들이 연결되어 전체 계약 체인이 된다.
핵심: 사용자는 전체 체인을 직접 만들지 않는다. 자기 바로 위 관계 하나만 만든다. 전체 체인은 이미 등록된 각 회원의 parent 관계를 따라가며 시스템이 조합한다.
2데이터 개념도 다시 단순화
개념 | 무엇을 의미하는가 | 예
회원 | 실제 계정/사업 주체 | A파트너, B파트너, 투게더페이, 영업사원 D
회원 유형/계약 위치 | 체인에서 어느 단계인지 | 상위파트너 / 하위파트너 / 영업조직 / 영업
직속 상위 관계 | 현재 회원이 누구 바로 아래인지 | D의 parent = 투게더페이
계약 수수료율 | 직속 상위와 현재 회원 사이의 계약 관계 값 | 투게더페이 → D = 0.10%
정산상품은 더 이상 이 구조의 핵심 데이터 단위가 아니다.
3회원 유형에 따른 직속 상위 유형 자동 결정
등록하는 회원 | 시스템이 요구하는 직속 상위 | 사용자에게 보이는 UI
영업 | 영업조직 | 영업조직 회원만 검색/선택 가능한 드롭다운
영업조직 | 하위파트너 | 하위파트너에 해당하는 회원만 검색/선택
하위파트너 | 상위파트너 | 상위파트너 회원만 검색/선택
상위파트너 | 없음 | ‘최상위 회원’으로 표시하고 상위 선택 UI 비활성/숨김
현재 회원 유형 값이 단순히 ‘파트너’ 하나뿐이라면 정책 결정이 하나 필요하다.
시스템은 ‘파트너’를 선택한 것만으로는 이 회원이 상위파트너인지 하위파트너인지 알 수 없다. 기존 데이터에 이미 상/하위 역할을 판별하는 규칙이 없다면 파트너 선택 시 계약 위치: 상위파트너 / 하위파트너를 고르는 한 단계가 필요하다. 반대로 기존 로직에서 자동 판별할 수 있다면 그 로직을 재사용한다.

14검증 루프 1 — 요구사항 논리
정산상품 선택 없이 회원등록이 완결되는가 → YES
사용자는 자신의 직속 상위만 선택하는가 → YES
회원 유형에 따라 잘못된 상위 유형을 선택하지 못하게 할 수 있는가 → YES
수수료율이 어느 관계에 속하는지 명확한가 → YES, parent-child Edge에 저장
각자의 직속 관계를 연결해 전체 체인을 만들 수 있는가 → YES
전체 계약구조와 각 관계 수수료율을 조회할 수 있는가 → YES
1차 결론: 설명한 목적에는 정산상품이라는 별도 객체가 없어도 된다.
15검증 루프 2 — UX 논리
복잡한 방식상위파트너 → 하위파트너 → 영업조직 → 영업을 등록 화면에서 모두 직접 선택
기존 체인을 사용자가 다시 조립하게 됨.
권장 방식현재 유형 → 시스템이 직속 상위 유형 결정 → 직속 상위 한 명만 검색 → 수수료율 입력
입력량과 오류 가능성이 최소화됨.
등록 화면에서는 직속 관계를 편집하고, 전체 계약체인은 미리보기/조회용으로만 보여주는 것이 가장 단순하다.
16검증 루프 3 — 개발/정산 논리
현재 정산상품이 실제 정산 계산에서 어떤 방식으로 참조되는지 추적해야 한다.
정산상품을 삭제하면 기존 계산 로직의 rate source를 MemberContractRelation.contract_rate로 전환해야 한다.
기존 회원의 정산상품 데이터를 새 관계 데이터로 마이그레이션할 방법을 정의해야 한다.
한 회원에게 동시에 여러 상위 관계를 허용할지 확인해야 한다.
관계 변경 시 기존 수수료율 이력을 종료 처리할지 덮어쓸지 결정해야 한다.
정산 계산이 과거 날짜 기준 관계를 조회해야 한다면 effective_from / effective_to가 필요하다.
상위 변경 시 하위 체인의 계산 결과가 어디까지 영향을 받는지 확인해야 한다.
가장 중요한 개발 검증: 현재 ‘정산상품 관리’가 단순 UI인지, 실제 원장/정산 계산의 정책 소스인지 확인해야 한다. 후자라면 화면 삭제보다 먼저 데이터 참조 구조를 바꾸는 작업이 필요하다.

19Claude Code에 돌릴 분석/수정 지시
목표:
정산상품 관리라는 중간 구조를 제거하고 회원 간 parent-child 계약관계와 관계 수수료율로 계약 체인을 구성한다.
1. 현재 회원관리의 회원 유형, 상위회원 선택, 등록/수정/프로필 컴포넌트와 API를 추적한다.
2. 현재 ‘파트너’가 상위파트너/하위파트너로 어떻게 구분되는지 기존 로직과 데이터 모델에서 확인한다.
3. 회원 유형별 허용 직속 상위 유형 규칙을 찾아 재사용하거나 최소 변경으로 추가한다.
4. 현재 정산상품 관리가 실제 정산 계산에서 참조되는 위치를 모두 추적한다.
5. 수수료율을 상품 속성이 아니라 parent-child 계약관계 속성으로 옮길 수 있는 기존 테이블/모델이 있는지 확인한다.
6. 가능하면 기존 relation/contract 모델을 재사용하고, 없으면 MemberContractRelation 형태의 최소 모델을 제안한다.
7. 회원등록 UI는 유형 선택 → 직속 상위 유형 자동 결정 → 해당 유형 회원 검색 → 관계 수수료율 입력 → 전체 체인 Preview 순서로 구성한다.
8. 사용자가 전체 상위 체인을 직접 선택하지 않게 한다. 직속 상위 하나만 선택하고 나머지는 parent 관계를 따라 자동 조회한다.
9. 계약구조 View에서 수수료율은 회원 노드가 아니라 연결선(관계)에 표시한다.
10. 정산상품 관리 메뉴/라우트/API/DB 의존성을 분류하고, 바로 삭제 가능한 것과 계산 로직 전환 후 삭제할 것을 나눈다.
11. 기존 정산상품 데이터를 새 관계 수수료율로 마이그레이션해야 하는지 판단하고 이행안을 제안한다.
12. 비활성 상위, 상위 변경, 수수료 변경 이력, skip-level, 다중 상위, cycle 방지까지 검증한다.
