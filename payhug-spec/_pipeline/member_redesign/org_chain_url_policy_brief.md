## 1. 확정된 뼈대 — 지금 흔들리지 않는 것

개편안의 계약 체인 구조는 아래까지 확정 상태다.

- **폭포수 4단 표준 체인** — 상위파트너 → 하위파트너 → 영업조직 → 영업, 그 아래 가맹점. 유형을 고르면 직속 상위 유형이 1단 고정으로 자동 결정된다(영업→영업조직 / 영업조직→하위파트너 / 하위파트너→상위파트너 / 상위파트너→없음). **[확정]** [출처: `spec.md:14` §0 채택 구조 — 사용자 결정 2026-08-19]
- **요율은 관계(Edge) 속성** — 수수료율 세트는 회원이 아니라 상위-하위 관계 1건에 저장되고, 체인은 직속 상위 관계의 재귀 조회로 자동 조합된다. 관계 1건 = 카드/배달 요율 세트 2개(Q1). **[확정]** [출처: `spec.md` §0·§1, `decisions_0819.md` 콘솔 답변 Q1 — 2026-08-19 18:11]
- **파트너 상·하위 자동 판별** — 등록 시 직속 상위를 "없음"으로 두면 최상위(상위파트너), 상위를 고르면 하위파트너. 별도 위치 선택 단계 없음. **[확정]** [출처: `decisions_0819.md` #1 P5 — 사용자 답변 2026-08-19]
- **중간 단계 생략 허용(Q4)** — 유형 단계를 건너뛴 상위 연결을 허용하되 확인 다이얼로그를 거쳐 연결한다. 최상위 총판 단독 체인도 허용. **[확정]** [출처: `decisions_0819.md` 콘솔 답변 Q4, `states_catalog.md` D6·D7 — 확정 동작 정의, "확인 필요" 배지 없음]
- **활성 상위 1개 제한(Q5)** — 한 회원의 활성 상위 관계는 1개. 상위 변경은 탈퇴가 아니라 수정 경로(기존 관계 종료일 기록 → 새 관계 생성, Q8 이력 준용). **[확정]** [출처: `decisions_0819.md` 콘솔 답변 Q5·Q8]
- **순환 연결 차단** — 어떤 경우에도 차단. **[확정]** [출처: `decisions_0819.md` #8a]
- **병렬 배분은 별도 가지** — 다우데이타(제휴사 직계약)·투자자는 폭포수 바깥의 병렬 배분 트랙이다. 순차 하향이 아니라 각각 배분하며, 이 트랙에는 '최상위'·'파트너' 용어를 쓰지 않는다. 투자자는 선택적 — 미연결이면 배분 제외. **[확정(구조)]** — 단 배분율 실값은 충돌 C1로 미확정 유지. [출처: `decisions_0819.md` #2 P2·#4 P4·M1·M2 — 회의록 8.14 §1]
- **다중 '하위'는 원래 허용** — 데이터 모델이 상위 포인터 1개짜리 평면 트리라, 한 파트너 아래 복수 영업조직·병렬 체인은 구조상 제약이 없다(목 데이터에도 복수 조직 존재). 금지된 것은 다중 '상위'(Q5) 하나다. **[확정 — 코드·목 기준]** [출처: 슬랙 리포트 §5 첫 항목]

정리하면: **세로 방향(누가 누구 위에 서는가)은 "유형별 1단 고정 + 생략 허용 + 상위 1개 + 순환 금지"까지 확정**이고, 가로 방향(한 상위 밑에 몇 갈래가 퍼지는가)은 원래 제한이 없다. 남은 구멍은 "같은 유형이 세로로 겹칠 수 있는가"(§2·§3)다.

## 2. 영업조직 → 하위 영업조직 (동일 유형 적층) — 현재 상태: 정책 대기 (07 §7-14)

### 2-1. 왜 Q4 확정으로 끝난 문제가 아닌가

Q4는 중간 단계 **'생략'**(건너뛰기) 결정이지 동일 유형 **'적층'** 결정이 아니다. 표준 규칙은 "영업조직의 직속 상위 = 하위파트너" 1단 고정(`spec.md:14`)이라, 영업조직 밑에 영업조직이 오는 관계는 확정 규칙 어디에도 자리가 없다. 상태 카탈로그도 이 케이스에 상태 번호를 부여하지 않고 "정책 대기 케이스 — 상태 미부여"로 명시해 두었다. **[정책 대기]** [출처: `decisions_0819.md` 8/20 반영표 B3, `states_catalog.md` Flow I 말미, `07_OPEN_QUESTIONS.md` §7-14]

### 2-2. 그런데 실데이터가 이미 있다

메타(메타플레이) → 이로움의 동일 유형 다단이 실데이터로 존재한다. 프론트는 상위 지정에 유형·깊이 제약이 없어 화면상 몇 단이든 만들 수 있고, 서버가 막는지는 미확인이다(목 데이터의 최대 체인은 4단이며 조직 2중 적층 예시는 없음 — 실데이터가 테스트 범위 밖 케이스라는 뜻). 게다가 메타플레이 계정은 '영업' 유형 오등록 정황까지 겹쳐 있어(유형 정정 대기), 이 실데이터 자체의 유형 확인이 선행돼야 한다. **[확인 필요]** [출처: 슬랙 리포트 §1·§4 후보 4·§5, `decisions_0819.md` C1(슬랙)]

### 2-3. 허용으로 정하면 함께 움직여야 하는 것 3가지

1. **관계 재귀 파생의 '중간 조직 무유실' 명기** — 가입 링크(난수 URL)에는 최하위 회원 코드 1개만 실리므로, 중간 조직은 링크가 아니라 관계 데이터의 재귀 파생으로 체인에 복원돼야 한다. 이 "중간 조직 무유실 = 관계 재귀 파생" 요건을 난수 URL→체인 시작점 서버 매핑 규칙(원장 분석 문서의 해당 확인 질문 자리)에 명기해야 한다. [출처: `decisions_0819.md` B3, `ledger_analysis_0819.md:161`(가입 코드→체인 매핑 규칙 확인 질문), 슬랙 리포트 §5 셋째 항목("재구성 위임" 추정 — 서버 확인 필요)]
2. **배분 단계 가변화** — 체인 구간 수가 4단 고정이 아니게 되므로, 구간별 요율 차감 연쇄(§4)가 가변 단수를 전제해야 한다. 관계 재귀 파생 원리 자체는 단수와 무관하게 성립하나, 배분 역할 명명 체계가 조직 1단 전제라 재설계가 필요하다(§4-3). [출처: `ledger_analysis_0819.md` §7 R6 확인 질문 3]
3. **현행 정산상품 폼의 1단 한계** — 병행 기간(Q2ⓑ) 존치되는 정산상품 폼은 조직 참여자 슬롯이 1단 1개뿐이라 3단 조직 체인을 배분에 담지 못한다. 이 지점이 07 §7-11(체인 내 수수료 분리 배분 요구)의 배분 축 문제와 같은 자리에서 만난다. [출처: `07_OPEN_QUESTIONS.md` §7-14 ③·§7-11 연계, 코드 근거 admin `app/settlement/policies/PolicyFormModal.tsx:241-247`]

덧붙여 용어 삼중 충돌이 걸려 있다 — 화면 표기 '영업'에 두 유형이 섞이는 자리, 회원 유형 코드와 정산 배분 역할 코드가 같은 철자를 서로 다른 뜻('영업' vs '영업조직 몫')으로 쓰는 문제. 허용 결정 시 용어장에 화면 표기와 코드 상수를 갈라 적는 열이 필요하다. **[확인 필요 — 서버 협의]** [출처: `02_TERMS_AND_STATUS.md` §6 용어 충돌 3건, `decisions_0819.md` L4, 코드 근거 admin `app/settlement/policies/page.tsx:46` vs `:78`, `app/partners/page.tsx:699`]

### 2-4. "하위 영업조직 여러 개"는 따라오는가 — 판단

**판단: 적층이 허용되면 별도 결정 없이 구조상 따라온다.** 근거는 세 겹이다. ① 다중 '하위'는 폭포수에서 원래 허용이다 — 평면 트리 모델에 하위 수 제한이 없고, 한 파트너 아래 복수 조직이 이미 확정 구조다(§1). ② Q5의 제한은 '상위' 축(활성 상위 1개)이라, 한 조직 밑에 하위 조직이 여럿 달려도 각 하위가 상위 1개를 갖는 정상 형태여서 Q5와 충돌하지 않는다. ③ 적층 결정의 실체는 "영업조직의 직속 상위 유형으로 영업조직을 허용한다"는 관계 유형 규칙 1개이며, 그 규칙은 갈래 수를 제한하지 않는다. 또한 가맹점 1건의 배분 체인은 담당 영업에서 상위로 올라가는 단일 경로라 갈래가 늘어도 선형이 유지된다 — 배분 원리는 흔들리지 않는다. **[유력 — 문서·프론트 구조 기준 추론]** 단서: 서버가 하위 수·깊이 상한을 따로 두는지는 미확인이므로, 서버 규칙 회신과 함께 확정할 것. [출처: 슬랙 리포트 §5 첫 항목(확정)·둘째 항목(서버 확인 필요), `decisions_0819.md` Q5]

## 3. 영업 → 하위 영업 — 미정의

동일 유형 적층 논의는 전부 **영업조직** 축이다. 영업 밑에 영업이 오는 구조는 어느 근거 문서에도 정의·언급이 없다 — `spec.md`의 유형→직속 상위 규칙은 "영업→영업조직" 하나뿐이고, 07 §7-14·슬랙 리포트 §5·상태 카탈로그 모두 조직 적층만 다룬다. 프론트는 상위 지정 무제약이라 화면상 만들 수는 있으나 서버 규칙 미확인이며, 실데이터 사례 언급도 없다. **현재 상태 = 미정의 — 7-14와 같은 계열의 정책 질문**으로, 7-14를 확정할 때 "동일 유형 적층의 허용 범위가 영업조직 한정인가, 영업을 포함한 일반 규칙인가"를 한 문장으로 같이 정하는 것이 경제적이다. **[정책 대기 — 미정의]**

한 가지 혼동 주의: 정산 배분 역할에는 '상위영업'·'하위영업'이 이미 존재한다(02 §6 배분 역할 표). 그러나 이는 다우 상품에만 있는 **배분 슬롯 2단**이지, 회원관리 체인에서 영업→영업 관계를 허용한 근거가 아니다 — 배분 축의 낱말을 계층 정책의 근거로 오독하지 말 것. [출처: `02_TERMS_AND_STATUS.md` §6 정산 배분 역할 표, 슬랙 리포트 §5 넷째 항목("다우 상품만 상·하위영업 2단")]

## 4. 수익 배분 구조 — 다단이 끼면 계산이 어떻게 되는가

### 4-1. TO-BE 원리: 체인 재귀 → 구간별 요율 차감 연쇄 **[확정(경로) + 확인 필요(세부)]**

관계 요율 전환(Q2ⓐ 확정·Q2ⓑ 병행)의 원장 반영 경로는 이렇다. ① 회원관리에서 관계 생성(직속 상위 1명 + 카드/배달 요율 세트 + 유효 기간) → ② 가맹점에 담당 영업 지정(가입 추천코드 자동 + 어드민 수동 보정), 체인은 저장하지 않고 담당 영업의 상위 관계 재귀로 파생 → ③ 신규 계약에 "요율 출처 = 관계" 마킹 + 계약 성립 시점 체인·요율 스냅샷 고정 → ④ 배치 계산(전량 서버)에서 구간(Edge)별 요율로 참여자별 수수료·부가세를 건별 계산 → ⑤ 배분·원장 행 적재(요율 출처·적용 관계 표식 스탬프 제안). 폭포수에서는 상위→하위 순차 하향으로 각 구간이 차감 연쇄를 이루고, 참여자별 매출·원가가 구간마다 다르게 귀속된다(M3). [출처: `ledger_analysis_0819.md` §7 R6 1~5단계, `decisions_0819.md` M1·M3]

**다단 조직이 끼는 경우**: 이 원리 자체는 구간이 4개든 5개든 그대로 돈다 — 체인이 저장값이 아니라 재귀 파생이기 때문이다. 달라지는 것은 ① 배분 행 수(구간 수만큼 가변) ② 배분 역할 명명(현행 라벨 체계가 상위파트너/하위파트너/영업조직/영업의 고정 단수 전제 — 관계 기반 신규 체계로 갈지 확인 필요) ③ 스냅샷·이력의 구간 수 가변 수용이다. 즉 **다단 허용의 병목은 계산 원리가 아니라 역할 체계와 표시·폼 구조**다. **[확인 필요]** [출처: `ledger_analysis_0819.md` §7 R6 6단계·확인 질문 3]

### 4-2. 현행과의 격차: 정산상품 1단 슬롯

병행 기간의 기존 가맹점은 정산상품 기준으로 남는데, 상품 폼의 참여자 슬롯은 조직 1단 고정이라 다단 체인을 표현할 수 없다. 따라서 다단 적층이 허용돼도 **관계 기준으로 마킹된 신규 계약부터만** 다단 배분이 가능하고, 상품 기준 가맹점은 구조적으로 1단에 묶인다. 과거 이력 재계산 여부는 별도 미결(Q2ⓒ)이다. **[확정(병행 방식) + 정책 대기(재계산)]** [출처: `decisions_0819.md` 콘솔 답변 Q2ⓑ·Q2ⓒ, `ledger_analysis_0819.md` §7 범위 명시]

### 4-3. Q3·병렬 배분과의 관계

- **Q3(페이허그 계약율)**: 최상위 등록 화면에서 페이허그와의 계약율을 입력받는 것으로 확정 — 폭포수 맨 위 구간(페이허그↔최상위)의 요율이 이 입력이며, 차감 연쇄의 상단 마감점이 된다. 값은 C1 미확정 — 화면·문서에는 예시 표기만. **[확정(위치) + 값 미확정]** [출처: `decisions_0819.md` 콘솔 답변 Q3, `states_catalog.md` I2]
- **병렬 배분(다우·투자자)**: 폭포수 차감 연쇄 밖에서 각각 배분한다. 다단 적층 논의는 폭포수 내부 문제라 병렬 트랙과 직접 얽히지 않지만, 비활성 상위 배분 동결(Q7 — 경고+동결 확정, 동결분 처리 미결)을 병렬 트랙에도 적용하는지는 별도 확인 질문으로 남아 있다. **[확정(구조) + 확인 필요(동결 적용 범위)]** [출처: `decisions_0819.md` M1·Q7, `ledger_analysis_0819.md` §4 확인 질문 5]
- **07 §7-11(체인 내 가맹점 수수료 분리 배분)**: 상위 총판이 하위 가맹점 수수료를 나눠 갖는 요구 — 배분 축이 하나 더 생기는 문제로, 다단 적층과 같은 자리(폼 슬롯·배분 모델)에서 만난다. 요구사항 문서화 전. **[정책 대기]** [출처: `07_OPEN_QUESTIONS.md` §7-11·§7-14 연계]

## 5. 가입 링크(URL) 생성 정책의 현재 위치

### 5-1. 확정된 것

- **추천코드 = 체인 시작점** — 가입 URL의 추천코드는 가입 가맹점의 계약 파트너 체인 시작점이다. 링크로 가입하면 그 가맹점은 링크 소유 회원의 하위로 연결되고, 그 위 체인은 관계 재귀로 파생된다. 이것이 링크가 곧 "체인 시작점"이 되는 원리다. **[확정(개념)]** — 단 서버가 실제로 코드 소유자에서 상위로 체인을 재구성하는지는 추정 단계(상위 코드로 링크를 만들면 본인이 체인에서 빠진다는 사고 방지 이력이 방증). **[확인 필요(서버 동작)]** [출처: `decisions_0819.md` #10a, 슬랙 리포트 §5 셋째 항목, 코드 근거 admin `app/partners/page.tsx:694-695` 주석·커밋 `3fbc230`]
- **TO-BE = 회원별 난수 링크 자동 발급** — 회원 생성 시 추천코드·가입 링크를 난수로 자동 발급하고(계정 자동 생성 개정과 한 묶음: 아이디 = 기업 코드 4자+순번, 비밀번호 초기값 = 기업 코드 4자+휴대폰 뒷자리), 목록의 행 확장에서 한 줄 체인·관계 수수료율과 함께 확인·복사한다(R4·R5). 구 생성기(3드롭다운 조합)는 폐기 — 조합 선택 UI 자체가 소멸해 탭 필터 부수효과·선택값 잔존·라벨 혼합 이슈가 구조적으로 해소된다(A1). **[확정(개편안 채택)]** [출처: `decisions_0819.md` R4·R5·8/20 반영표 A1, `states_catalog.md` I5·I6, 슬랙 리포트 §6 ①~③]
- **참여자 시점 노출 범위 = 자기+하위 체인 한정** — 행 확장의 가입 링크·관계 요율은 자기와 하위 체인까지만 노출(상위 코드 노출 사고 재발 방지). **[확정(명문화)]** [출처: `decisions_0819.md` B1]

### 5-2. 대기 중인 것

- **발급 주체 정책 = 07 §7-12 대기.** 두 단이다. (a) 현행·병행 기간 — 운영 안내 "파트너 계정으로 URL 생성"이 유효한 정책인지 서버 요건·과거 동작에서 온 관행인지(코드상 파트너 코드는 필수가 아니며 영업 코드 단독 링크도 생성된다 — 슬랙 리포트가 "필수" 서술을 정정), 그리고 기배포 URL을 병행 기간에 유지하는가 차단하는가. (b) 개편 후 — "전 유형 자기 링크 자동 발급, 체인은 관계에서 파생"을 발급 정책으로 공식 채택하는가. **[정책 대기]** [출처: `07_OPEN_QUESTIONS.md` §7-12, `decisions_0819.md` B2, 슬랙 리포트 §3 정정 콜아웃]
- **전환기 중복 경로 우선순위** — 같은 가맹점이 기배포 코드 URL과 난수 링크 양쪽으로 유입될 때 체인 기준을 어느 쪽으로 잡는가. **[확인 필요]** [출처: 슬랙 리포트 §7 질문 12, 07 §7-12 영향 단락]
- **생성 권한표** — 유형×유형 생성 권한은 프론트 하드코딩 0건·전부 서버 위임이라 전 셀 확인 필요 상태의 권한표만 세워져 있고, 정책 선정의 여부 자체가 07 §7-13 대기다(선행 조건 = §7-10 체인 구조 개발 파악). **[정책 대기 + 확인 필요]** [출처: `decisions_0819.md` B4·§B4 권한표, `07_OPEN_QUESTIONS.md` §7-13·§7-10]

한 줄 요약: **링크의 좌표는 정해졌다(누구의 링크 = 그 회원이 체인 시작점, 노출은 자기+하위). 남은 것은 자격이다(누가 발급 주체인가 = 7-12, 누가 누구를 만들 수 있는가 = 7-13, 옛 링크를 언제까지 인정하는가 = 미결).**

## 6. 개발·정책 확인 질문 (이 주제 한정 5건)

1. **[7-14 · 개발+정책]** 영업조직 동일 유형 적층을 서버가 현재 허용하는가(깊이 상한·검증 규칙 포함), 그리고 메타플레이·이로움컴퍼니의 실제 회원 유형은 무엇인가 — 실데이터 확인 후 적층 허용 여부를 정책으로 확정. 확정 시 "허용 범위가 영업조직 한정인가, 영업 포함 일반 규칙인가"(§3)를 같은 문장에서 결정. [슬랙 리포트 §7 질문 9·10]
2. **[7-12(b) · 개발]** 난수 링크 가입 시 서버가 링크 소유 회원에서 상위로 관계 재귀 파생해 체인을 구성하는가 — 중간 조직 무유실이 보장되는가, 중간 조직이 배분에 포함되는가. [슬랙 리포트 §7 질문 7, `ledger_analysis_0819.md:161`]
3. **[7-12(a) · 정책]** 병행 기간 중 구 생성기·기배포 코드 URL의 유효성(유지/차단)과, 두 경로 중복 유입 시 체인 기준 우선순위. [`decisions_0819.md` A1, 슬랙 리포트 §7 질문 12]
4. **[7-13 · 개발→정책]** 로그인 유형별 등록 가능 유형 반환값 전체 매트릭스(§B4 권한표 전 셀) — 회신 수신 후 정책 선정의 vs 서버 추인 택일. [`decisions_0819.md` §B4, 슬랙 리포트 §7 질문 2·3]
5. **[7-14③·7-11 · 개발]** 다단 조직 체인의 배분 역할 체계 — 정산 배분 역할 코드가 '영업조직 몫'을 뜻하는 명명의 정리 가능 여부와, 가변 단수 체인을 배분·원장 행이 수용하는 모델. [`ledger_analysis_0819.md` §7 R6 질문 3, 슬랙 리포트 §7 질문 11, 02 §6]
