# 투자자 어드민 용어 — 값의 계보

대표 정의서(`ceo_definitions.md`, 2026-08-27 17:59 수신)에 나오는 용어 29건이 페이허그 어디서 오는지 추적한 결과.

조사 범위는 읽기뿐. `payhug-admin-web`·`payhug-investor-admin` 무변경, 커밋·push 0건.

---

## 0. 이 문서를 읽는 법

### 왜 필요한가

투자자 화면에 `투자실행액 1,523,100,000원` 같은 숫자가 뜬다. 그 숫자를 만들려면 **페이허그 어딘가에 그 재료가 이미 있어야 한다.** 없으면 새로 만들어야 하고, 그게 곧 개발 범위다.

이 문서는 용어 하나마다 "그 재료가 지금 어디 있는가"를 찍어 둔 지도다.

### 출처 구분 4종 — 뜻

| 표기 | 뜻 | 개발 관점 |
|---|---|---|
| **기존 어드민에 있음** | 지금 운영 중인 어드민 화면을 열면 그 값이 실제로 떠 있다 | 가져다 쓰면 됨 |
| **DB·로직에 있음** | 화면에는 안 보이지만 서버가 내려주는 응답 필드·정산 계산 과정에는 존재 | 화면만 만들면 됨 |
| **설계에만 있음** | Figma 기획서(정산채권DB 등)에 칸은 그려져 있으나 **운영 서버에 그 테이블이 있는지는 미확인** | 실물 유무부터 확인 |
| **투자자용 신설** | 페이허그 어디에도 없다 | 원천부터 새로 만들어야 함 |
| **확인필요** | 근거가 갈리거나 정의문 자체가 없음 | 결정 먼저, 개발은 그다음 |

`설계에만 있음`은 지시문의 `DB·로직에 있음`을 둘로 쪼갠 것. Figma 정산채권DB는 **기획 도면**이지 돌아가는 DB가 아니라서, 운영 응답 필드와 같은 칸에 두면 오독된다.

### 개발 용어 풀이

| 용어 | 비유 |
|---|---|
| **API 응답 필드** | 서버가 화면에 보내는 택배 상자 안의 물건 이름표. `netPayoutAmt` 같은 영문이 그것 |
| **타입 정의**(`types/settlement.ts`) | 그 택배에 뭐가 들었는지 미리 적어 둔 송장 양식 |
| **프론트에서 계산** | 화면 쪽에서 더하기 빼기를 함. 서버는 재료만 주고 조립은 화면이 함 |
| **백엔드가 내려줌** | 서버가 이미 다 계산해서 완성품을 보냄. 화면은 받아서 그리기만 함 |
| **원장(Ledger)** | 누가 얼마 벌고 얼마 썼는지 참여자별로 적은 장부 |
| **배치(Batch)** | 하루치 정산을 한 덩어리로 묶어 처리하는 단위. "8월 24일 매출분 김밥나라 정산 묶음" 같은 것 |
| **폭포수 배분** | 수수료가 하위→상위로 물 떨어지듯 단계별로 나뉘는 구조 |

| **쓰임** | ① `선정산 수수료 = 채권매입 + 시스템 이용료 + 이체 수수료`(`app/page.tsx:213`) ② 이해관계자 5인에게 폭포수 배분 ③ 계산서 발행 시 **면세** 대상(시스템·이체는 과세, `TaxInvoiceTab.tsx:161`) |

#### 요율 체계에서 어느 것을 가리키는가 — 조사 결과

**채권매입수수료(MARGIN)는 단일 요율이 아니라 5명이 나눠 갖는 통(pot)이다.**

정책 화면의 요율 행 템플릿(`app/settlement/policies/page.tsx:107-118`):

```
MARGIN × INVESTOR   (투자자)
MARGIN × PAYHUG     (페이허그)
MARGIN × UPPER      (상위파트너)
MARGIN × LOWER      (하위파트너)
MARGIN × SALES      (영업조직)
SYSTEM_FEE × PAYHUG / UPPER / LOWER
TRANSFER_FEE × PAYHUG
```

매출조회 화면의 수수료율 분해 툴팁(`app/sales/[bizNo]/page.tsx:1193-1235`)이 이 구조를 실제 숫자로 보여준다:

```
투자자          investorRate %
페이허그         (payhugMargin + payhugSystemFee) %
  └ 마진         payhugMargin %
  └ 시스템이용료   payhugSystemFee %
상위총판         partnerRate %      (0보다 클 때만 노출)
하위총판         subPartnerRate %   (0보다 클 때만 노출)
영업사원         salesRepRate %
─────────────────────────
합계            preSettlementRate %
```

타입 정의는 `hooks/usePurchaseLedger.ts:19-27`(`FeeBreakdown`).

**판정**

| 물음 | 답 | 근거 |
|---|---|---|
| 대표 정의서의 `채권매입수수료`가 투자자 몫만인가, 전체인가 | **확인필요** | 대표 정의서에 채권매입수수료의 정의문·기준금액·요율이 없음(`ceo_definitions.md` 전문 확인). `ceo_impact.md:312-329`가 Q-1으로 이미 등재 |
| 어드민에서 "투자자 몫"에 해당하는 값 | `investorRate`(요율) / `Payout.margin` 중 `role === "INVESTOR"` 행(금액) | `app/sales/[bizNo]/page.tsx:1196-1197`, `types/settlement.ts:44-57` |
| 상위 1% / 하위 1% / 페이허그 0.25% / 투자자 0.11%라는 숫자 | **운영 코드에 없음.** `0.25`·`0.11` 리터럴 0건. 값은 전부 DB `PolicyRate` 레코드에서 내려옴 | `policies/page.tsx:166` `GET /admin/settlement/policies` |
| 그 숫자의 출처 | Figma 계산식 노드 503:2 — `채권매입수수료율 1% / 0.25% / 0.11%`. 요율설정표는 `투자자(vat면제) 0.11%` | `payhug-spec/analysis/figma_policy_fee.md:142·272` |

> **C1(수수료율) 미확정 유지.** 위 숫자는 Figma 설계 문서 인용이고, 같은 문서 안에서도 기준금액 표기가 `지급예정액`/`매출액`/`원본 결제 대금` 3종으로 갈린다(`figma_policy_fee.md:121`). 시스템이용료도 0.3% vs 0.1%로 3배 차이(`:187`). 어느 값도 채택하지 않는다.

> **면세/과세 갈림** — 채권매입수수료는 면세, 시스템이용료·이체수수료는 과세. 투자자 배분액에 VAT가 붙는지가 여기서 갈린다(`TaxInvoiceTab.tsx:161`, `figma_policy_fee.md:186`).

### 1-3. 미지급금 · 과지급금

| 필드 | 내용 |
|---|---|
| **용어** | 미지급금 / 과지급금 |
| **출처 구분** | **기존 어드민에 있음** — 어드민 정산 로직에 이미 있는 개념 |
| **실제 소재** | **미지급금** = 미정산 누락 도메인. `MissedSettlementsData.totalAmount`(`types/settlement.ts:651`) · `totalNetPayoutAmt`(`:645`) · `netPayoutAmt`(`:635`·`:624`), 조회 `GET /admin/settlement/missed-settlements`(`hooks/useSettlementOverview.ts:349`). **과지급금** = 단일 필드 없음. 발생 원인 두 갈래 — 취소 환수 `CANCEL_CLAWBACK`(`types/settlement.ts:525`, 금액은 `AdjustmentCategorySummary.pendingAmount` `:533` 필터) · 현장결제 중복 수령 `offlinePendingTotal`(`hooks/usePurchaseLedger.ts:108`) |
| **기존 어드민 표기** | 미지급금 — 화면 라벨 `미지급`(`PreSettlementTab.tsx:1269`), 엑셀 헤더 `미지급액`(`:385`). 과지급금 — `취소 환수`(`PreSettlementTab.tsx:108`) · `미회수(다음 배치)`(`app/sales/[bizNo]/page.tsx:729`) |
| **계산 위치** | 미지급금은 값이 그대로 있다. 과지급금은 두 갈래를 합치는 식이 필요하다 |
| **재료** | 둘 다 실재. 없는 것은 **채권 1건 단위로 귀속시키는 경로**(N-1·N-2) |
| **쓰임** | 상환액 SB, 투자수익 M, S입금부족율 SLi 세 산식의 차감항 |
| **투자자 화면** | 미등장. 상환액·투자수익을 깎는 항과 S입금부족율의 분자로만 |

#### 6대 개념의 그것과 같은가 다른가 — 판정

**판정: 같은 개념이다. 등급 확정.**

| 축 | 정책서 6대 개념 | 대표 정의서 |
|---|---|---|
| **미지급금** | "원래 가맹점에게 지급해야 했으나 실제 지급되지 않은 금액"(`02_TERMS_AND_STATUS.md:47-56`). 방향 = **페이허그 → 가맹점** | **같다.** 선정산으로 가맹점에 지급해야 하는데 못 준 금액 |
| **과지급** | "PayHug가 가맹점에게 실제 지급해야 할 금액보다 더 지급한 발생 금액"(`02_TERMS_AND_STATUS.md:102`). 방향 = 페이허그가 가맹점에 초과 지급 → 가맹점에서 회수 | **같다.** 가맹점에 더 나간 금액 |

**같다고 보는 근거 3가지**

1. **정의문이 일치한다.** 02 §2·§4의 문장과 뜻이 같다. 방향도 주체도 같다.

2. **어드민에 실물이 있다.** 미지급금은 미정산 누락 도메인이 그대로다 — 화면 배너가 "정산 배치가 완료된 날짜에 뒤늦게 도착하여 선정산 처리가 누락된 건"이라고 정의문을 달고 있고(`PreSettlementTab.tsx:1197`), 해소 액션이 `바로이체`·`이미지급(기록만)`이라 미지급 상태임이 분명하다(`:1214`·`:1221`). 과지급금은 취소 환수와 현장결제 중복 수령 두 갈래로 잡혀 있다.

3. **종전 판정은 역산 추정이었다.** 정의문이 없어 산식 위치(`상환액 = 순지급액 − max(0, …)`)에서 방향을 **플랫폼 → 락계좌**로 되짚었는데, 그 추정이 틀렸다. 산식은 성립한다 — 투자자가 산 채권 중 가맹점에 아직 지급되지 않았거나 더 지급된 몫만큼 상환·수익이 조정되는 구조다.

**남은 것 — 정의가 아니라 귀속 단위**

- 두 값 다 지금은 **가맹점·배치·날짜 축**에 붙어 있다. 대표 산식은 **정산금채권 1건 축**을 요구한다. 옮기는 경로가 N-1(채권 객체)·N-2(채권 단위 대사)다.
- 계약 용어(`과정산금`·`미정산금`)와의 매핑은 **미확정 유지**. 계약 정의는 "정산주체(플랫폼)별 초과·부족 입금"(`analysis/archive_02_계약약관.md:91-92`)이라 주체가 플랫폼이고, 운영 6개념은 주체가 페이허그다. 근거 없이 잇지 않는다.

**⚠ 미회수금과 합치지 않는다**

`carryForwardTotal`(`types/settlement.ts:290`)·`carryForwardAmt`(`:390`)는 "당일 이체액으로 차액을 전부 회수하지 못해 다음 날로 이월된 금액"(`app/settlements/[id]/fee-adjustments/page.tsx:239-241`)으로, 02 §4가 가르는 `과지급`(발생 원인·최초 금액) / `미회수금`(현재 남은 회수 잔액) 중 **뒤쪽**이다. 과지급금 산정에 끌어다 쓰면 같은 돈을 두 번 센다.

### 1-4. 날짜 3종 — 선정산일 · 정산예정일 · 매출일자

```

   transactionDt                Batch.closedAt(날짜부)            payoutDt
   = Batch.targetDate           = settlementDate
   화면 "거래일" / "매출일"      화면 "정산일"                    화면 "지급일(카드사/플랫폼)"
                                                                   "지급예정일" / "입금예정일"
   = 대표의 매출일자             = 대표의 선정산일                 = 대표의 정산예정일
```

#### 정산예정일이 "반쪽"인 이유 3가지

1. **선정산 도메인에 없다.** `payoutDt`가 달린 타입은 `LedgerItem`(매출조회 원장)과 `MissedTransaction`(미정산 누락 건) 둘뿐. `Batch`·`PreSettlementMerchant`·`PreSettlementTransaction`에는 없다. 정산현황 화면 데이터만으로는 정산예정일을 알 수 없고 매출조회 원장을 따로 붙여야 한다.

2. **배달플랫폼 쪽은 입력 경로조차 없다.** 수기 매출 입력 모달(`components/sales/ManualSalesModal.tsx:230-242`)의 `지급예정일` 인풋은 카드 매입 탭 안에만 있다. 배달 탭에는 날짜 필드가 없다. 스크래핑 원본 근거도 여신협회 카드 매입내역만 확인됐다. **배달 정산예정일이 실제로 채워지는지는 백엔드 확인 필요.**

3. **산정 캘린더가 미확정으로 등재돼 있다.** `payhug-spec/spec/admin/02_매출조회.md:89` — `D+1/D+2/매일 중 어느 기준인지 미확정 → C2`.

#### C2(지급 캘린더)와 어떻게 얽히는가

C2 원문(`analysis/00_종합.md:19-22`):
- 운영 확정 — 전일 매출을 익일 오전 11:30·오후 6시, 하루 2회, 주말·공휴일 포함 매일 지급
- 문서 간 차이 — 양수도계약 제4조④ "매일" / Q&A "D+1 11:30~12:00" / 제안서 "365일" / **Figma 정산채권DB "지급예상일 = 익익영업일(D+2)"**

**얽히는 지점은 D+2 쪽이다.** `figma_policy_db.md:14-15`가 강한 가설로 해소해 뒀다 — 정산채권DB에서 `지급예상일`과 `입금일`이 같은 값이고 `입금액`이 액면금액과 같으므로, D+2는 **가맹점 지급일이 아니라 카드사 → 전용계좌 입금 예정일**이다. 즉 D+1(선정산 지급, `선정산일`)과 D+2(카드사 입금, `정산예정일`)는 충돌이 아니라 **서로 다른 두 날짜**.

이 해소가 사실이면 금융일수는 대체로 1~2일이 된다. 다만 필드 설명문이 없어 `확인필요` 등급 유지. **C2 미확정은 그대로 둔다.**

> **선정산일의 함정** — `closedAt`은 타임스탬프이고 지급이 하루 2회라 **같은 선정산일에 배치가 2개** 생긴다. 어드민은 `.substring(0,10)`으로 날짜 단위로 묶는다(`BatchDetailTab.tsx:87·346`). 채권 단위 금융일수를 셀 때 오전 배치와 오후 배치를 같은 날로 볼지 결정이 필요하다.

> **셈법 미확정** — 대표 정의서 원문의 금융일수 예시 2건이 서로 어긋난다. L19 `선정산일 260827, 정산예정일 260808 → 1`(끝점이 시작점보다 앞섬), L43 `20260824 → 20260826 → 2`(편면산입으로 계산 성립). `ceo_impact.md:331-336` Q-2로 등재. 편면/양편에 따라 W금융일수 `3.16667` vs `4.16667`, Ty수익율 `12.6789%` vs `9.636%`로 갈린다(`glossary_manuscript.md:135`).

### 1-6. 할인율

| 필드 | 내용 |
|---|---|
| **용어** | 유동화투자자의 할인율 (0.11% 예정) |
| **출처 구분** | **설계에만 있음** — 운영 어드민의 같은 이름은 **다른 것** |
| **실제 소재** | Figma 정산채권DB `529:2950`의 [수익권자] `할인율` 칸. 참여자별로 각각 존재 — 수익권자·페이허그·재양수인·재재양수인·채권매입업체 5주체에 `할인율`/`양수가액`/`분배액`이 붙는다(`analysis/figma_policy_db.md:1.1`). 요율설정표에 `투자자(vat면제) 0.11%`(`figma_policy_fee.md:272`) |
| **기존 어드민 표기** | **`할인율`이라는 낱말은 어드민에 딱 1곳** — `app/merchants/[id]/page.tsx:674` `(순지급 X원 x 할인율 Y%)`. 이건 **예상 매출 기반 정산 시의 리스크 할인**(`ForecastMerchant.discountRatePct`, `services/settlementService.ts:128`)이지 투자자 할인율이 아니다. 주말·스크래핑 장애로 실제 매출을 못 받았을 때 평균 매출로 추정 지급하며 깎는 비율 |
| **계산 위치** | 투자자 할인율 — 아직 아무데도 없음 / 예상정산 할인율 — 백엔드가 내려줌 |
| **재료** | 계약 조건. 재양도합의서 제8조 `채권매입수수료 / 산정 기준: 정산금채권 양수액 / 요율: ____%`(공란) |
| **쓰임** | `투자실행액 = 미회수 순지급액 합계 × (1 − 할인율)`, `Ai = 순지급액 × (1 − 할인율)`, `ty수익율 = 할인율 × (365 / w금융일수)` |
| **투자자 화면** | **열 헤더 아님.** 용어 안내 `<dd>` 안 산식 문자열로만 — `Ty수익율 : 할인율 × (365 / w금융일수)` (`invest-assets.html:374` 외 11개 화면 동일, `xls-profit-status.html:137` 엑셀 각주) |

> **C1 미확정 유지.** 대표 정의서는 `0.11% 예정`이라 적었으나, `예정`(값 확정·절차 미완)과 현행 화면의 `예시`(아무 값)는 층위가 다르다. `ceo_impact.md:366-374` Q-6이 등재. 값 채택 0건 유지.

> **할인율과 채권매입수수료율이 같은 값인지 미확정.** 산식을 맞추면 `r = 할인율 / (1 − 할인율) = 0.110121%`로 0.11%와 다른 값이 나온다(`ceo_impact.md:312-329` Q-1). 두 요율이 별개인지, 채권매입수수료의 기준금액이 양수액이 아니라 순지급액인지 회신 필요.
