## 화면 1. 정산 현황 — 차액 정산 탭

### ① 메뉴 위치·진입 경로
- **위치** — 사이드바 [정산] > 정산 현황(`/settlement/overview`)의 3번째 탭 "차액 정산". 탭 진입 시 최초 1회 자동 조회(OV page.tsx:176-178), 이후 조회 버튼·필터 변경으로 재조회.
- **총판 노출** — 노출됨 [확정]. 탭 버튼에 isAdmin 게이트가 없다(page.tsx:282-291). 총판(PARTNER/SALES_ORG/SALES/AFFILIATE/INVESTOR)은 정산 현황 6탭 중 선정산 결과·차액 정산·이체 내역 3탭을 본다.
- **API** — `GET /admin/settlement/fee-adjustment-dashboard?dateFrom&dateTo(&cardCorp&salesSource)` (HK:292-310). 총판 응답이 소속 가맹점으로 스코프되는지는 서버 소관 [확인 필요].

### ② 구성
- **필터열** — 공용 기간 필터 + 가맹점명·사업자번호 검색 + 에이전시 셀렉트. 이 탭에서만 "매출 유형(복수 선택)" 버튼 5종(전체/카드/배달의민족/요기요/쿠팡이츠, page.tsx:366-408)과, 카드 선택 시 2뎁스 "카드사(복수 선택)" 칩(page.tsx:413-453)이 추가된다. 카드사 옵션 목록은 서버가 필터 적용 전 전체 기준으로 내려준 `availableCardCorps`(HK:303) — 선택해도 옵션이 줄지 않는다.
- **매출 유형 툴팁** — "특정 매출 유형을 선택하면 원장과 연결된 건만 표시. 예상매출 대사처럼 원장 미연결 건은 전체에서만 확인" 고지(page.tsx:374-377) [확정].
- **정렬·엑셀** — 콘텐츠 최상단 우측: 거래일 정렬 토글(최신/오래된순) + 엑셀 다운로드(page.tsx:677-680).
- **KPI 카드** — 4열 그리드. ① 전체 차액(순액·전체 건수·대기 건수) + ② 서버 `summary.categories` 배열의 카테고리별 카드(순액·건수·대기 건수, page.tsx:683-720). 코드 주석은 "KPI 카드 4개"(:682)지만 카드 수는 1 + 카테고리 수로 서버 응답에 따라 변한다 — 0건 카테고리 포함 여부는 [확인 필요].
- **일별 추이 차트** — 막대 3계열: 환급(파랑)/차감(빨강)/취소환수(보라), y=0 기준선, 만 단위 축약. 데이터가 2일 이상일 때만 표시(page.tsx:723-750).
- **서브탭 6** — 전체 / 카드 수수료 차액(FEE_DIFF) / 배달 수수료 차액(DELIVERY_DIFF) / 취소 환수(CANCEL_CLAWBACK) / 예상매출 대사(ESTIMATED_DIFF) / 미회수 이월(CARRY_FORWARD). 각 탭에 건수 병기(page.tsx:756-772).
- **상세 테이블** — 거래일 / 가맹점(에이전시 뱃지 + 사업자번호) / 승인번호 / 유형(전체 탭에서만 카테고리 뱃지) / 카드사 / 예상수수료 / 실제수수료 / 차액(+파랑=환급, −빨강=차감) / 구분(유형 8종 뱃지) / 상태(반영완료+반영일 / 대기중) (page.tsx:794-867).

### ③ 로직
- **서버 집계 vs 클라 필터** — 매출 유형·카드사 필터는 서버 파라미터(쉼표 구분)로 보내 KPI·차트·목록 전부에 반영되고, 변경 즉시 자동 재조회한다(page.tsx:192-202). 반면 에이전시·가맹점명 필터는 목록 행만 클라이언트에서 거른다(page.tsx:610-616) — KPI·차트에는 반영되지 않는다 [확정].
- **필터 가드** — 매출 유형에서 카드를 빼면 하위 카드사 선택을 자동으로 "전체"로 초기화해 빈 결과를 방지(page.tsx:187-190).
- **정렬 키** — 거래일 → id 2차 정렬(page.tsx:621-624).
- **엑셀** — 단일 시트 "차액정산" 12컬럼(거래일~상태). 차액 컬럼은 환급 유형이면 +원값, 아니면 −원값으로 부호를 입혀 내보낸다(page.tsx:626-663).

### ⑤ 정책 (확정/가설/확인 필요)
- **[확정] 카테고리 5종 체계** — 카드 수수료 차액·배달 수수료 차액·취소 환수·예상매출 대사·미회수 이월이 하나의 차액 정산 대시보드로 묶인다(TY:457, page.tsx:544-550).
- **[확정] 미회수 이월 규칙(화면 문구 기준)** — 환수가 당일 지급액을 초과하면 지급액 0원 처리 후 잔여를 다음 정산에서 차감하며, 매일 자동으로 잔액 0까지 반복(BatchDetailTab.tsx:459-468, settlements/[id]/fee-adjustments/page.tsx:239-244). 정책서 원천 조항과의 대조는 [확인 필요].
- **[확인 필요 · C4]** — "예상매출 대사"는 예상 매출 기반 선정산 후 실제 데이터와 대사한 차이라는 화면 설명만 있고, 가맹점 노출 라벨 "예상 지급 차액"과의 정의 일치는 미확정. 이 탭의 수치로 C4 정의를 확정하지 말 것.
- **[확인 필요 · C1]** — 예상수수료·실제수수료의 요율 근거는 화면에 없음. 특정 요율을 채택해 서술 금지.
- **대기중(PENDING) 건의 KPI 포함 방식** — netAmount에 대기 건이 포함되는지(반영 예정액인지 반영액인지)는 서버 집계 [확인 필요].

### ⑥ 고려사항
- **KPI와 목록의 모집단 불일치** — 에이전시·가맹점명 필터 시 표는 줄어드는데 KPI·차트는 전체 기준 그대로다 [확정]. 화면설계서에 "카드·차트는 서버 전체 기준" 주석 필요, 또는 개선 검토.
- **카드 수 가변** — 기간에 존재하는 카테고리에 따라 KPI 카드 수가 달라질 수 있어 4열 그리드가 2줄로 흐를 수 있다.
- **예상매출 대사 필터 함정** — 원장 미연결 건이라 매출 유형을 하나라도 고르면 사라진다. 툴팁이 있지만 놓치기 쉬움 — 운영 가이드 반영 권장.
- **차액 정산 탭의 '차액'과 다른 화면의 '차액'** — 아래 ⑧의 4용어 표를 반드시 병기해 오독을 막을 것.

## 화면 2. 정산 현황 — 이체 내역 탭

### ① 메뉴 위치·진입 경로
- **위치** — 정산 현황(`/settlement/overview`) 4번째 탭 "이체 내역". 탭 진입 시 최초 1회 자동 조회(page.tsx:179-181).
- **총판 노출** — 노출됨 [확정](page.tsx:292-301, 게이트 없음). 총판 3탭 중 하나.
- **API** — `GET /admin/settlement/transfer-records?dateFrom&dateTo` (HK:312-327).

### ② 구성
- **정렬·엑셀** — 이체일 정렬 토글 + 엑셀 다운로드(TransferRecordsTab.tsx:284-288).
- **KPI 4카드** — 지급 이체(성공건/전체건 + 성공 금액) / 매출 회수(성공건/전체건 + 성공 금액) / 전체 성공(건수·금액) / 전체 실패(건수·금액)(:291-316).
- **날짜별 카드** — 헤더: 날짜 + "N건 (성공 N건)" + 우측에 지급/회수 × 성공·실패 금액 분해(0원 구분은 숨김, 실패 0원이면 실패만 숨김)(:319-346). 본문: 시간/구분/가맹점/금액/수취 은행/수취 계좌/수취인/상태/거래번호 9컬럼 테이블.
- **회수 페어 행** — "회수" 뱃지 + "2단계" 서브라벨, 클릭 시 하위 2행 펼침: ① 출금 "락계좌 → 미지급계정", ② 입금 "미지급계정 → 모계좌" — 각각 시간·계좌·상태·거래번호 표시(:432-535).
- **실패 행** — 거래번호 자리에 쿠콘 오류 메시지(20자 초과 시 말줄임, hover 전체)(:420-426).

### ③ 로직
- **회수 페어 매칭** — 쿠콘 회수 플로우는 출금이체(API 02003700)+입금이체(02001110) 레코드 2건이 생기지만 실제 입금은 1회이므로, 같은 merchantId + 같은 금액으로 페어를 찾아 1행으로 묶는다. 짝이 없으면 단독 행으로 남긴다(:24-87).
- **대표 금액·상태** — 페어의 대표 금액 = 출금액(:89-91). 대표 상태 = 둘 다 성공/확인완료→성공, 하나라도 실패→실패, 그 외 출금 상태를 따름(:93-100).
- **유형 3종** — 지급(DISBURSEMENT)/회수(COLLECTION)/수동 지급(ADMIN_MANUAL). 집계에서 수동 지급은 지급 버킷에 들어간다(COLLECTION이 아니면 전부 지급, :106-109).
- **KPI 집계** — 화면이 페어 묶음 후 재계산한다(서버 집계 필드는 미사용). 성공 = SUCCESS/CONFIRMED. **실패 카드는 건수·금액 모두 FAILED 상태만 합산**(`totalFailedAmount`, :131-164). 요청중·타임아웃은 성공에도 실패에도 안 잡힌다.
- **날짜 헤더 분해** — 헤더의 "실패"는 비성공 잔여(실패+요청중+타임아웃) 기준(:117-129) — KPI 실패 카드와 기준이 다르다 [확정]. 코드 주석(:116)은 "KPI 카드 기준과 동일"이라고 남아 있으나 KPI 변경 이후 낡은 주석이다.
- **엑셀** — 페어를 묶지 않고 원천 레코드를 그대로 낸다(회수 1건이 2행, :229-263). 11컬럼(일자/시간/구분/가맹점명/에이전시/금액/수취은행/수취계좌/수취인/상태/거래번호).
- **클라 필터** — 에이전시·가맹점명(가맹점 ID·사업자번호 포함) 필터는 날짜별 레코드에 적용 후 빈 날짜 제거(:211-223). KPI도 필터된 행으로 재계산되므로 이 탭은 KPI·목록이 일치한다.

### ⑤ 정책 (확정/가설/확인 필요)
- **[확정 · C5] 여기의 '회수'는 매출 회수(스윕)** — KPI 라벨 "매출 회수", 계정 흐름 라벨 "락계좌 → 미지급계정 → 모계좌"(:300,494-517). 정책 문서의 '회수'(과지급 회수)·'미회수금'과는 다른 개념이다. 화면설계서에 반드시 병기.
- **[확정] 상태 5종** — 성공/확인완료/실패/요청중/타임아웃(:10-16). 성공과 확인완료의 업무적 차이(이체 완료 vs 입금 확인)는 [확인 필요].

- **미지급계정** — 회수 중간 경유 계정의 실체(은행 가상계좌인지 내부 계정인지)는 [확인 필요]. 6대 개념의 '미지급금'과 이름이 비슷하나 동일시 금지.

### ⑥ 고려사항
- **실패 집계 기준 이원화** — KPI(실패 상태만) vs 날짜 헤더(비성공 잔여)가 다르다 [확정]. 요청중·타임아웃이 많은 날은 헤더 실패 금액 > KPI 실패 금액. 화면설계서에 두 기준을 명시하고, 통일 여부는 기획 결정 사항으로 남길 것.
- **성공+실패 ≠ 전체** — 요청중·타임아웃이 양쪽 어디에도 안 잡혀 건수 합이 전체와 안 맞을 수 있다 [확정].

- **엑셀과 화면 행 수 불일치** — 화면은 페어 1행, 엑셀은 2행. 대사 시 혼동 방지 주석 필요.

- **[확정 문구/확인 필요 정책] '이틀' 규칙** — "이틀 이상 지난 건은 선정산이 아니라 수수료만 제외한 순지급액 전액을 그대로 이체"가 화면에 고정 문구로 존재. 다만 '이틀'의 판정 기준(달력일/영업일, 기산점이 매출일인지 배치 완료일인지)은 서버 소관이며 C2(지급 캘린더)와 엮여 [확인 필요]. 이 문구로 지급 캘린더를 확정하지 말 것.

## 화면 5. 정산 상세 — 수수료 원장 (건별 원장·배치 원장)

### ① 메뉴 위치·진입 경로
- **위치** — 정산 현황 > 정산 상세 탭(관리자 전용, page.tsx:270-281) > 좌측 정산 목록에서 배치 클릭 → 우측 하단 "수수료 원장 상세" 카드(BatchDetailTab.tsx:677-690).

- **API** — 배치 클릭 시 배분집계(`…/batches/{id}/payouts`) 조회 후, 원장(`…/batches/{id}/ledgers`)을 별도 호출하는 2단 조회(HK:221,257). 엑셀은 기간 일괄 API(`batch-payouts`/`batch-ledgers`, HK:276,285).

### ② 구성
- **아코디언 3계층** — (a) "시스템 이용료 (건별 합산)" 섹션: 거래별 SYSTEM_FEE 원장을 참여자 단위로 합산한 요약(N건 합산 표기, :756-782). (b) 거래별 원장: 매출원 뱃지(카드=남색/배달=주황)+주문번호+매장명+"예상" 뱃지, 우측에 정산액·배분 합계 — 채권매입(MARGIN)·시스템 이용료가 건별로 붙는다(:783-815). (c) 배치 레벨 원장: 거래에 안 붙는 유형(이체 수수료 등)이 배치 줄로만 나온다(:816-841). **즉 건별 원장 = 채권매입·시스템이용료, 이체 수수료 = 배치 줄** [확정].
- **원장 표** — 참여자(뱃지 2종: "납부 → 상대방", "{기록용 참여자} 지급 N원" 전달금 앰버 뱃지) / 역할 / 유형(여러 유형이 섞인 표에서만) / 매출 / 원가 / 수익 / VAT / 순수익 / 배분액 + 소계 행(:864-928). 배분액 색: +초록/−빨강/0 회색.
- **엑셀 "수수료 원장 상세" 시트** — 18컬럼(정산일/매출일/가맹점명/에이전시/주문번호/매출원/매장명/거래금액/수수료 유형/참여자/역할/매출/원가/수익/VAT/**전달금**/순수익/배분액)(:268-291). 화면과 같은 순서(거래별→배치 레벨)·같은 전달금 재귀속 적용(:150-175).

### ③ 로직
- **표시 보정** — 표 렌더 직전 `reattributeSalesPassthrough`로 전달금 귀속을 보정한다(:847, 화면 6 참조). 원장 데이터·배분액은 불변.
- **납부자 원장 판정** — 배분액이 음수이면서 유형이 시스템 이용료/이체 수수료인 줄 = 가맹점 대신 수수료를 부담하는 납부자. 같은 유형에서 양수 배분을 받는 참여자를 "납부 → OOO"로 병기(:851-863).
- **전달금 뱃지** — passthrough+VAT > 0인 줄에 같은 유형의 기록용(excluded) 참여자명으로 "{OOO} 지급 N원" 표시, 식별 안 되면 "영업조직"(:859-863,890-894).
- **시스템 이용료 합산** — 거래별 SYSTEM_FEE 원장을 참여자(payee+role) 키로 전 필드 합산해 배치 요약을 화면에서 만든다(:715-742). 같은 원장이 건별 뷰와 합산 뷰 두 곳에 보인다.

## 화면 6. [공통 모듈] 전달금 재귀속 — lib/settlementLedger.ts

### ① 메뉴 위치·진입 경로
- **화면 아님** — 원장 표시 보정 공통 모듈(2026-08-07 신설). 적용 화면 3곳: 정산 상세 원장 표(BatchDetailTab.tsx:847), 정산 상세 엑셀 수수료 원장 상세(:152), 정산 시뮬레이션 원장 표(simulation/page.tsx:533). 화면설계서에는 세 화면의 공통 규칙 박스로 넣는다.

### ② 구성
- **단일 함수** — `reattributeSalesPassthrough(entries, groupKey)`: 원장 배열을 받아 보정된 배열을 돌려준다. 보정 대상이 없으면 원본 그대로(LG:67-68).

### ③ 로직
- **적용 범위** — 하위→상위 폭포수 배분을 쓰는 수수료 유형만: MARGIN, FEE_ADJUSTMENT(LG:15). 체인 식별은 수수료 유형 + groupKey(거래 단위, 엑셀 일괄에선 `transactionId ?? "batch"`).
- **발동 조건 3가지(전부 충족 시)** — 체인에 하위(LOWER)·상위(UPPER) 참여자가 모두 있고, 하위의 전달금+VAT ≠ 0이며, **하위의 수익이 0**(마진 없이 자리만 차지하는 형식 참여자)일 때(LG:43-51).
- **보정 내용** — 하위: 전달금·전달금VAT를 0으로, 순수익 = 수익+VAT로 재계산. 상위: 전달금·VAT를 넘겨받고 순수익에서 그만큼 차감(LG:53-64). **배분액(payout)은 건드리지 않는다** — 가맹점 차감액과 무관(LG:24).

### ④ 계산식
- 보정 후 항등식 유지: `순수익 = 수익 + 수익VAT − 전달금 − 전달금VAT` [확정 — LG:57,63이 이 식으로 재계산].

### ⑤ 정책 (확정/가설/확인 필요)
- **[확정] 왜 필요한가** — 원장은 영업조직 몫을 항상 하위파트너의 전달금으로 기록한다. 하위가 실재하지 않는 형식 정책에서는 상위가 실제 지급 주체인데, 그대로 보여주면 하위 순수익이 음수로 뜨고 상위의 지급 의무가 드러나지 않는다(LG:17-23 주석).
- **[확정] 표시 보정 한정** — 원장 데이터는 그대로 두는 화면 표기 보정이다(LG:1). **실제 자금 이동 주체·서버 원장의 의미는 [확인 필요]** — 화면 표기를 근거로 자금 흐름을 확정하지 말 것.

### ⑥ 고려사항
- **서버 원장과 화면·엑셀의 불일치** — 서버 raw 데이터를 직접 뽑으면 전달금 귀속이 화면과 다르다. 대사 시 "표시 보정 적용 여부"를 항상 명시할 것.
- **적용 유형 확장 시** — 새 폭포수 유형이 생기면 WATERFALL_FEE_TYPES 갱신 필요(누락 시 구 표기로 회귀).

### ⑦ 엮인 메뉴·화면
- AD_SETTLE_DETAIL_BATCH(원장 표) · AD_SIM/AD_SIM_MULTI(시뮬레이션 원장 표) · 정산 상세 엑셀. 배분 요약 표(payout 기준)는 보정과 무관 — 두 표의 관계 서술에 주의.

### ⑧ 용어
- **재귀속** — 형식 하위파트너의 전달금·순수익을 상위파트너 줄로 옮겨 표시하는 보정. / **폭포수 배분** — 하위→상위로 원가를 넘기며 배분하는 방식(MARGIN·FEE_ADJUSTMENT). / **형식 참여자** — 수익 0으로 자리만 차지하는 정책상 참여자.

## 화면 7. 정산 시뮬레이션 — 원장 표·배분 요약

### ① 메뉴 위치·진입 경로
- **위치** — 사이드바 [정산] > 정산 시뮬레이션(`/settlement/simulation`). 정책 선택 → 거래 입력 → 실행 후 결과 영역에 원장 표들이 나타난다.
- **총판 노출** — 메뉴 비노출 [확정 — participantNavGroups에 없음, 총판 메뉴는 홈+4항목]. 직접 URL 접근 차단 여부는 [확인 필요 — 페이지 자체 가드 없음].
- **API** — `POST /admin/settlement/simulate` — **DB 저장 없는 계산 전용**(simulation/page.tsx:132-162, 상단 안내 문구 :203-206) [확정].

### ② 구성
- **정산 요약 4카드** — 총 거래금액 / 거래 건수 / 총 수수료(가맹점 부담) + sub "부과: 채권매입 N · 시스템 N · 이체 N" / 가맹점 지급액(강조)(:330-351).
- **건별 원장 카드** — 거래마다 #번호 + 유형·금액 + 수수료·정책명(ruleType) 또는 "스킵: 사유" → MARGIN(채권매입 수수료) 표 + SYSTEM_FEE(시스템 이용료) 표(:354-398). **건별 원장은 채권매입·시스템 이용료 두 종류만** [확정].
- **SYSTEM_FEE 건별 합산** — 전 거래의 시스템 이용료 원장을 참여자 단위로 합산한 배치 뷰(:401-408).
- **TRANSFER_FEE(이체 수수료) - 배치당 1회** — 건별 없이 배치 줄 하나(:411-418).
- **원장 표 10컬럼** — 참여자(기록용 태그 + 전달금 앰버 뱃지) / 역할 / 매출 / 매출VAT / 원가 / 원가VAT / 수익 / VAT / 순수익 / 배분액(:539-592). 정산 상세 표보다 VAT 분해 컬럼이 2개 많다.
- **이해관계자 배분 요약** — 참여자(법인·사업자(VAT) 뱃지) / 역할 / 유형(기록용=주황·이탤릭 / 직접배분=파랑) / 채권매입 / 시스템 이용료 / 이체 수수료 / 총 배분액(:421-497).

### ③ 로직
- **원장 표 렌더 전 재귀속** — `reattributeSalesPassthrough` 적용(:533, 화면 6과 동일 규칙). 전달금 뱃지 "{기록용 참여자} 지급 N원"(:569-573).
- **부과액 계산** — 수수료 유형별 부과 총액 = 제외(excluded) 아닌 줄 중 배분액 양수의 합(:196-197). 채권매입 부과 = Σ 거래 수수료(스킵 건 제외, :323-324).
- **시스템 이용료 합산** — 정산 상세와 같은 방식으로 참여자 키 합산(:167-193).

### ④ 계산식
| 항목 | 쉬운 말 | 원어(코드) | 근거 |
|---|---|---|---|
| 총 수수료 sub | 가맹점 부담 수수료의 유형별 부과 분해 | 채권매입 `Σ tx.fee` + 시스템 `chargedSum(SYSTEM_FEE)` + 이체 `chargedSum(TRANSFER_FEE)` | :323-326,343 |
| 부과액 | 기록용 제외, 양수 배분(받는 쪽)의 합 | `ledgers.filter(!excluded && payout>0).Σ payout` | :196-197 |
| 가맹점 지급액 | 서버 요약값(화면 계산 아님) | `summary.merchantPayout` | :345-349 |
| 순수익 | 수익+VAT−전달금(−VAT) — 재귀속 후에도 유지 | LG 항등식 | LG:53-64 |

### ⑤ 정책 (확정/가설/확인 필요)
- **[확정] 기록용 vs 직접배분** — 기록용(PASSTHROUGH)은 폭포수 배분·부과 총액 집계에서 제외(회색 이탤릭·주황 태그). 단 **"장부에만 남는 기록"이라고 단정하지 말 것** — 원장 표에서 전달금의 실지급 상대로 표시된다(화면 표기 확정 · 실제 자금 이동 주체는 서버 [확인 필요]).
- **[확정] 요율은 선택한 정책 상품이 결정** — 정책 셀렉트([ruleType] 정책명)에 따라 결과가 달라진다. 특정 요율 값(C1)을 본 화면 서술에 채택 금지.
- **[확정] 스킵** — 정책이 처리하지 못하는 거래는 "스킵: 사유"로 표기되고 수수료 부과에서 제외(:366-369,323-324).

### ⑥ 고려사항
- **시뮬레이션 ≠ 실제 정산** — 오프라인 차감·플랫폼 차감·차액 정산이 없는 순수 수수료 배분 계산이다. 실제 배치와 나란히 캡처할 때 이 차이를 명시.
- **배분 요약 표는 재귀속 미적용** — 원장 표만 보정된다. 기록용 줄의 총 배분액(주황)과 원장 표 배지가 서로 다른 관점임을 주석으로.

- **총판 노출** — 카드·버튼 모두 노출 [확정 — FeeAdjustmentSummary에 readOnly prop이 없고 조회 전용 화면]. 이력 페이지도 조작 버튼이 없어 총판 열람 가능.
- **API** — 카드: `GET /admin/merchants/{id}/fee-adjustment-summary`(merchantService). 이력: `GET /admin/merchants/{id}/fee-adjustments?status=`(page.tsx:67-88).

### ② 구성
- **진입 카드(가맹점 상세 내, AD_MERCHANT_DT_ADJSTAT)** — 차액 정산 대기(건수+예정 금액, 노랑) / 이번 달 누적 / 전체 누적 3행 + "상세 통계 보기" 펼침(총 환급/총 추가 차감/순 차액) + 하단 "차액 정산이란?" 3단계 설명. **이력이 0건이면 카드 자체를 숨긴다**(FeeAdjustmentSummary.tsx:60-62) [확정].
- **이력 페이지 헤더** — "카드 수수료 차액 정산 이력" + 가맹점명(:151-157).
- **통계 4카드** — 전체 건수 / 환급 N건+금액 / 추가 차감 N건+금액 / 순 차액(:159-192).
- **상태 필터 3** — 전체 / 완료(APPLIED) / 대기(PENDING) — 서버 파라미터로 재조회(:194-211).
- **테이블 9컬럼** — 거래일 / 승인번호 / 카드사 / 정산적용 수수료 / 실제 수수료 / 차액 / 구분(유형 8종) / 상태(대기·완료·취소) / 정산일(appliedAt)(:213-302).
- **프로세스 안내** — "1. 선정산 단계: 정산 당시 적용수수료로 선정산 지급 / 2. 매입 확정: 실제 수수료 확인 후 차액 계산 (정산적용 − 실제) / 3. 다음 선정산: 차액 환급 또는 추가 차감"(:304-321) [확정 문구].

### ③ 로직
- **필터 연동 통계** — 상태 필터를 바꾸면 목록을 재조회하고, 통계 카드도 필터된 목록으로 재계산된다(:38-43,122-132). 즉 "대기" 필터에서는 통계도 대기 건만.
- **통계 모집단 한정** — 환급/차감 건수·금액·순 차액이 adjustmentType이 정확히 REFUND / DEDUCT인 건만 집계한다(:122-132) [확정]. 배달·예상매출·이월·환수 유형이 응답에 섞이면 전체 건수에는 잡히되 환급·차감·순 차액에서 빠진다.
- **차액 부호** — 화면 8과 동일한 TYPE_CONFIG 방식(:90-102).

### ④ 계산식
| 항목 | 쉬운 말 | 원어(코드) | 근거 |
|---|---|---|---|
| 순 차액 | REFUND 금액 합 − DEDUCT 금액 합 (클라 계산) | `totalRefundAmt − totalDeductAmt` | :126-132,183-191 |
| 차액 프로세스 | 정산적용 수수료 − 실제 수수료 → 다음 선정산에서 환급/추가 차감 | 안내 문구 | :304-321 |
| 카드 요약 | 대기/이번 달/전체 누적 (서버 집계) | `pendingCount/thisMonth*/total*` | FeeAdjustmentSummary.tsx:15-24 |

### ⑤ 정책 (확정/가설/확인 필요)
- **[확정] 차액 정산 3단계 수명주기** — 선정산(적용 수수료) → 매입 확정(차액 계산) → 다음 선정산(환급/차감 반영). 진입 카드와 이력 페이지가 같은 문구를 쓴다.
- **[확정] 상태 3종** — 대기(PENDING)/완료(APPLIED)/취소(CANCELLED). 취소 상태의 발생 조건·업무 의미는 [확인 필요].
- **[확인 필요] '카드' 한정 여부** — 화면 제목은 "카드 수수료"인데 TYPE_CONFIG에는 배달·예상매출·이월 등 8종이 있다. 서버가 이 API에서 카드 유형만 내려주는지, 다른 유형도 오는지 확인 필요 — 통계 왜곡 여부가 여기에 달렸다(③ 참조).
- **[확인 필요 · C1]** — 정산적용 수수료의 요율 근거(카드사별 수수료 관리 값과의 관계)는 이 화면에서 단정 금지.

### ⑥ 고려사항
- **통계 왜곡 가능성** — REFUND/DEDUCT 외 유형이 응답에 있으면 "전체 건수"와 "환급+차감 건수"가 안 맞는다 [확정 — 코드 구조]. 서버 응답 범위 확정 후 집계식 보강 필요.
- **취소 필터 부재** — CANCELLED 라벨은 있는데 필터 버튼이 없어 전체에서만 보인다.
- **필터 연동 통계의 양면성** — 통계가 필터를 따라가는 것은 이 화면뿐(차액 정산 탭 KPI는 서버 전체 기준) — 화면 간 집계 기준 차이를 설계서에 명시.
- **디버그 로그 잔존** — console.log 다수(:49,52,58,134) — 정리 대상(경미).
- **진입 카드 숨김 규칙** — 이력 0건 가맹점에선 카드가 아예 없어서 "차액 정산이 없는 상태"를 화면에서 확인할 수 없다 — 기획 의도인지 확인.
