# PayHug 정산 로직

## 1. 기본 산식

기본 구조:

```
전일 매출
- 카드 수수료
- 배달 플랫폼 수수료
- PayHug 채권매입수수료
- 이체수수료
+ 플랫폼 환급
+ 추가 지급
- 선정산 제외금액
- 이전 과지급 회수금
= 최종 선정산 지급액
```

## 2. 카드 선정산 산식

기존 협의에서 파악된 산식:

```
최종 선정산금액
= (전일 전체 매출 - 카드수수료)
× (1 - PayHug 수수료율)
- 이체수수료 300원
```

다만 실제 서비스에서는 플랫폼별·항목별 수수료 계산 순서와 버림 정책을 재확인해야 한다.

`확인 필요` 위 산식은 이체수수료를 지급액에서 빼는 자리에 두는데, `PAYHUG-260 본문`의 지급액 예시는 이체수수료를 빼지 않고 계산한다. 항목 관계와 대조는 02 §1 「선정산 지급액 구성 항목」, 판단은 07 §7-21.

## 3. 수수료

### PayHug 수수료

- 채권매입수수료
- 서비스 이용 수수료
- 건별 또는 비율 기반으로 적용

#### 채권매입수수료 산식

`확정` 산식 원문. (Figma `EUK2P3tDOkprcnRmMqNns4` `5:71` 엑셀 「용어 정의」 행 47)

```
채권매입수수료 = 결제주체지급금액 × 선정산수수료율 (소수점이하 올림)
```

`확정` 선정산수수료율은 정산금채권양수도계약서 제17조에 %단위로 기재된 비율을 가리킨다. (`5:71` 행 48)

`확인 필요` 요율 값은 미확정이다. 문서 표기는 `1%`, 26.08.09 원장 실측은 `0.6% + 올림`이고 둘을 잇는 문장이 없다 (07 §7-27, C1). 용어와 배분 체인은 02 §7.

`확정` 시스템이용료 산식은 원문에 `순지급액 × 0.1% (부가세 0.01%)`로 적혀 있다. 기준 금액이 선정산 대상액이 아니라 순지급액이라는 점이 채권매입수수료와 다르다. 요율 값 자체는 C1 미확정 범위다. (`EUK2P3tDOkprcnRmMqNns4` `22:282`)

### 전산 수수료

- 가맹점 1개 기준 하루 1회
- 이체수수료 300원

### 외부 수수료

- 카드사 수수료
- 배달 플랫폼 수수료
- 배달앱 건별 수수료
- 광고비 등 플랫폼 차감 항목

### 세금계산서 과세 구분

`확인 필요` 채권매입수수료·시스템이용료·이체수수료 중 어느 것이 과세 대상인지, 발행 주체와 수취 주체가 누구인지, 집계 주기가 월 단위인지 정의되어 있지 않다. (`PAYHUG-192 본문`)

## 4. 버림·반올림 정책

카드사별 순지급액에 수수료율을 적용한 금액과 전체 합계 기준 계산 사이에 차이가 발생할 수 있다.

확인 필요:
- 건별 버림
- 카드사별 버림
- 일별 합계 후 버림
- 소수점 처리 단위
- 화면 표시값과 실제 지급값의 차이

### 배달의민족 기간 묶음 정산금의 일자 배분

`확정` 배민 정산금은 기간 묶음으로 오므로 항목별 기준을 정해 거래일에 나눠 붙인다. (`PAYHUG-171 본문`)

| 항목 | 기준 |
|---|---|
| 일반 조정 | 주문번호로 추적한 뒤 그 거래일자 |
| 우리가게클릭비 | 클릭발생일 |
| 부가세 | 거래일별 배율로 나눠 계산(사사오입 반올림) |

`확정` 부가세 사사오입으로 수수료 1원 차이가 생기지 않는다. 일별 계산의 부가세 합을 다시 일별로 역산한 것이기 때문이다. (`PAYHUG-171 코멘트 2026-08-30`)

`확인 필요` 위 답변의 검증 산출물이 티켓에 없다.

### 표시 자릿수

`확인 필요` 어드민 원장의 소수점 6자리 표시가 계산 정밀도인지 표시 정밀도인지 구분되어 있지 않다. 권한별 표시 자릿수(관리자 6자리·총판 정수)도 티켓에 예시로만 적혀 있다. (`PAYHUG-200 본문`)

## 5. 지급 시점

- 전일 매출 기준
- 매일 오전 10시 데이터 업데이트
- 다음날 오전 11시 30분과 오후 6시, **하루 2회 지급** (운영 확정, 2026-07 고객센터 반영)
- 주말·공휴일 포함 매일 지급
- 오전 11시 30분 이후 매입·확인된 금액은 오후 6시 추가 선정산으로 반영

`확정` 하루 2회라는 사실은 두 출처가 맞물려 선다. 어드민 모계좌 잔액 새로고침이 필요한 시각이 오전 11시 30분·오후 6시 두 개이고 두 시각의 기준이 「선정산 이전」으로 적혀 있으며(`PAYHUG-227 본문`), 가맹점 화면 안내문이 같은 두 시각을 선정산 지급 완료 시각으로 적는다(merchant `app/settlement/account/excluded/page.tsx:16`).

`확정` 이것은 하루 중 몇 시에 몇 번 지급하느냐의 축이다. 거래일로부터 며칠 뒤에 지급하느냐(계약 '매일' · 운영 D+1 · DB 설계 익익영업일)는 다른 축이며 미확정이다(C2). 두 축을 섞어 읽지 않는다.

`확정` 바이패스 지급 시각(오전 11시 40분 전후)은 오전 회차 직후다. (`PAYHUG-208 본문`·`PAYHUG-253 본문`)

### 기준시간과 기산일

`확정` 채권매입대금을 산출하는 기준시간은 전일 00시 00분 ~ 전일 23시 59분이다. 계약서가 정의한 `기준매출`의 시간 범위다. (Figma `EUK2P3tDOkprcnRmMqNns4` `5:66` 엑셀 「용어 정의」 행 13, 페이허그서비스 이용계약서)

`확정` 정책 원문에 적힌 정산 주기는 `주말·공휴일 포함 D+1 정산`, 입금 시간은 `오전 11:30 ~ 12:00`이다. (`EUK2P3tDOkprcnRmMqNns4` `5:64`)

`확정` 같은 파일의 프레임은 지급 일시를 `매일 선정산 대상 11시30분, 18시`로 적는다. (`5:39`·`5:26`)

`확인 필요` 두 원문이 회차에서 갈린다. 워드 캡처는 오전 1회, 프레임은 오전·오후 2회다. `D+2` 표기는 이 파일에 없다. 기산일 축의 정합은 C2.

### 회수 대사일

`확정` 회수 대사일은 매일 19시다. 빠른계좌조회(쿠콘 스크래핑) 수집주기 10시 30분·18시 30분을 참고해 정한 시각이며, 이날 대사로 다음 선정산일에 회수하거나 환급할 금액이 정해진다. (`EUK2P3tDOkprcnRmMqNns4` `5:58`)

`확정` 여기서 쓰는 회수는 다음 선정산 금액에서 차감하거나 환급하는 축이다. 어드민 「매출 회수」(락계좌→모계좌 스윕)와 바꿔 적지 않는다.

### 매출 데이터 수집 범위

`확정` 매일 수행하는 매출 스크래핑의 조회 범위는 3일이다. (`PAYHUG-233 본문`)

`확인 필요` 취소·매입·후보정으로 3일 범위 밖에서 늦게 반영되는 건을 잡기 위한 월 단위 수집(매월 1일·1개월분)과 계약 심사용 3개월 수집은 개발 착수 전이다. 스크래핑이 1건 오류나면 처음부터 다시 돌리는 처리가 없어 재시도 정책 자체가 설계되지 않았다 (07 §7-26). (`PAYHUG-233 본문`·`PAYHUG-233 코멘트 2026-08-30`·`2026-08-31`)

## 6. 정산 후 변동

선정산 완료 후 다음 변동이 발생할 수 있다.

- 매입 지연
- 추가 매입
- 승인 취소
- 매입 취소
- 환불
- 플랫폼 정정
- 프로모션 환급
- 광고비 환급
- 스크래핑 데이터 갱신
- 실제 입금액 변경

처리 방향:

- 추가 지급 필요: 차기 지급 또는 바로이체
- 초과 지급 발생: 회수건 생성
- 지급 전 음수 발생: 당일 지급액에서 차감
- 지급 후 음수 발생: 미회수금으로 관리

## 7. 바이패스 판정

### 판정 기준

락계좌로 들어온 입금 건을 아래 기준으로 가른다. (`PAYHUG-208 본문`)

| 판정 기준 | 처리 |
|---|---|
| 입금일 < 선정산 시작일 | 바이패스 대상 |
| 선정산 시작일 ≤ 입금일, 거래일 < 선정산 시작일 (예: 하나카드 D+1 입금) | 바이패스 대상 |
| 선정산 미적용 플랫폼·카드사 입금 (예: 카드 선정산 미연결 가맹점) | 바이패스 대상 |
| 입금일·거래일 모두 선정산 시작일 이후 | 선정산 대상 (바이패스 제외) |

### 판정에 쓰는 세 날짜

`확정` 판정은 세 값의 비교로만 이뤄진다.

- 거래일: 가맹점에서 결제가 일어난 날
- 입금일: 그 거래의 정산금이 락계좌에 들어온 날
- 선정산 시작일: 그 가맹점의 선정산이 개시된 날

`확정` 거래일과 입금일은 어긋난다. 하나카드 D+1 입금처럼 거래일은 시작일 이전인데 입금일은 시작일 이후인 건이 있어, 입금일만 보면 바이패스 대상을 놓친다. 위 표 2행이 그 경우다. (`PAYHUG-208 본문`)

`확정` 세 날짜는 시각과 다른 축이다. 매출 데이터 업데이트 시각(오전 10시), 선정산 지급 시각(오전 11시 30분·오후 6시, §5), 바이패스 지급 시각(오전 11시 40분 전후, `PAYHUG-208 본문`)은 실행 순서를 정할 뿐 판정 기준에 들어가지 않는다.

`확정` 판정에는 선정산 중단·재개 시점과 플랫폼·카드사별 선정산 적용 여부, 해당 거래의 선정산 지급 여부도 함께 본다. 입금일만으로 판단하지 않는다. (`PAYHUG-253 본문`)

`확정` 거래일에 그 플랫폼이 선정산 중이었는지를 보는 기준은 02 §5의 거래 단위 대상 판정과 같은 규칙이다. (`PAYHUG-186 본문`·`PAYHUG-253 본문`)

## 8. 선정산 지급 후 원거래 취소

### 원칙

`확정` 채권매입 후 발생한 원거래 취소에 따른 원금 손실은 가맹점이 부담하고, 이미 발생한 채권매입수수료는 환급하지 않는다. (`PAYHUG-260 본문`)

### 회수액 산식

```
회수액 = 순지급액 전액
가맹점 부담 차액 = 회수액 − 선정산 지급액 = 채권매입수수료 + 시스템이용료
```

| 항목 | 금액 | 근거 |
|---|---|---|
| 순지급액 | 10,000원 | 티켓 예시 |
| 채권매입수수료 | 100원 | 티켓 예시 |
| 시스템이용료 | 11원 | 티켓 예시 |
| 선정산 지급액(미리받는돈) | 9,889원 | 10,000 − 100 − 11 |
| 회수액 | 10,000원 | 순지급액 전액 |
| 가맹점 부담 차액 | 111원 | 10,000 − 9,889 = 100 + 11 |

`확정` 이체수수료는 취소와 관계없이 부담주체가 일별 발생비용으로 부담한다. 회수액에 더하지 않는다. (`PAYHUG-260 본문`)

`확정` 여기서 쓰는 회수는 가맹점에게 나간 지급액을 되찾는 축이다. 어드민 「매출 회수」(락계좌→모계좌 스윕)와 플랫폼 조정 회수는 다른 축이다.

`확인 필요` 예시 금액에서 역산되는 비율을 요율 근거로 쓰지 않는다 (07 §7-18, C1).

`확인 필요` 회수 실패 시 처리 경로와 6대 개념 등재 위치가 티켓에 없다 (07 §7-22).

케이스 정리는 04 §9.

## 9. 플랫폼 정산금 지급일

플랫폼·카드사가 정산금을 락계좌에 넣는 날이다. 페이허그가 가맹점에 지급하는 시각(§5)과 다른 축이다.

### 쿠팡이츠

`확정` 쿠팡이츠는 정산기준일을 내려주지 않고 예고 지급일이 실제 입금과 어긋난다. 지급일은 시스템이 영업일 기준 D+4로 직접 산출한다. 운영 배포일 2026-08-22. (`PAYHUG-171 본문`)

`확정` 영업일 판정에 공휴일 캘린더 공공 API를 쓴다. 주말·공휴일·대체공휴일을 포함하며, 노동절·제헌절을 넣은 결과가 실제 쿠팡 지급 캘린더와 일치함을 실측으로 확인했다. (`PAYHUG-171 본문`)

`확정` 캘린더 갱신 주기는 매주 월요일이다. 캘린더 데이터가 수집되기 전이면 해당 건의 정산을 보류하고 알림 처리하며, 수집되면 정상 처리한다. (`PAYHUG-171 본문`)

`확인 필요` 하위 개발 PAYHUG-245(쿠팡이츠 지급일 확정 로직 수정)가 진행 중이라 D+4 규칙 적용이 완결되지 않았다.

### 카드

`확정` 카드사 정산예정일은 매출일 + 2영업일이다. (`PAYHUG-229 본문` 2차 미팅 2026-08-30)

`확인 필요` 같은 자리에 적힌 「평균 만기 2.0일 · 월~목 거래 1일 · 금토일 거래 3일」은 일수만 단순 평균하면 (1×4 + 3×3) ÷ 7 = 1.857일이라 2.0일과 맞지 않는다. w금융일수의 가중치가 금액이므로 단순 평균과 다를 수 있으나 산출 근거가 티켓에 없다. 이 값은 투자자 어드민 산식의 전제이며 C2를 해소하지 않는다.

`확인 필요` 「매출발생일 다음 날 선정산이 지급되어 플랫폼 정산 예정일과 하루 차이가 난다」는 서술은 금융일수를 세는 전제로 적힌 것이다. C2(지급 캘린더)를 확정하는 근거로 쓰지 않는다. (`PAYHUG-229 본문` 2차 미팅 2026-08-30)

## 10. 당일 차감 대상액이 지급 대상액을 넘을 때

`확정` 차감 대상 금액이 당일 선정산 대상액보다 크면 그날 차감되지 않고 이월되어 다음 정산일에 차감된다. 8/24 발생 광고비가 8/25 선정산의 차감 대상이었으나 그날 차감 가능한 매출이 없어 8/26 선정산에서 8/25 발생 광고비와 함께 차감된 사례가 있다. (`PAYHUG-240 본문`)

## 11. 선정산 지급액 산식

### 정책 원문 (26.08.15)

`확정` 항목 정의와 산식 원문. (Figma `EUK2P3tDOkprcnRmMqNns4` `77:311`·`77:312`·`77:329`)

| 항목 | 정의 원문 |
|---|---|
| 총 매출액 | 연동된 플랫폼 예상 매출액 (승인 내역, 입금 예정액) |
| 총 수수료 | 연동된 플랫폼 예상 수수료 (예상 수수료율 적용) |
| 순지급액 | 총 매출액 − 총 수수료 |
| 선정산 제외액 | 선정산 대상에서 제외되는 금액 (바로이체, 이미지급 포함) |
| 거래 수수료 차액 | 실제수수료 − 예상 수수료 (거래일 기준) |
| 선정산 대상액 | 계산서 발행에 따른 채권 매입 금액. 순지급액 − 선정산 제외액 − 거래수수료 차액 |
| 선정산 수수료 | 채권매입 수수료, 시스템이용료, 이체 수수료의 합계 |
| 정산 반영 수수료 차액 | 일별 정산일 차이로 발생하는 수수료 차액 |
| 플랫폼 차감 | 광고비 등 |
| 플랫폼 환급 | 프로모션, 상생요금제 환급, CS 조정액 등 |

```
선정산 지급액(미리받는 돈)
= 선정산 대상액 − 선정산 수수료 − 정산 반영 수수료 차액(주문취소·승인취소·매입취소 포함) − 플랫폼 차감액, 플랫폼환급액
```

`확정` 정산 반영 수수료 차액은 이해관계자에게 배분된 분배 수수료 차액의 합과 같아야 한다. (`77:329`)

`확정` 플랫폼 차감·플랫폼 환급으로 분류되지 않는 추적 불가능한 금액은 부호 상태에 맞춰 매출액이 큰 플랫폼의 차감액 또는 환급액에 포함한다. (`77:329`)

### 현행 어드민 코드의 산식

`확정` 코드가 계산하는 순서는 아래와 같다. (admin `app/settlement/overview/PreSettlementTab.tsx:98`)

```
선정산 지급액
= 선정산 대상액 − 선정산 수수료 + 정산 반영 수수료 차액(취소 환수 포함) − 오프라인 차감 − 플랫폼 차감 + 플랫폼 환급
```

`확정` 화면에 찍히는 부호는 그날 값의 부호이며, 산식은 항상 부호를 포함해 더한다. `미회수 이월`·`오프라인 차감`은 값이 있을 때만 붙는 조건부 항이다. (admin `PreSettlementTab.tsx:466`·`:467`)

`확정` 어드민 화면 캡처 2건의 표기 산식이 화면 값과 맞는다. 지급액 두 줄은 코드 산식과 같은 방식이다.

### 남는 상충

`확인 필요` **정산 반영 수수료 차액의 부호가 정책과 코드에서 갈린다.** 정책 원문은 `− 정산 반영 수수료 차액`, 코드는 `+ 정산 반영 수수료 차액`이다. 다만 코드 주석이 이 값과 건별 거래 수수료 차액은 모집단도 부호 규약도 다르다고 적으므로 결과가 같을 수 있다. 단정하지 않는다 (07 §7-29). (`77:329` / admin `PreSettlementTab.tsx:98`·`types/settlement.ts:434`)

`확인 필요` 정책 원문이 마지막 항을 `− 플랫폼 차감액, 플랫폼환급액`으로 쉼표로 묶어, 환급까지 빼는 것으로 읽힌다. 코드는 플랫폼 환급을 더한다. (`77:329` / admin `PreSettlementTab.tsx:98`)

`확인 필요` 선정산 대상액 산식이 두 갈래다. 26.08.15 정책 원문은 거래수수료 차액을 빼고, 세금계산서 기준을 적은 메모는 `순지급액(매출액−예상수수료) − 선정산 제외액(바로이체) = 선정산 대상액(세금계산서발행기준)`으로 그 항이 없다. (`77:329` / `22:287`)

`확인 필요` 8/15 화면은 선정산 제외액을 `−279,789`, 거래 수수료 차액을 `−33,821`로 음수 표기해 놓고 계산은 그 절댓값을 빼는 방식이다. 표기 부호와 계산 부호가 어긋난다. (`77:328`)

부호 규약과 라벨 구분은 02 §9.
