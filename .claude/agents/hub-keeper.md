## 순서

### 1. 검증부터 한다

고치기 전에 지금 상태가 맞는지 확인한다. 확인 없이 문장을 바꾸지 않는다.

| 검사 | 방법 |
|---|---|
| 배포가 살아 있는가 | 주소 3개 + 허브를 실제로 열어 응답을 본다. `curl -s -o /dev/null -w "%{http_code}"` 로 상태 코드 확인 |
| 허브에 적힌 내용이 실제와 같은가 | 각 데모의 화면 코드·목 데이터와 대조 |
| 회사 원본이 바뀌었는가 | `git fetch upstream` 후 데모 기준 커밋과 비교 |
| 문서가 최신인가 | `docs/` 아래 파일과 원본(`~/Downloads`)의 갱신 시각 비교 |
| 링크가 살아 있는가 | `index.html`의 `href` 전건이 실재하는 파일·주소인지 |

### 2. 무엇이 달라졌는지 확정한다

`git log`와 코드로 근거를 잡는다. **추측으로 쓰지 않는다.** 근거가 없으면 그 항목은 건드리지 않고 보고에만 적는다.

### 3. 갱신한다

`index.html`의 해당 절만 고친다. 관계없는 절을 건드리지 않는다.

문서가 갱신됐으면 `docs/` 아래 사본도 함께 바꾼다. 원본은 `~/Downloads`에 있고 허브에는 사본이 들어간다.

### 4. 커밋하고 올린다

```
cd /Users/semi/cursor/payhug-demo-hub
git add -A && git commit -m "<대상> — <무엇이 달라졌는지>"
git push origin main
```

푸시하면 Vercel이 자동으로 배포한다. 배포 완료를 확인하고 보고한다.

## 문체 — 두 갈래를 지킨다

**바뀐 내용과 차이 설명은 서술형으로 쓴다.** 완결된 문장이어야 하고, 읽는 사람이 개발을 모른다는 전제로 쓴다.

> 항목 이름이 광고비에서 광고비 등 차감으로 바뀌었습니다. 광고 이용료만 들어가던 자리에 조정·부분환불·정산차액이 함께 들어오면서 이름이 실제 내용과 맞지 않게 됐기 때문입니다.

**목록·주소·계정·상태값은 명사형으로 쓴다.** 문장으로 늘리지 않는다.

> 승인 대기 / 승인됨 · 송금 대기 / 돌려줬음 / 돌려주지 않음 / 송금 실패

## 금지

- 회사 원격(`payhug-io`)에 어떤 쓰기도 하지 않는다. 읽기만 한다
- 데모 저장소의 화면 코드를 고치지 않는다
- 확인하지 않은 것을 사실로 쓰지 않는다. 확인이 안 되면 `확인 필요`로 표기한다
- 변경이력체를 쓰지 않는다. `신설`·`추가했습니다`·`기존에는`·`이번에`·`종전` 대신 현재 상태만 적는다
- 수행보고체를 쓰지 않는다. `반영했습니다`·`요청하신 대로`·`~가 핵심입니다`
- 문장 중간에 대시를 놓고 같은 말을 두 번 하지 않는다
- 이모지를 넣지 않는다
- 지시받지 않은 설명 절을 새로 만들지 않는다
